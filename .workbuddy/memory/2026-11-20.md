### 关键教训（本次踩的三个坑）

1. **分频 off-by-one**：首版"执行后装 reload"，reload=1 变隔拍执行。
   host 替身用例 s_cnt=[6,6,6,6,6] 当场抓住。正确语义：执行后装 reload-1。
2. **生成器返回值不是自由的**：让 Gen_Rte 返回头文件路径后，building.py 的
   `Generate()` 把 .h 当编译源注册（PkgGlob 为它写 SConscript → SCons 报
   "don't know how to build .h"）。生成器只产头就必须 return []。
3. **隐式声明**：main.c 调 Rte_MainFunction 忘 include rte.h，
   GCC 只给 warning 且能链过 —— 双镜像重建后 grep warning 才发现。
   链接成功 ≠ 声明正确。

## 10.6 第一条完整业务闭环：CAN1 控制 → LED 状态机 → CAN0 上报

**状态**：Host 10/10、静态回归 10/10、双镜像零警告；上板脚本待跑。

### 关键取舍：控制复用 CCVS 而非新起报文

- CAN1 的 34 条 RX 由 `can1.dbc` 注入，而 DBC 是客户资料（gitignore）。
  新报文要改注入脚本 + 多网络通道映射（生成器按网络下标分配控制器号），
  代价大；第一版复用 `CCVS.ParkingBrakeSwitch`（bit 2|2，0/1/2/3 语义天然匹配）。
- 状态挂 CAN0 已有 `0x200`（100 ms）的空位 bit 10–15，不动 M10 的原有信号。
- 换成专用报文时只改 `Com.json` + `Board.json` 的 ref，业务不动 —— 这正是要证明的。

### 实现

- 新增 `led_biz.c/.h`：500 ms 亮相 / 500 ms 灭相（50 拍），非阻塞；500 ms 无
  **有效**命令停（按有效命令计时，不按帧到达 —— 持续发 raw 2/3 也会超时停）。
- 上报 5 位：mode(0=停/1=闪/3=未收到) / out / phase / fault_timeout / fault_cmd。
  `LED_OUT` 只表示驱动成功提交（无电气反馈，Host 直连 DOUT 写必失败 → 恒 0）。
- RTE 端口 +6、调度表 +LedBiz；BcmSig 绑定 +6（RX 为同一 Com 信号的第二个绑定，超时 500）。

### 验证踩坑

1. `Rte_Read` 对"对方报 FAULT"返回 **E_OK + ERROR**，不是 E_INVALID —— 只看返回值
   会漏判无效命令；已在业务里显式判 ERROR/INVALID。
2. portmap P1b 禁止把端口号变量传给 `Rte_Write`（包装函数也不行），
   已改为每处直写 `RTE_PORT_*`。
3. 变体配置必须保留业务依赖的端口：LED_R 端口改为绑 LED_G，而不是删掉。
4. 超时故障恢复：任何有效命令都要清 timeout 位（原先只在首条命令时清，漏了）。

### 上板抓到的真 bug：超时被算了两遍（1 s 才停）

- 现象：帧停发 750 ms 后板子仍在闪，`fault_to=0`（脚本 timeout 用例 3 项 FAIL）。
- 根因：BcmSig 的 500 ms 是**PDU 到达年龄**，在窗口内 `Rte_Read` 仍返回 OK；
  LedBiz 每拍都当"新有效命令"把自己的 50 拍计数器清零 → 实际超时 = 500 ms
  （年龄窗口）+ 500 ms（业务计数）= 1 s。
- 修正：两条路径分开 ——
  - `MAX_AGE_EXCEEDED`/`NEVER_RECEIVED`（帧没了）→ **立即**停；
  - 帧在但值无效（raw 2/3）→ 业务 50 拍计数到 500 ms 再停。
- Host 补了"帧完全停发 60 拍"用例（此前只测了"发无效值"），一跑就复现，修正后 12/12。
- 教训：**同一个时间语义只能有一个计时者**；两个 500 ms 串联不会互相校验，只会相加。
