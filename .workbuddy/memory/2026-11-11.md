## M9 网络管理：CanNm + Nm + ComM 状态镜像（26/26 上板通过）

镜像 `text 135832 / data 188 / bss 6632`（相对 M8：text +5.5 KB）。
全回归：M0 26、M2 40、M3 17、M4 23、M5 24、M6 23、M7 16、M8 11、M9 26 —— 共 206 项全过。

### 分层
```
应用 main.c           只调 Nm_NetworkRequest / Release / PassiveStartUp
   Nm（208 行，原样）   按 busType 分发
  ComM（128 行，自写）  状态镜像 + 弱符号 ComM_Log → 串口
 CanNm（1183 行，原样） 状态机 / 定时器 / CBV
  CanIf → 邮箱 11(TX) / 12(RX)，0x500
```

### 关键参数
- `CANNM_MAIN_FUNCTION_PERIOD = 10`（ms，与 BSW_PERIOD_MS 一致）
- **配置表里的时间字段是"主函数周期数"，不是毫秒** ——
  用 `CANNM_CONVERT_MS_TO_MAIN_CYCLES()` 换算（与 AS 生成器一致）。
  误填毫秒值 → 周期慢 10 倍且不报错
- MsgCycleTime 200ms / RepeatMessageTime 800ms / NmTimeout 2000ms / WaitBusSleep 2000ms
- NodeId 0x42，CBV 在 byte1，NID 在 byte0
- 开了 `CANNM_USE_STD_TIMER` 和 `CANNM_REQUEST_BIT_AUTO_SET`
- 关了 RemoteSleepInd / CoordinatorSync / GlobalPn / CarWakeup / ComUserData / PassiveStartupRepeat

### 四个坑（都是"不报错只不工作"型）

**① `Nm.c` 的 ComM 通知由 `#ifdef USE_COMM` 包着，不是 `USE_NM`**
- 四处：`Nm.c:139/149/159/169`
- 只定义 USE_NM → NM 照跑照发，但 `!m` 永远 `comm=NO_COM`
- 全仓只有这 4 处用 USE_COMM，定义安全（`Nm/SConscript` 已注明）

**② CanNm ↔ Nm 双向引用，不能靠 LIBS 排序**
- 本工程链接不带 `--start-group`，静态库单次扫描必有一边解析不到
- 解法同 as-master：两库互不声明，都进最终链接行

**③ PduR 的 PduHandleId 必须填 0**
- `CanNm_RxIndication` / `CanNm_TxConfirmation` 把首参当**通道下标**
- 填 CanIf 的 PDU 号（10/4）就是越界读，C 编译器看不出来
- 已在 `PduR_Cfg.h` 标 `@warning`

**④ 验收脚本的计时基线比固件更容易错**（首发 24/26，两个失败全是脚本）
- "CBV 请求位没置"：捕获窗口跨过 800ms 边界，混进 NormalOperation 的 0x10 帧
- "PREPARE 耗时 1.3s 不是 2s"：计时起点在"打完 note 之后"，
  而 `nm_state()` 一次串口往返 0.2s，两条 note 把起点推后 0.9s
- 修法：**先抓帧再查状态**；计时从"最后一帧对端报文"算起

### 实测行为（可复现）
```
初始        comm=NO_COM(0)        cannm=BUS_SLEEP(1)      无 0x500
!a 0.15s    comm=FULL_COM(2)      cannm=REPEAT_MESSAGE(5) CBV=0x11
!a 1.0s     comm=FULL_COM(2)      cannm=NORMAL_OPERATION(4) CBV=0x10，周期 200ms
!R +0.6s    —                     cannm=READY_SLEEP(3)    停发
!R +2.6s    comm=FULL_COM_READY_SLEEP(3)  cannm=PREPARE_BUS_SLEEP(2)
!R +4.6s    comm=NO_COM(0)        cannm=BUS_SLEEP(1)
!A          comm=FULL_COM(2)      cannm=REPEAT_MESSAGE(5) CBV=0x00（不冒充主动唤醒）
!A +0.8s    —                     cannm=READY_SLEEP(3)    无本地请求自动回落
```

### "可被唤醒"的边界（必须说清楚）
✅ 本节点请求（`!a`）
✅ 别的节点在发 → NmTimeout 不断重启，本节点不睡（实测对端发 3s 一直 READY_SLEEP）
⚠️ 收发器唤醒 → EcuM → `Nm_PassiveStartUp`：手动验通（`!A`），EcuM 未接
❌ 真正把 MCU 从低功耗叫醒：属 EcuM + 平台，M10

**ComM 是状态镜像，不会让 MCU 睡觉** —— BUS_SLEEP 只是"NM 认为可以睡"，
功耗数据不能拿来做结论。

## M10 信号层：Com 接入（22/22 上板通过）

镜像 `text 140800 / data 216 / bss 6672`（相对 M9：text +5.0 KB）。

### 范围：只接机制，不接业务信号（用户明确要求）
灯光/门锁/雨刮位布局来自整车通信矩阵，现在没有。硬编假布局将来全要改，
且分不清哪些是当时编的。所以用 3 个**边界信号**把机制钉死：

| 信号 | 起始位 | 宽度 | 验证点 |
|---|---|---|---|
| TX_COUNTER | 0 | 8 | 字节对齐打包，每帧 +1 |
| TX_FLAG | **9** | **1** | 非字节对齐单 bit（byte1 的 bit1） |
| TX_LEVEL | 16 | **12** | 跨字节不占满（byte2 + byte3 低 4 位） |
| RX_COUNTER | 0 | 8 | 解包 + 信号超时替换 0xEE |
| RX_TEMP | 16 | 16 | **Motorola 大端** |

接真实信号只改 `Com_Cfg.c` 一张表，`Com.c` 不动。

- **Com_Cfg.c 编进 Com 库**（不是平台库）：`Com_GlobalContextType` 随 `USE_DCM` 变字段，
  配置与实现必须同一翻译环境，否则 `Com_Config.context` 越界写

### 必需宏（少一个就静默失效）
- `COM_USE_CAN` —— 不定义则 `Com_MainFunctionTx`/`Com_TriggerIPDUSend` **整段被编译掉**，
  零告警、API 全返回 E_OK、总线上永远没帧
- `COM_USE_SIGNAL_CONFIG` —— 没有信号级超时/替换
- `COM_MAIN_FUNCTION_PERIOD=10` + `COM_CONVERT_MS_TO_MAIN_CYCLES`
- 不定义 `COM_USE_MAIN_FAST`（多一个主函数=多一个"没被 tick 就不发"的位置）

### 三个坑

**① 大端信号的 `BitPosition` 是 7，不是 0**
- 填 0 时 `01 23` 读回 **0x9180**（左移 7 位），`FFFF` → 0xFF80
- `Std_BitGetBigEndian()`（`std_bit.c:33`）把 bitPos 当"从字节 LSB 数起的位序号"，
  大端起点是字节最高位 = 7
- 规则：大端 `BitPosition = 7 - 字节内偏移`；小端仍是 `起始位 & 7`
- 不报警，值还落在合法范围（25℃ → 8961℃）

**② TX/RX 不能共用 ID**
- 最初都写 0x200，结果接收测试没法做：板子每 100ms 也在发，注入就撞车
- 拆成 0x200 发 / 0x201 收

**③ M10 的周期流量暴露了潜伏的 SDK 缺陷（最重要）**
- M2 的 `!s`(STOPPED) → `!g`(STARTED) 开始失败：控制器永久静默
- 把 Com 分组停掉再走同样序列 → 正常恢复
- 即：**控制器停止期间只要有一次 `Can_Write`，就再也起不来**
- 根因：`CTRL1` 第一次 `0x052CA007`、第二次 `0x052CA00F`（**bit3 SMP 翻转**）
- 源头：`FlexCanDrv_GetDefaultCfg()`（`flexcan_drv.c:389`）漏 `selected3bitSampling`，
  `cfg` 是栈变量 → 第二次拿到残留值
- 修法：取默认值前 `memset(&cfg, 0, sizeof(cfg))`（根治，不是补单个字段）
- **M5 时擦肩而过**：当时发现 STOPPED→STARTED 会弄哑，结论是"别用"就删了 `!k`，
  没查根因。教训：把"这条路不能走"当结论比"找到为什么"危险得多

### 实测行为
```
0x200  100.1 ms 周期，抖动 99~101
byte0 每帧 +1；byte1 恒 0x02；byte2=0xBC；byte3=0x0A；byte4~7=0
注入 01 23 → temp 291；FF FF → 65535；80 00 → 32768
停发 1s → rx cnt=0xEE（替换值）、temp=0（初值），0.9s 触发
!y 停 → 0 帧；再 !y → 10 帧/s
回归：0x123、0x500、10 03 全正常
```

### 新增串口命令
`!v` 信号 dump（tx 应用值 + rx Com 解出值 + grp 状态）、`!y` 分组启停

### 遗留（接真实信号前处理）
- 无 shadow buffer：`Com_SendSignal` 就地改发送缓冲。8 字节/10ms/单字节写在 M4 上原子，
  **加 16/32 位信号要重新评估**
- `COM_USE_MAIN_FAST` 关闭，需要 5ms 以下发送节拍时再开

## M11 状态管理：EcuM 三阶段 + ComM/CanSM 标准链路（18/18 上板通过）

镜像 `text 148208 / data 216 / bss 6720`（相对 M10：text +7.4 KB）。
全回归：M0 26、M2 40、M3 17、M4 23、M5 24、M6 23、M7 16、M8 11、M9 26、M10 22、M11 18

### 结构（自下而上，全部按 AUTOSAR 分层）
```
EcuM（115 行，AS 原样）  三阶段初始化表 + 10 ms BSW 调度表
  ↓ EcuM_AL_EnterRUN（应用侧集成代码）
ComM（688 行，AS 原样）  仲裁：Nm 请求 + CanSM 请求 + Com 分组开关
  ↓                                    ↓
CanSM（703 行，AS 原样）          Nm → CanNm
  ↓
CanIf → Can → 硬件
```
- `app/app/src/EcuM_Cfg.c`：三张初始化表（Zero/One/Two）+ 主函数表
- `app/app/src/ecum_callout.c`：全部 `EcuM_AL_*`（集成决策）
- 新增命令：`!u`（RUN→POST_RUN）/ `!U`（POST_RUN→RUN）/ `!q`（模式查询）
- `!a`/`!R` 改走 `ComM_RequestComMode`；`!A` 改走 `ComM_Nm_NetworkStartIndication`

### 两个致命坑（都是"整机静默"级，靠调试器才定位）

**① 厂商 FlexCAN 驱动的所有硬件等待都没有超时出口**
- `FlexCanDrv_WaitExpired()`（`flexcan_drv.c:238`）依赖 `obj->waitExpired`，
  而 `FlexCanDrv_Init()` 明确置 0，**全仓无赋值** → 每个 `while(握手位)` 都是死循环
- 症状：接上 CanSM 后启动第一拍卡死，**串口不再输出、心跳停止**
- 调试器读到 PC 在 `FlexCanDrv_EnableCanOperationClk`（PCC 解锁等待）
- 修：AC 层实现 `CanAc_WaitExpired()` + 每通道独立预算（20 万次），
  每次调驱动前 `CanAc_WaitBegin()` 重置（`waitFailed` 是粘滞的）

**② 本平台 FlexCAN 不能做低功耗往返 —— 而 `CAN_CS_SLEEP` 正是这么干的**
- CanSM 进 NOCOM 四步：STOPPED → **SLEEP（写 MDIS=1）** → TRCV NORMAL → STANDBY
- 写下去就再也回不来。实测（CAN0=0x40038000，注意 **0x4003C000 是 CAN1**）：
  - MCR 恒 `0xD890000F`（MDIS=1/LPMACK=1/NOTRDY=1）
  - 调试器 `w4` 清 MDIS → **读回不变**
  - PCC CK_EN0/CK_EN1 两位都是 1、SW_RST0=0、LOCK=0（时钟开着、没复位、没加锁）
  - CAN1 正常（只 Configure 过一次、没睡过）
- 滚雪球：STOPPED 请求 → 断电模块进不了 freeze → FRZACK 永不置位 →
  CanSM 卡在 PRE_NOCOM 重试 → 永远到不了 FULLCOM → 通道一次都起不来
- 三处修正：
  1. `CanAc_SetSleepMode` 不再写 MDIS（与 STOPPED 一样只 freeze+halt）
  2. `CanAc_DeInit` 在 `LPMACK=1` 时**直接返回 E_OK**（复位后 MDIS 本来就是 1，
     此时模块必然不通信，正好满足 STOPPED 语义；不这样处理 CanSM 第一步就死锁）
  3. 平台层 `CanAc_EnableClock()` 显式开 PCC 两个时钟位，且在**任何**驱动调用之前
- 另：`Configure` 收敛成**每通道只做一次**（`s_configured`），
  之后 STARTED 只 `FlexCanDrv_Start`（清 freeze/halt），O(1) 无低功耗往返；
  顺带让 M10 的 SMP 位翻转问题再也不会被触发

**③ as-master 的 ComM 也缺实现**
- `ComM_EcuM_WakeUpIndication()` 在 `ComM.h:105` 只有声明，全仓无定义（链接期才报错）
- `!A` 改调同链路后半段 `ComM_Nm_NetworkStartIndication()`（`ComM.c:612` 置同一个 flag）
- M12 接唤醒中断时应补一行转调，而不是在应用层继续调 Nm 侧入口

### 语义变化（导致 M9/M10 脚本要改）
- **`!R` 现在是真的释放通信**：ComM→NO_COM→CanSM 停控制器，总线无帧、诊断不通
  → m9 在断言"心跳/诊断仍在"之前先 `!a` 重新请求
- m10 开头先 `!a` 并等首帧出现，不再假设上一条验收留下的状态
- m9 的 CBV 断言从"每帧都置请求位"改成"至少一帧"（ComM 多一拍仲裁，
  捕获窗口尾部可能越过 800 ms 混进 NormalOperation 的帧）

### 实测行为
```
启动        [ecum] RUN，nvm boot #N，无 PCC/Configure 超时
!q          mode=2 (RUN)
!m          comm=FULL_COM_NETWORK_REQUESTED(2) cannm=NORMAL_OPERATION(4)
```

`m11_check.py` 的"控制器可逆"验的是 **bus-off 恢复所用路径**，不是"真 bus-off 后自愈"。

## M12 睡眠/唤醒框架（15/15 上板通过）

镜像 `text 150636 / data 216 / bss 6720`（相对 M11：text +2.4 KB）。
全回归：M0 26、M2 40、M3 17、M4 23、M5 24、M6 23、M7 16、M8 11、M9 26、M10 22、
M11 18、M12 15 —— 共 **261 项全过**。

### 交付
1. **平台层**（`platform_cvm0146.c`）：
   - `Platform_GetWakeupSource()` / `GetWakeupSourceName()` / `ClearWakeupFlags()`
     （封装 `PowerDrv_*`，`-1` 归一成 `PLATFORM_WAKEUP_NONE=0xFF`）
   - `Platform_EnterStopMode()` = `PowerDrv_SetPowerMode(STOP)`（实现是清 SLEEPDEEP + WFI）
   - `Platform_StopTick()` / `StartTick()` / `SetTickPeriodMs(ms)`
2. **ComM 补缺口**：`ComM_EcuM_WakeUpIndication()` 只有声明没有实现（as-master 第二个缺口），
   在 `ComM.c` 加一行转调 `ComM_Nm_NetworkStartIndication`（走同一个 flag）
3. **EcuM 集成层**（`ecum_callout.c`）：
   `EcuM_EnableWakeupSources` / `EcuM_CheckWakeup`（只信硬件标志，不信传入位图）/
   `EcuM_EndCheckWakeup`；`EcuM_AL_EnterSLEEP` 只记录+打日志（不 WFI）
4. **启动横幅**加 `wake : NONE (255)  [cold boot]`
5. **`!z`**：手动睡一次，100 ms 兜底，报告唤醒源

### 关键判断：没做真低功耗，是刻意的
硬件条件不具备：
- 收发器 WAKE 引脚**没接**（`Can_Cfg` 只有 STB）
- CAN0 RX（PTE4）端口唤醒**没配**（要睡前从 ALT5 切 GPIO 边沿中断）
- SysTick 是唯一兜底，停了就有睡死风险（只能断电恢复）

所以 `!z` 走 Cortex-M **Sleep**（外设时钟没关，电流不降），价值是验证：
```
!z → tick +1 (约 100 ms), 唤醒源=NONE(255)
   → CheckWakeup req=0x0100 hw=NONE
```
`tick +1` 是关键证据：空转的话会前进上百 tick，只 +1 说明真停在 WFI。
**"能睡" ≠ "省电"，必须分开说。**

### 设计取舍：为什么 EnterSLEEP 不直接 WFI
进 SLEEP 时 POST_RUN 只是"发起"撤通信，Nm 还要 ReadySleep(2s) + PrepareBusSleep(2s)，
CanSM 才停控制器。立刻睡会截断报文，且 CAN 模块低功耗态不可逆（M11 教训）。
所以 WFI 由应用在确认总线已静之后主动调（`!z`）。

① PTE4 端口唤醒 → ② 停 SysTick + LPTMR 兜底 → ③ Standby → ④ 电流实测

## M13：A/B 分区 UDS bootloader（2026-11-11 下午）

低功耗按用户要求往后放，这一轮做 bootloader，明确是 **A/B 分区**。

### 分区（`boot_flash_map.h` 唯一权威）
```
0x00000000  Boot        64 KB   （实际 54 KB）
0x00010000  Slot A     448 KB   尾部 4 KB = meta（主备各 1 扇区）
0x00080000  Slot B     448 KB   同上
0x000F0000  预留        64 KB
```
单槽可用镜像 444 KB，当前镜像 155.8 KB。

### 用户拍板的两个决策
1. **boot 只做启动管理**（选槽/校验/跳转/回滚），**不带 UDS 刷写** —— 刷写在 app 里做
2. **分区 64/448/448/64**

### 核心机制（照 as-master `bl_ab.c` / `bl_meta.c`）
- **活动槽 = meta.rollingCounter 大者**，无独立标志位（单次写，天然原子）
- meta 主备各一份，**先备后主**写入
- 状态机 EMPTY → TESTING → CONFIRMED；连续 3 次启动失败 → INVALID（自动回滚）
- 升级只写**非活动槽** → 正在跑的那份永不被动 → 不砖

### 必须双镜像
Cortex-M4 无 MMU，绝对地址链接时定死。AppB 刷进 A 槽必跳飞。
`--app=App`（0x10000）/ `--app=AppB`（0x80000）两个 Application 子类，
只差 LD 与 `APP_SLOT_INDEX`。

### boot 体积
`Mcu_Init()` 拉 20+ 驱动 → 56 KB（64 KB 只剩 8 KB）。
加 `Platform_McuInitMinimal()` 只初始化 clock/flash/power/reset/**pins**/uart → **54 KB**。
（pins 不能省，见坑②）

### 实测（双向都验过）
```
slot A : CONFIRMED rc=9  size=159560 crc=0F2F97AA
slot B : CONFIRMED rc=10 size=159564 crc=F7513B8F
[boot] active slot : B → jump to slot B base=0x080000
[app]  slot : B (link 0x00080000)
```
刷写 6.8 KB/s，155.8 KB 用 23 秒，擦除 0.5 秒（每周期 1 扇区 + 0x78 pending）。

### 七个坑（按发现顺序）
| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| ① | `missing binary operator before "("` | `#if (sizeof(X) % 8)`，预处理阶段 sizeof 未求值 | 改 `_Static_assert` |
| ② | boot 上电即 HardFault，`BFAR=0x44` | 精简 Mcu_Init 漏 `PinsDrv_Init`，Uart2 配引脚时端口基址 NULL | 补 5 个 PinsDrv_Init |
| ③ | boot 报 CRC 失败但打印里 CRC 一致 | `CheckImage` 要求 `imageSize%8==0`，实际 154804%8=4 | 只要 4 字节对齐 |
| ④ | 刷到第 18 块（offset 2040）必挂 0x72 | `FlashDrv_Read1sSection` **拒绝跨扇区**，判空按 1 KB 切段跨了 2 KB 边界 | 切段同时按扇区边界夹 |
| ⑤ | 多帧请求发完无响应 | `isotp_lite._send_long` 忽略 FC 的 BlockSize（板子 BS=8），一次推 17 个 CF | 按 BS 分段等 FC + STmin 延时 |
| ⑥ | 校验成功但工具报 MISMATCH | 响应 `71 01 FF 01 <status>`，状态在 r[4]，工具读 r[3] | 改 r[4] |
| ⑦ | J-Link 重烧后"能跑一次、一复位就 HALT" | meta 记着旧 CRC → boot 不跳 → 能修 meta 的 app 没机会跑（死锁） | `BootMeta_DemoteToTesting()` 降级 TESTING 仍跳一次 |
