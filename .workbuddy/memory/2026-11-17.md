## App → Boot 刷写交接（10 02）

- **机制**：`meta.reserved[0]` 一次性标志（0xFF=无请求=擦除态，0x01=请求）。App 收到 `10 02` → `Dcm_SessionChangeIndication` → `BootApp_RequestFlashMode()` 只置标志 → 150 ms 后主循环写 meta + `Platform_Reset()`。Boot 上电读到先清再进 UDS。
- **为什么不在回调里直接写**：`Dcm_Dsp.c:382` 的 indication 在正响应组包**之前**，此刻复位诊断仪收不到 `50 02`。
- **为什么用 meta 而不是 NvM**：同 CRC 保护、不依赖存储栈、无 Job 时序；擦除态 0xFF 天然兼容旧 meta。
- **安全阀（必须有）**：`Boot_UdsLoop(idleTimeoutMs)`；App 请求 = 30 s 空闲超时回退，无镜像/回滚/调试 = 不进超时；进非默认会话后 `engaged=1` 永不超时（否则刷到一半被踢）。
- **实测三条响应**：交接前 `59 02 8F C0 01 00 8F`（App）→ `10 02` 后 3.5s `7F 19 11`（boot）→ 36s 后 `59 02…`（自动回退）。
- **工具侧**：`uds_flash.py` 会话从 0x03 改 0x02；且要发**两次**（复位后 Dcm 回 DEFAULT，boot 的 0x27/31/34 要求编程会话）。
- App 会话表加 `DCM_PROGRAMMING_SESSION`（原来只有 DEFAULT+EXTENDED，10 02 会回 NRC 0x12）。
- 尺寸：App 240,516→241,084（+568），Boot 51,448→51,896（+448）。
- 回归：m3 18/18、a9 18/18、m23 24/24、Host 2/2；完整刷写 242,232 B 一次通过（40+ s > 30 s 超时，证明 engaged 正确）。

## 02.8 SCons 自动生成集成（提交 d5754d3）

- **没按原设计做**：原计划把 `RegisterConfig` 的源从 `CanIf_Cfg.c` 换成 `CanIf.json`。走不通，三条实测理由：① 生成链是五步有序整体（生成→注入→拷入→断言→对账），`RegisterConfig` 按库触发，表达不了顺序；② `Can_Cfg.c`/`CanIf_Cfg.c`/`PduR_Cfg.c` 是手写文件 + `@generated` 区块，换 GEN 输出会丢人工设计说明；③ `Com_Cfg.c` 是"生成后拷入入库"，改编译单元收益为零。
- **改成构建前门禁**：`tools/gen_gate.py` 算输入指纹（4 JSON + 2 DBC + `generator/**/*.py` + 3 注入脚本 + `config.py`）与产物指纹（7 个入库文件）。未变 skip（端到端 0.5 s / 判定本身 36 ms），变了跑五步（7.2 s）。
- 门禁挂在 `Building()` 开头（任何库 `config()` 之前）；`--generate` 必须在 `SConstruct` 里 `SConscript()` **之前**短路 —— 不带 `--app` 时 `BUILD_DIR` 没有 app 子层，variant_dir 撞车会抛 `app App already registered`。
- 缺 DBC 三态：无状态 → `degrade`（用入库产物，新克隆正常路径）；输入变了 → `blocked` rc=2；产物漂移 → 告警继续。`scons -c/-n/-h` 不触发生成。
- **顺带挖出两个真缺陷**：① `CalcHash()` 缓存键漏了生成器源码 → 改生成器、JSON 没动时 `Generate()` 判"没变化"直接返回旧结果，**改了不生效且无提示**；`a4` 的 C1（幂等）抓不到，因为它证的是"稳定地一致"不是"稳定地更新"。探针实测：给 `Com.py` 插一行注释输出，连跑两遍 `Com_Cfg.c` 一字节未变。② `Com_Cfg.c` 工作区 CRLF / 仓库 LF（527384 vs 510550 B，差值=行数），`text eol=lf` 把差异吃掉，所以产物比对必须 LF 归一。
- 并发：`.genlock`（`O_EXCL`，600 s 残留自动清，拿到锁后**再判一次**指纹）+ `.gendb.pkl` 原子落盘（带 pid 的 tmp + `os.replace`）。`.sconsign.dblite` 仍共享，记为已知边界：不要在同一工作区并发跑两个 scons。
- 证据：`gen_gate_check` 15/15；探针实验 `[GEN] → 只重编 1 个 TU → 241084/1712/15040 不变`，撤探针 git diff 为空；三镜像 App/AppB 241,084、Boot 51,896 与基线一致；看板 Node DOM stub 11/11（**stub 里 `location.hash` 必须带 `#`**，脚本 `slice(1)` 靠它）。
- `a3_isolation_check` 需 Kvaser + 目标板，当前板上是改动前镜像（8/10，0x124 那条失败），未纳入本次判据。
- **写作教训**：`git` 的 `text eol=lf` 会让"字节级差异"隐身；`json.dumps` 重排整个 `roadmap.json` 会造出 2345 行假 diff，必须按原 `indent=1` 回写。

## 22.3 启动判定：先建矩阵与用例，证伪"降级后回滚"（提交 6bf9be6）

- **能测的前提**：`BootMeta.c` 只依赖 3 个 `Platform_Flash*`，所以 Host 上能真编译它。新增 `app/platform/host/test/test_boot_meta.c` + `include/boot_sim/platform_cvm0146.h`（只替换 Flash，逻辑用板上同一份），`host_build.py` 加 `STANDALONE_TESTS` 与 per-test include 顺序。
- **证伪**：`BootMeta_DemoteToTesting()` 把 `bootAttempts` 清零，而 `main.c:707-721` 每次上电都走它 → 计数恒为 1，永不 INVALID、永不回滚。B5 对照组（镜像好的 TESTING）第 4 次就判 INVALID，证明机制本身没事，是降级分支绕过了它。
- 另两个洞：D2（陈旧 meta 与真损坏不可区分，代码注释承认是有意为之）、D3（`Boot_LooksLikeImage` 只看 SP/PC 不看 CRC，是第二个"未验证镜像"入口）。
- **必须改的唯一固件代码**：`CheckImage` 的 CRC 原先是 `(const uint8_t*)base` 裸指针，与同函数里向量表的 `Platform_FlashRead()` 是两条取数路径，且 Host 上 0x20000 是野地址（`VirtualAlloc` 也失败）→ 整段没法测。改成 64 B 分段经平台层 + AUTOSAR 分段 CRC 累算，**等价性由 B2 证明**（测试端一次性算 vs 固件端分段算）。Boot 51,896→51,968(+72 B)，App 不变（`--gc-sections` 回收）。
- **关键排查**：UDS 造不出"meta 有效+镜像坏"——`0x31/0x34` 只接受槽基址且拒绝活动槽，`0x37` 的 CRC 从 Flash 回读算，meta 永远自洽。所以上板用例 H1~H3 必须靠 debug 钩子或 J-Link（决策 D-BOOTFAULT）。**计划里的测试手段要先验证可达性，否则脚本写完跑不通。**
- 看板：M22 任务 1/3 标 PARTIAL，证据里明确写"判据未满足、已证伪"，不冒充 PASS。
- **看板校验的一个假通过**：DOM stub 里断言 `current` 含"复位恢复"，改文案后仍 PASS —— 因为该串在页面别处也出现。改成断言新文案里的独特串（"D1 已证伪"）才有效。**断言要挑唯一标识，别挑可能复用的短语。**

## 22.3 修 D1/D2/D3 + 02.8 依赖边上图（提交 1579c39、36b753a）

- **D1 修法**只改一行：`DemoteToTesting` 里删掉 `meta.bootAttempts = 0`。注释要写清为什么——清零看起来"重新计数"很合理，但 boot 每次上电只要 CRC 不符就再调一次，计数永远回到 1。

- **`bootfault` 命令**（仅开发构建）：`meta-crc` / `meta-blank`，只改 meta 不动镜像——最坏是判定走另一分支，不会变砖。量产镜像 `grep -c bootfault` = 0、App 241,084 与基线逐字节一致。
