## D1 第二步收官：boot UDS 刷写端到端打通（commit 1625a41）

### 根因（主因）
`Platform_InitTick()` 在 boot 里**从来没被调用**（app 是 EcuM 调的）。
`s_ms` 恒为 0 → `Boot_UdsLoop` 的 `(Platform_NowMs()-next) >= DCM_MAIN_FUNCTION_PERIOD`
永不成立 → `CanTp_MainFunction` / `Dcm_MainFunction` 一次都没跑过。
现象：CAN 收发硬件全好（探针发 8 帧 0x7E8 上位机全收、RX 邮箱 CS.CODE 能看到 FULL），
诊断仪发什么都是彻底沉默（连 NRC 都没有）。

**教训**：这类"所有寄存器证据都绿但就是没反应"的问题，要优先怀疑"主循环/调度跑没跑"，
而不是继续查硬件。没有寄存器能反映"状态机推进了几步"，只能靠计数打点。

### 附带发现
1. **本片 FlexCAN 没有 RXIMR 区**：只解码到 `base+0x87F`（CAN0 base = 0x40038800）。
   读 `RXIMR[5]`（base+0x894）立刻精确总线错 `cfsr=0x8200 BFAR=0x40038894`；
   写会被吞掉（所以 `FlexCanDrv_InitCanRAM` 那段清 RXIMR 的循环一直"正常"）。
   `flexcan_reg.h` 里 `RXIMR/HR_TIME_STAMP/ENHRXFIFO/ERFFEL` 只能当偏移占位，**不能读**。
2. **厂商 startup 把所有异常入口弱别名到同一个 `Default_Handler` 死循环**，
   故障现场不留任何信息，表现是"串口突然没声 + 几秒后复位"。
   新增 `app/boot/src/boot_fault.c` 覆盖 HardFault/MemManage/BusFault/UsageFault，
   打印 `CFSR/HFSR/BFAR/MMFAR` + 入栈帧 `PC/LR/xPSR/SP`。
   要点：`naked` + 内联汇编取 MSP/PSP（序言会改 MSP）；`Boot_FaultReport` 必须
   `__attribute__((used))`，否则 `-Os` 下被当成未使用 static 删掉。
3. boot `-Os` 后 51,276 / 130,048 B，余量充足。

### 实测链路
- 10 02 → `06 50 02 00 32 01 F4`；3E 00 → `02 7E 00`
- `uds_flash.py --elf AppB.exe --slot B --verify`：transfer 100%（203,124 B）→
  `31 01 FF01` CRC OK → `11 01`
- 复位后 boot 选 B（rolling counter）、CRC 一致、`jump to slot B entry=0x090400`，
  app 起来 `boot confirmed for slot B`

### bring-up 工具约定
`CanAc_DbgDump`（寄存器快照）/ `CanAc_DbgProbe`（主动发 8 帧 0x7E8 二分 TX/RX）/
`CanAc_DbgStatus`（每秒 `isr/rx/mb/cs/iflag`），统一由 `BOOT_CAN_PROBE` 控制，
**默认 0** —— 探针会往总线插 8 帧假 0x7E8，刷写时必须关。

## M22 + app 关下载收官（commit 44e6efd）

### app 侧关 0x34/0x36/0x37
`Dcm_Cfg.h` 注释掉 `DCM_USE_SERVICE_REQUEST_DOWNLOAD / TRANSFER_DATA /
REQUEST_TRANSFER_EXIT`（这三个宏会改 `Dcm_ConfigType` 字段数量，
`Dcm_Cfg.c` 里是**成对** `#ifdef`，只改一边编不过）。
app 服务集剩 0x10/0x11/0x14/0x19/0x22/0x27/0x2E/0x31，尺寸 202,896 → 200,608 B。

### CAN1 进 Com/PduR 的四个"必须"
1. **`USE_PDUR` 必须定义**：生成器 `Com.py:225` 有 `#ifdef USE_PDUR` 分支，
   不定义则 TX 的 `TxPduId` 退回 `COM_ECUC_PDUID_OFFSET + COM_xxx`（自身下标），
   Com 的周期发送会**打到 PduR 的诊断路径**上。编得过、Kvaser 上没正确报文，极难查。
2. **`Com_MainFunction_Fast` 必须进主循环**：它是 `bTxRetry` 的唯一推进者。
   缺它的现象是"每个 ID 在总线上只出现 1 帧"，而 `com can1` 里 `t` 还在正常回卷
   —— 因为 `t` 是 `Com_MainFunction` 推的，两件事互不相干。
3. **ComM 必须挂上所有 IPdu 组**：组按 network 建（CAN1=0 / CANTEST=1）。
   少挂一个 = 那组报文永不发、**无任何报错**，只有总线上"少了几个 ID"。
4. **信号级 `Timeout` 单位是主函数周期数**，JSON 写毫秒必须过
   `COM_CONVERT_MS_TO_MAIN_CYCLES()`。`Com.py` 原来只在 IPdu 级换算了，
   信号级直接写裸数字 → 1000 ms 被当成 1000 拍，实测 2.6 s 才替换。

### shim 模式（每条报文一个函数）
`CanIf_RxPduType` / `CanIf_TxPduType` 只有函数指针、**无 context 字段**，
所以 PduR 的 `pathId` 只能靠"每条报文一个 shim 函数"硬编码带进去。
`tools/sync_canif.py` 按 dbc 自动生成 40 个 shim，RX shim 里先调
`App_CanIfRxIndication`（保 `!k` 的 pdu 计数 = M19 判据）再转 PduR。

### PduR 双编号（易错点）
- 发送路径：`SrcPduRef->PduHandleId` = Com 的 IPdu 号（`Com_TxConfirmation` 用它当下标）
- 发送路径：`DestPduRef->PduHandleId` = CanIf 的 PDU 号（`CanIf_Transmit` 用它当下标）
- 接收路径：`DestPduRef->PduHandleId` = Com 的 IPdu 号

### 标记注入的坑
`inject()` 用 `text.find(BEGIN_MARK)` 总找第一个标记，而 body 自身带标记
→ 第二次注入会把 DstPdu 的内容写进 SrcPdu 区（报
`incompatible types ... PduR_DstPdu undeclared`）。必须按下标
`find(BEGIN_MARK, i+1)` 定位第 N 组。
