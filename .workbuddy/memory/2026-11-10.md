### 关键事实（以后别再查）

- **CAN0 有 96 个邮箱**：`mcu.c` 里 `canRamNum=3`，8 字节数据时单邮箱 16 字节，

### 新学到的两条

1. **两层 CAN 过滤，硬件在 CanIf 之前。**
   `individualMask` 不匹配 → 帧不进 CPU、中断都不置 → CanIf 的软件掩码再对也不执行。
   要"一条过滤项匹配一组报文"，必须两层同时放行，且**硬件掩码要比软件宽**
   （否则软件过滤永远测不到）。
   硬件：`canid=0x18FF0000, mask=0x1FFF0000`；软件：`canid=0x18FF0100, mask=0x1FFFFF00`。
   `individualMask` 语义：1=必须匹配，0=不关心。

2. **CanIf 表里的 `canid` 必须满足 `canid & mask == canid`。**
   否则等式永不成立，症状只是"这条报文收不到"，不报任何错。

### 串口命令协议（M2 控制面验证用）

`!o` 离线 / `!n` 在线 / `!s` 停控制器 / `!g` 启动 / `!t` 收发器待机 / `!r` 正常。
用 `!` 前缀是为了不破坏 M0 的"任意字符回显"验收项。

### `txok` 的一个坑

`txok` 只在**总线上有另一个节点 ACK** 时才增长。只插 J-Link、不接 Kvaser 时，
控制器 ACK 错误无限重发，txok 恒 0 —— 正常现象，不是固件问题。

## M3 落地：PduR + CanTp + Dcm（17/17 上板通过）

镜像 `text 88904 / data 28 / bss 5776`。M2 回归 40/40、M0 回归 26/26。

### 拓扑：一条 ISO-TP 链路要过 4 条 PduR 路径

TP 报文要过**两次** PduR（N-PDU 一次、SDU 一次）。第一次写成 2 条路径是错的，
CanIf 上来直接进 Dcm，方向也反了。

| pathId | 方向 | Src | Dest |
|---|---|---|---|
| 0 | SDU 上行 | CanTp | Dcm |
| 1 | SDU 下行 | Dcm | CanTp |
| 2 | N-PDU 上行 | CanIf | CanTp |
| 3 | N-PDU 确认 | **CanTp** | CanIf |

**path0 必须是 0**（`Dcm_StartOfReception` 拿 RX pathId 当通道索引，有 `id < numOfChls` 校验）。
**path3 的 Src 是 CanTp 不是 CanIf**（`PduR_TxConfirmation` 走 Src.api->TxConfirmation，确认往上游走）。

### 三个真实踩坑（都表现为"板子静默"，很有迷惑性）

1. **`GetSesChgPermissionFnc` 传 NULL → HardFault**
   `Dcm_Dsp.c:373` 不判空。CFSR=`INVSTATE`（跳到地址 0）。症状：banner/printf 正常，
   一发 `10 03` 整块板子静默，像 CAN 收不到。J-Link 读 PC=0x4A4(Default_Handler)、IPSR=3 定位。

2. **`XXX_MainFunction()` 不能扔进自由循环**
   CanTp/Dcm 的定时器是"每调用一次减一 tick"，主循环几万次/秒 → N_Bs 瞬间超时。
   症状：**单帧全通、多帧一律失败**。修法：10 ms 的统一 BSW 调度（`BSW_PERIOD_MS`）。

3. **多帧发送必须开 `CANTP_USE_TX_CONFIRMATION`**
   不开则 CF 推进只能靠 `CanTp_MainFunction_Fast()`（1ms，且绕过 STmin）。
   症状：FF 发出、第一帧 CF 也发出、然后没下文。

### 环境/工具结论

- **`can-isotp` 的 `CanStack` 在这块 Kvaser 上收不到响应帧**（板子确实回了，库 process() 不返回）。
  m3_check.py 改成手写 70 行 ISO-TP（SF/FF/CF/FC），每帧可控，反而更好排查。
- `Dcm.c` 的 `Dcm_Init` 里 `config` 变量只在 SECURITY_ACCESS 分支用，未开时告警 →
  加 `(void)config;`（已标注为本地修改）。
- Dcm/CanIf/PduR 的 SConscript 都做了裁剪（去掉未移植模块的 `$Xxx_Cfg`），消除 CPPPATH 噪音。

### 决策：官方引擎 + AS 外观（用户拍板）
对比过 as-master 的存储栈后放弃它：**MemIf 和 Fls_Ac* 全仓无实现**（只有声明和调用），
NvM 配 `NVM_CRC8` 实际不校验（`NvM.c:232` 注释 "now only support CRC16 and NONE"），
且多一层 Fls 异步作业机 = 多一个"没被 tick 就永远 PENDING"的位置。
官方这套有现成 DFlash 适配（nvm_demo/fee_internal.c），层次少一层。

### 目录布局（Windows 大小写坑）
```
infras/memory/
  vendor/fee, vendor/nvm   厂商原样，升级=整目录覆盖
  NvM/NvM.c                AUTOSAR 外观
  NvM/NvM_Port.h           零厂商类型/零 AUTOSAR 类型的边界
```
**关键**：`NvM.h`(AUTOSAR) 与 `nvm.h`(厂商) 在 Windows 上同名。
只注册 `$MEMORY`(infras/memory) 和 `$MEMORY_VENDOR`(infras/memory/vendor)，
**绝不挂叶子目录**；代码里一律写 `"nvm/nvm.h"` / `"fee/fee.h"` 带斜杠形式。

**更硬的冲突**：两个 `NvM.h`/`nvm_types.h` 都定义 `NVM_REQ_OK` 等 7 个名字
（宏 vs 枚举）。同一 TU 同时 include 必炸：先 AUTOSAR 则枚举定义被宏污染编译不过；
先厂商则宏把后续 `NVM_REQ_OK` 全展开成 0，**不报错但比较永远错**。
这就是 `NvM_Port.h` 存在的唯一理由。

### 四个坑（前两个是"不报错只不工作"型）

1. **`Fee_Cfg.h` 的 `FEE_CFG_CACHE_BYTES` 必须 ≥ 最大块长（8 对齐）**
   厂商 demo 抄 64 字节。但 GC 搬块会用它放**一整块**数据
   （`fee.c:776` read(...,obj->buff,blocksize) / `:799` write(...)）。
   DTC 块 ALIGN8(65)=72 → 越界 8 字节 → 正好冲掉紧邻的 `NvM_Initialized`
   （`Fee_Cache` 0x200009CC+64 = 0x20000A0C = `NvM_Initialized`）。
   症状：前 210 次写全正常，第一次 GC 后 `NvM_GetStatus()` 恒返回 `MEMIF_UNINIT`，
   全存储哑掉。已改成 `ALIGN8BYTE(FEE_CFG_BLK_DTC_BYTES)` + 逐块 `#if` 校验。

2. **`Fee_Runtime.job` 不能指向 `Fee_SysJob`**
   `Fee_GetUserJob()` 会把用户作业整个 `*config = *userJob` 拷进 `runtime->job`。
   指向 SysJob 就等于把 READ 操作码写进系统作业槽 →
   `Fee_GetSysJob()` 从此永远为真，且 op≠GC 时 IDLE 分支什么都不做，
   **用户作业永远取不到**。三个"正常值"凑成死锁：
   `fee=IDLE / jr=PENDING / block=PENDING`，表现 `NvM_ReadAll()` 永久超时。
   修：`Fee_Cfg.c` 里新增独立的 `Fee_JobCurrent` 作为 `runtime->job`。

3. **`FlashDrv_Read1sSection()` 每次是一条 FTFC 命令**（内部读整 1 KB），
   按 8 字节逐片调用 = 1 条变 128 条。2×12 KB 扫描 → 三千多条命令 → 初始化秒级。
   修：`FeeAc_IsErased()` 按 1 KB 扇区边界切段，一段一条命令。

4. **厂商 `immediate=false` 只写 RAM**（`nvm_statemachine.c:257`），与 AUTOSAR
   `NvM_WriteBlock` 语义冲突。本工程所有块配 `true`，"延迟落盘"上移到
   `NvM.c` 的脏块掩码 + `NvM_SetRamBlockStatus` + `NvM_WriteAll`。

### 三个硬事实（都是实测推翻猜测）

**① 单节点实验室造不出 bus-off —— 协议决定，不是配置问题**
- 断开 Kvaser（无应答）跑 60 s：`TEC` 涨到 **128** 后一动不动
- Kvaser 250k 错速：`TEC=136 REC=7`，仍不 bus-off
- Kvaser 连发 **16939 帧**同 ID 不同数据去撞：`TEC` 只到 1~7
- 原因：ISO 11898-1 §7.1.3 —— **error passive（TEC≥128）下 ACK 错误不再累加 TEC**
- 结论：硬件触发条件用 `!e` 验（`BOFFMSK=1`），记录链路用 `!i` 故障注入验

**② `SetControllerMode(STOPPED→STARTED)` 会弄死控制器 —— 恢复不能靠它**
- 重启前：`ESR1.IDLE=0`、`TEC=128`、Kvaser 2 s 收 8 帧
- 重启后：`ESR1.IDLE=1`、`TEC=0`、**Kvaser 3 s 收 0 帧**、`CanIf_Transmit` 仍返回 E_OK
- `obj->waitFailed = 0` → **不是超时退出**，是二次 Configure 本身有问题
- `CTRL1` 从 `0x052CA087` 变 `0x052CA00F`（`SMP` 位翻转，因 `selected3bitSampling` 未初始化）
- 结论：去掉软件兜底重启。恢复交给硬件 `BOFFREC=0`（**FlexCAN 里 0 才是自动恢复使能**）
- 真要做硬恢复 → `NVIC_SystemReset()`（EcuM 级），留给 M6

**③ SDK 两个"漏初始化"字段**（`FlexCanDrv_GetDefaultCfg` 没设）
- `warningIntEnable` → 决定 `CANx_ORed` 三个源的掩码，栈垃圾会引发中断风暴
  → `CanAc_Init` 里显式补 `false`
- `selected3bitSampling` → 决定 `CTRL1.SMP`，两次 Configure 值不同

### DTC 设计
- 故障码 **U0001 = 0xC00100**（高速 CAN 通信总线），通道号放 `channel` 字段
- 记录 16 字节：`dtcCode(4) occurCount(2) firstBoot(2) lastBoot(2) channel(1) errBits(1) fltConf(1) rsv(1)`
- `dtcCode==0` 表示空槽；槽满**丢弃新事件不覆盖老记录**（老记录是没被污染的样本）
- 落盘策略：只置脏 + `Fault_MainFunction()` 在引擎空闲时合并写 —— 连续 bus-off 只写 1~2 次

### 串口命令（新增）
`!b` dump 故障表、`!B` 清除、`!i` 注入一次 bus-off、`!e` CAN0 寄存器现场、
`!f` 高频发 100 帧（验证 TEC 涨不涨）

## M6 诊断服务：Dem + Dcm 0x19/0x14（23/23 上板通过）

### 关键决策：自写 Dem 子集，不引 as-master 的 2070 行

- **`Dcm_Dsp.c` 里 400 行现成的 0x19/0x14 一行没改就能用** ← 这是选这条路的核心理由
- 升级路径：替换 `Dem.c` 即可，调用方不动

### 分层修正：fault_log 下沉为 Dem
- M5 的 `app/app/src/fault_log.c` 分层错了：infras 的 Dem 不能反向依赖 app
- 整体下沉 `infras/diagnostic/Dem/Dem.c`，接口换成 `Dem_SetEventStatus()`

### Dem 语义：一个 DTC 可挂多个事件
- `Dem_Find()` **只按 dtcCode 匹配，不看通道** —— CAN0/CAN1 bus-off 合并成同一条 U0001
- 按通道分开记会让 0x19 读出两条一模一样的 `C00100`，测试仪误判为两个故障
- `channel` 字段只保留**首次**出故障那一路

### 踩到的坑（脚本侧为主）
1. **预处理不认强转**：`#define DEM_CFG_MAX_DTC ((uint8_t)(...))` 放进 `#if` →
   `missing binary operator before token "("`。宏要参与 `#if` 就不能带 `(type)`
2. **AS 的 `DEM_UDS_STATUS_*` 本身带强转**（`((Dem_UdsStatusByteType)0x01)`），
   所以状态可用掩码那条对账**做不了 `#if`** → 改由 `m6_check.py` 在板上验
3. **`re.search` 的 `^` 只匹配文本开头**（无 MULTILINE 时）→ 横幅永远匹配不到。
   `m5_check` 是逐行 search 所以没事，`m6_check` 搜整段就踩了
4. **0x14 先回 NRC 0x78**（`USE_NVM` 下 `DCM_E_RESPONSE_PENDING`），
   脚本不吞 `7F 14 78` 会让下一条命令读到上一条尾巴 = "命令串位"
5. **`USE_NVM` 宏是被 config 注册自动加的**（`USE_%s`），不是我们手写的 ——
   排查 0x14 为什么走 pending 分支时容易漏掉这点

## M7 写能力：0x27 安全访问 + 0x2E 写 DID（16/16 上板通过）

镜像 `text 129204 / data 188 / bss 6568`（相对 M6：text +1.5 KB）。
全回归：M0 26、M2 40、M3 17、M4 23、M5 24、M6 23、M7 16 —— 全过。

### 0x27：按用户要求"暂时都通过"
- `Dcm_GetSeed()` 返回固定 `11 22 33 44`
- `Dcm_CompareKey()` **恒返回 E_OK**（任何 4 字节都算对），有 `@warning` 标记
- `sessionMask = DCM_EXTENDED_MASK` → 默认会话下发 `27 01` 得 NRC 0x7E（标准行为）
- 解锁后再 `27 01` → `67 01 00 00 00 00`（ISO 14229：已解锁无需发 key，AS 的 Dsl 自带）
- `USE_NVM` 已定义 → `Dcm_Dsl.c` 不定义 `Dcm_NvmSecurityAccess_Ram`，**必须平台侧提供**
- `SecurityNvMBlkId` 填 `0xFF`（不存在的块）：因为 CompareKey 恒通过、AttemptCounter 恒 0、
  `NvM_WriteBlock` 走不到。换真算法前必须建 SECURITY 块

### 三个坑（都实测抓到的）

**① `securityMask` 是"允许的等级集合"，不是"最低要求"**
- 填 `0x01`（以为"1=不限制"）→ **解锁后所有服务全被拒**，回 NRC 0x33
- `Dcm_Dsl.c:135` 是按位与命中判断：`securityMask & (1u << currentLevel)`
- 解锁后 currentLevel=1，`0x01 & 0x02 = 0` → 被拒
- 正确值 **`0x03`** = bit0(LOCKED) | bit1(L1)。要真限制就填 `0x02`

**② VIN 有两个数据源，0x2E 一做就露馅**
- `Dcm_Cfg.c` 有 `Dcm_Vin[17] = "CVM0146M3TEST0001"`，NvM 有 VIN 块 `CVM0146M4NVM00001`
- 0x2E 写 RAM 副本掉电就没，0x22 读常量永远读不到新值
- 统一到 NvM VIN 块：0x22 读它、0x2E 写它
- **连带**：M3 的 VIN 断言改成 `CVM0146M4NVM00001`；
  M3 那条"用 0x2E 造 20 字节长请求"的用例改成写 **F187（不可写）**，
  否则每跑一次回归就把 VIN 写成 17 个 X（实际踩到了）

**③ NvM 对同一块的重复写会丢弃，但 `NvM_WriteBlock()` 仍返回 E_OK**
- 连续两次 `2E F1 90`：第一次成功，第二次 `6E F1 90` 正响应但读回还是旧值
- 厂商 `Nvm_Write` 只把指针入队，作业未完成时同块请求被丢
- 修：`Dcm_WriteVin()` 先查 `NvM_GetStatus() != MEMIF_IDLE` → 忙则回 `conditionsNotCorrect`(0x22)
- 脚本侧：`write_vin()` 收到 0x22 重试（最多 8 次）；`read_vin()` 带 3 次重试

### 顺带修的脚本问题
- `isotp_lite.py` 加 `flush_rx()`：连续请求间清残留响应帧，否则"命令串位"
- m7 开头先 `10 01` 强制回默认会话（否则上一轮停在扩展会话会让"默认会话被拒"假失败）
- m7 收尾**固定写回 `VIN_DEFAULT`**（不是"跑之前的值"，否则脏值会累积传递）

### 新增
- `tools/m7_check.py` 16 项
- `DCM_USE_SERVICE_SECURITY_ACCESS` / `DCM_USE_SERVICE_WRITE_DATA_BY_IDENTIFIER`

## M8 多扩展帧接收 + 软件定时器（11/11 上板通过）

镜像 `text 130320 / data 188 / bss 6568`（相对 M7：text +1.1 KB）。
全回归：M0 26、M2 40、M3 17、M4 23、M5 24、M6 23、M7 16、M8 11 —— 全过。

### 核心结论：**"RX mailbox 不支持扩展帧"这个阻塞根本不存在**
之前把这条列为 Foton 49 条 29-bit 报文 / CanNm / Com / J1939Tp 的前置硬阻塞。
逐项实测全部否定：
- `FlexCanDrv_SetMsgId()`（`flexcan_drv.c:164`）对 `isExt` 分支**正确**置 `CS.IDE|CS.SRR`
- `MESSAGE_BUFFER_ID_EXT_ID_MASK = 0x1FFFFFFF`, shift=0 → 完整 29 位
- `canRamNum=3` × 512B ÷ 16 = **96 个邮箱**（CAN0），CAN1 = 64 个
- M2 时就验过一条扩展帧，只是没往"多条并行"推一步
→ **是判断错了，不是芯片不行。** 这类"记在记忆里的结论"必须定期用实验复核。

### 踩的坑：加报文把 CanIf 表序搞乱了
- 加 4 个 J1939 报文时把 `0x18FF0001` 留在原位（排在 `0x18FExxxx` 之前）
- 结果**它自己**收不到了，新加的四条全正常 → 像"老功能被新配置破坏"
- 根因：`CanIf_RxDispatch()`（`CanIf.c:104`）用**二分查找**，乱序会砍掉该搜的那一半
- 两条硬约束：① 全表按 canid 严格升序；② **掩码项必须在所有精确项之后**
- 加 `CanIfCfg_CheckRxOrder()` 初始化自检（只 warn 不阻断）

### 配置变更
- CAN0 邮箱 mb6(掩码 0x1FFFFF00 收 0x18FF01xx) + mb7~mb10(4 个不同 PGN)
- CanIf PDU 5~9：`CANIF_RX_J1939_PGN/A/B/C/D`，`CANIF_RX_PDU_NUM` 5→10
- 强制顺序：0x321 → 0x7E0 → 0x18FEA100 → 0x18FEB100 → 0x18FEC100 → 0x18FEF100
  → 0x18FF0001 → 0x18FF0100(掩码，末尾)

### 软件定时器（CanNm 前置）

- 拆两层：`infras/system/timer/std_timer.c`（逻辑原样，含溢出处理）
  + `app/platform/cvm0146/src/StdTimerAc.c`（`Std_GetTime()` = `Platform_NowMs()*1000`）
- **溢出处理必须保留**：32 位 us，71.6 分钟回绕；AS 用 NO_OVERFLOW/OVERFLOW 两种状态
