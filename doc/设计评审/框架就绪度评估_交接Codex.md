## 1. 这个框架是什么

基于 **CVM0146（Cortex-M4F）** 的车身控制器框架，目标是 Foton IDM 智能电器盒（L1 24V / S1 12V）。
技术路线：复用开源 asar 的 BSW（`infras/`，文件头 `Copyright (C) 2021 Parai Wang`，`ref: AUTOSAR CP 4.4.0`），自建 HAL + 配置层，不引入完整 AUTOSAR 工具链。

| 事实 | 值 |
|---|---|
| 构建 | `cmd //c "build.bat --app=App"`；变体 `Boot` / `App` / `AppB` |
| 工具链 | `C:\soft\gcc\10.3.1` + SCons + Python 3.12 |
| 尺寸（v1 时点） | App `text=233,924 / data=1,712 / bss=12,616` |
| 调度周期 | 单一 10 ms 节拍（`BSW_PERIOD_MS`），无快速任务 |
| 验证 | 28 个上板脚本（Kvaser 抓包 + 串口命令对拍），多数支持 `--port/--channel/--bitrate` |

## 3. v1 错在哪里（逐条修正）

| # | v1 的说法 | 事实 | 证据 | 性质 |
|---|---|---|---|---|
| **R1** | 未提调度重复 | `main.c` 每拍先直调 `CanTp_MainFunction()` + `Dcm_MainFunction()`（`main.c:375-376`），`EcuM_BswService()` 又按 `EcuM_DriverMainList` 跑一遍（含 CanTp/Dcm/NvM/Dem，`EcuM_Cfg.c:170` 附近），拍末再调 `NvM_MainFunction()` + `Dem_MainFunction()`（`main.c:405-408`） | 见左 | **遗漏重大缺陷**：CanTp/Dcm/NvM/Dem 四个模块每拍各执行**两次** |
| **R2** | P4/C12：脚本硬编码端口通道，"质量资产不可移交" | `m10_check.py:107-109`、`m19_check.py:183-188` 均有 `--port/--channel/--bitrate`，`COM2` 只是默认值 | 见左 | **判断错误，撤回** |
| **R3** | C6：缺 0x3E；0x27 是"种子 0" | `Dcm_Cfg.h:53` 已启用 `DCM_USE_SERVICE_TESTER_PRESENT`；`Dcm_Cfg.c:323` 种子是固定**非零** `11 22 33 44`；真实缺口是 `Dcm_CompareKey()` 恒通过 | 见左 | **事实错误，修正** |
| **R4** | P3：默认表会误解锁 `unlock` | 当前只绑 11 个灯 + 1 条手刹，未绑 `CentralLockSw`；`bcm_sig_cfg.c` 明写动作信号不能塞开关枚举 | 见左 | **把扩展风险写成当前错误** |
| **R5** | 百分比（85/70/55/5…）+ "三个修改点降 10%" | 无计分模型，不可复现，且把"业务未开发"混进"框架就绪度" | — | **撤回，改四态** |

### 3.1 R1 的实际影响（比"重复调用"更严重）

`CanTp`/`Dcm` 的定时器是"每次 MainFunction 递减一次"，配置里的 N_Bs/N_Cr/S3 按 `*_MAIN_FUNCTION_PERIOD` 折算成 tick 数（`main.c:365-372` 的注释自己写了这件事）。每拍跑两次 = **时间基准走两倍**：

| 配置项 | 标称值 | 实际生效 |
|---|---|---|
| S3（诊断会话保持） | 5 s | 约 2.5 s |
| N_Bs（多帧流控超时） | 1 s | 约 0.5 s |
| N_Cr（连续帧超时） | 1 s | 约 0.5 s |

**这解释了为什么它必须排在业务扩展之前**：一旦出现"多帧偶发失败"或"诊断会话莫名掉线"，排查会从协议配置一路查到硬件，很难想到是调度重复。M3/M13 的刷写验证是在这个前提下通过的——不代表配置值正确。

## 6. 验收门槛（下一轮的工作定义）

按既定路线四条线：**AS 基座 / App（裸机或 FreeRTOS）/ Boot（裸机）/ 无以太网**。
每条门槛必须是**可执行判据**，不是"做完了"。

| ID | 门槛 | 判据 / 验证方法 | 通过标准 | 当前 |
|---|---|---|---|---|
| **A1** | 调度唯一性 | 静态：每个 `*_MainFunction` 在 `main.c` 与 `EcuM_Cfg.c` 中只出现在一处；运行期：给每个主函数加调用计数，跑 1 s 对比 | 每拍每模块调用次数恒为 1；S3 实测 = 配置值 | ✗ |
| **A2** | 信号有效性 | 单接口返回四态（NEVER_RECEIVED / VALID / INVALID / TIMEOUT），用 Kvaser 分别构造：不发帧 / 正常帧 / 无效值 / 停发 | 四态各自可复现，且业务层不接触 Com 类型 | ✗（方案未定） |
| **A3** | 测试隔离 | 一个构建开关产出"发布件"；`nm App.exe \| grep CanTest` 为空；总线上无 0x123/0x124 | 发布件零调试帧、零调试符号 | ✗ |
| **A4** | 生成一致性 | 三个生成脚本连跑两遍 `git status` 无 diff；每个生成区块有 `@generated` 标记；手写段落有反向断言 | 幂等 + 边界可机器判定 | ◐ |
| **A5** | Boot 异常恢复 | 覆盖矩阵：升级中断电@擦除中/写入中/校验前、镜像校验失败、rollback、双槽边界 | 每格有验证记录，且设备可恢复到已知可用态 | ◐ |
| **A6** | 资源预算 | text/data/bss/栈水位/最坏中断延迟实测 | 有数值 + 明确余量阈值（如 RAM ≤70%、栈 ≤60%） | ✗ |
| **A7** | 诊断最小集 | 0x27 真实算法（种子随机源、失败计数、延迟）、DTC/DID 清单落地 | 安全访问不可被任意 Key 通过 | ✗ |
| **A8** | 存储掉电安全 | 断电注入：写块中途断电 N 次，检查 CRC/冗余与恢复 | 无"写坏不可读"路径 | ✗ |
| **A9** | 业务骨架 | 至少 1 条端到端业务（输入信号 → 决策 → 输出驱动 → 诊断上报） | 走通即证明形状，再铺剩余 | ✗ |
| **A10** | 无以太网约束 | 链接不引入 lwIP/SoAd 等模块 | map 文件无相关符号 | ✅（当前天然满足） |

**建议的修复顺序**：A1 → A3 → A2 → A4 → A5 → A6 → A7 → A8 → A9。理由：A1 不修，后面所有时间相关测试结论都不可信；A3 不修，A6 的尺寸数据会被调试代码污染。
