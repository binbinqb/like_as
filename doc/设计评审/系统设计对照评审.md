### 1.1 一个必须先说清的命名陷阱

**DBC 文件名与实车 CAN 通道号不是一一对应的**：

| DBC 文件 | 内容 | 实车通道 | 速率 | 依据 |
|---|---|---|---|---|
| `can0.dbc` | 组合开关 2 条（SSM_LightCom / SSM_OWW） | **CAN3** | **500 kbps** | 矩阵 `组合开关_CAN3` sheet + 框图 p2 |
| `can1.dbc` | 整车网 40 条 | **CAN1** | **250 kbps** | 矩阵 `IDM_CAN1` sheet + `1.General` 的 `ECU Location: CAN1` |

框图 p2 明写：

```
CAN1  非CANFD，预留终端电阻   数据传输速率：250kbps   接整车通讯CAN网络（含ESCL控制器）
CAN2  非CANFD，预留终端电阻   数据传输速率：250kbps   设计预留，量产状态不贴片
CAN3  非CANFD，贴终端电阻     数据传输速率：500kbps
```

> 这三个速率是**按 PDF 文字坐标**核对过的，不是靠阅读顺序推断。框图 p2 页面上
> 三组文字各占一块，`数据传输速率：xxxkbps` 紧贴其上方的 `CANn_H`/`CANn_L`：
>
> | 文字 | x | y |
> |---|---|---|
> | `数据传输速率：250kbps` | 319 | 1483 |
> | `CAN1_H` / `CAN1` / `CAN1_L` | 322 | 1492 / 1506 / 1520 |
> | `数据传输速率：250kbps` | 319 | 1553 |
> | `CAN2_H` / `CAN2` / `CAN2_L` | 324 | 1563 / 1576 / 1590 |
> | `数据传输速率：500kbps` | 326 | 1621 |
> | `CAN3_H` / `CAN3` / `CAN3_L` | 324 | 1632 / 1646 / 1660 |
>
> 按阅读顺序抓文本会把 `500kbps` 错配给别的信号（它前后都是无关的 IO 名称），
> 这类错误一旦进了代码就是"总线根本不通"，且没有任何报错。

**现有代码是两路都 500 kbps**（`CAN_CFG_BAUDRATE = 500000u`）——
装在实车上 CAN1 直接通信失败，且不报配置错误。

## 2 架构级冲突（必须决策后才能动代码）

### A1 刷写服务归属：bootloader 还是 app

`2.Service` 表的原文（`√` = 支持，`×` = 不支持）：

| SID | Application/Default | Application/Extended | Bootloader/Default | Bootloader/Extended | Bootloader/Programming |
|---|---|---|---|---|---|
| 0x34 请求下载 | × | × | × | × | **√3** |
| 0x36 数据传输 | × | × | × | × | **√3** |
| 0x37 请求退出传输 | × | × | × | × | **√3** |
| 0x31 例程控制 0x01 | × | √1 | × | **√0** | **√3** |
| 0x27 安全访问 0x01/0x02 | × | **√0** | × | × | × |
| 0x27 安全访问 0x03/0x04 | × | × | × | × | **√0** |
| 0x2E 写入数据 | × | √1 | × | × | **√3** |

（`√0` 不需安全访问，`√1` 需级别 1，`√3` 需级别 3）

**M13 的现状与此相反**：app 里实现了 0x34/0x36/0x37 并写非活动槽，boot 只做
选槽/跳转。当时的决策是"boot 只做启动管理"，理由是省 30 KB 代码。

**按规范，正确流程是**：

```
app  (扩展会话)  31 01 F002       检查预编程条件（不需安全访问）
app  (扩展会话)  10 02            进编程会话 → 应答后跳 boot
boot (编程会话)  27 03 / 27 04    L3 解锁
boot (编程会话)  31 01 FF00       擦除
boot (编程会话)  34 / 36 / 37     下载
boot (编程会话)  31 01 FF01       检查编程依赖性
boot (编程会话)  31 01 F001       检查编程完整性
boot             11 01            复位
```

**注意**：这不否定 A/B —— 框图 p2 设计要求第 1 条明确写
"支持诊断仪故障诊断及远程 OTA 升级（**A/B 双分区**）"。A/B 逻辑保留，
只是把"往哪一个槽写"的动作从 app 挪到 boot。

**代价**：boot 要挂一份精简 Dcm（0x10/0x11/0x27/0x31/0x34/0x36/0x37/0x3E），
估算 +25~30 KB。当前 boot 54 KB / 64 KB，**放不下**，需要重新划分区或把
boot 区扩到 96 KB。

### A2 三路 CAN 的职责与网络管理

框图设计要求第 8 条原文：

> 无AutoSar软件使用要求，**CAN1无网管理（IDM与ESCL之间主从唤醒）**，
> **CAN3按照AutoSar网络管理**（Q-FT R587-2021《福田汽车CAN网络管理规范》）

拆开看是两件事：

| 通道 | 现有代码 | 应改成 |
|---|---|---|
| CAN1（整车网 250k） | CanNm + ComM + 0x500 标准帧 NM | **去掉 CanNm**，唤醒靠 ESCL 主从（硬线 + CAN 收发唤醒） |
| CAN3（组合开关 500k） | 无 | **加 CanNm**，报文格式按 Q-FT R587-2021 |
| CAN2 | 无 | 保持不用（量产不贴片） |

另外矩阵里 NM 报文的真实 ID 是 **`0x18FFA056`（IDM 发）/ `0x18FFA055`（组合开关发）**，
PGN 0xFFA0 —— 不是 11 位标准帧 0x500。

> **缺失资料**：Q-FT R587-2021《福田汽车CAN网络管理规范》不在这批资料里。
> 需要它才能定 NM 的报文内容、定时参数（重复报文时间、NM 超时）。

### A3 诊断 ID 与寻址

`1.General` 原文：

```
ECU Name          : IDM
CAN Baudrate      : 250K
ECU Location      : CAN1
Physical Request  CAN ID : 0x18DA56F9
Functional Request CAN ID : 0x18DBFFF9
Physical Response CAN ID : 0x18DAF956
DTC Length        : 3 bytes
SeedLength        : 4 bytes
```

三处要改：

| 项 | 现有 | 应为 | 影响 |
|---|---|---|---|
| 诊断 ID | `0x7E0` / `0x7E8`（11 位） | `0x18DA56F9` / `0x18DAF956`（29 位） | CAN 邮箱掩码、CanIf 过滤表、CanTp N_SA/N_TA、Dcm PduId |
| 功能寻址 | 无 | `0x18DBFFF9` | CanIf 需要多一个 RX 表项 |
| 通道 | CAN0 | **CAN1** | 邮箱表整体迁移 |

**一个必须确认的矛盾**：诊断 ID 里的源地址是 **0x56**，但 `can1.dbc` 里 BCM 发的
6 条业务报文源地址是 **0x21**（`0x18FE4021` / `0x18FF0C21` …）。

矩阵里 `IDM_NW` 是 `0x18FFA056`（源地址 0x56），与诊断一致；但 `BCM_LCSF` 等
6 条是 `…21`。两种可能：

1. IDM 用 0x56 作诊断/网络管理地址，用 0x21 作业务报文地址（可能，但少见）
2. `can1.dbc` 里的 "BCM" 节点是**另一个**控制器，IDM 只借用它的报文定义

**这一条不问清楚，CanIf 的源地址过滤就会配错。**

#### 证据：矩阵的 "IDM" 列不是"IDM 发送"

把矩阵里 `IDM` 列标 `T` 的 21 条按源地址拆开，发现有 9 条**不可能**是 IDM 发的：

| 源地址 | 报文 | 实际发送方 |
|---|---|---|
| 0x21 | BCM_LCSF / BCM_Ctrl / BCM_OEL / BCM_OWW / BCM_DoorCtrl / BCM_DM1 | DBC 里 `tx=BCM` |
| **0x34** | **PEPS1 / PEPS2 / PEPS_ESCLM** | PEPS 控制器 |
| **0x33** | **DM1_TPMS / TireCondition** | 胎压模块 |
| **0xEC** | **DW_State**（46 个信号） | 大屏/显示模块 |
| **0x19** | **ECC2** | IVI 车机 |
| 0x56 | IDM_NW / ID1 / ID2 / ID3 | **IDM 自己** |

PEPS（0x34）、胎压（0x33）绝无可能是 IDM 发的报文。所以矩阵 `IDM` 列的真实含义
更可能是**"IDM 作为网关需要转发/路由"**（框图里确实有 "BCAN路由到PCAN" 一行），
而不是"IDM 发送"。

**更强的反证**：矩阵里 `IDM` 列标 **R**（接收）的 24 条中，有 2 条的源地址是 **0x21**：

```
0x18FEF121  CCVS（巡航车速）   sa=0x21
0x1CFEC321  ETC5              sa=0x21
```

一个 ECU 不会"接收"自己发的报文。**所以 IDM 的源地址不是 0x21**，
而 `0x18FFA056 IDM_NW` + `1.General` 的诊断 ID 都指向 **0x56**。

那 0x21 是谁？`can1.dbc` 的 `BU_` 列表里同时有 `BCM` 和 `NODE_21` 两个节点，
而 `BCM_LCSF` 的 `tx=BCM` 但 ID 是 `…21` —— **DBC 内部就自相矛盾**。

**这条推论会改掉 CanIf 的过滤表规模**：

| 口径 | 数量 | 说明 |
|---|---|---|
| 矩阵标 R | **24 条** | IDM 明确要收的 |
| 矩阵标 T 且源地址为 0x21/0x56 | 9 条 | 其中 6 条 SA=0x21 存疑 |
| 矩阵标 T 但源地址是别人（0x34/0x33/0x19/0xEC） | 9 条 | 只能是转发 |
| J1939 TP 协议 | 4 条 | 长报文分段，不是应用报文 |
| 说明性行（无 ID） | 3 条 | 大屏发送 / BCAN路由 / 网络管理 |

**Q1 必须先回答**：按"IDM 发送"配是 9 条 TX；按"IDM 转发"配还要多一套路由表。

## 3 参数级偏差（改配置即可）

全部来自 `1.General` + 诊断规范 §6.3/§6.4/§7.1 + `10.DTC_Status`：

| # | 项 | 现有 | 规范要求 | 出处 |
|---|---|---|---|---|
| B1 | CanTp **BS** | 8 | **0** | `1.General` CP_BlockSize(BS) = 0；规范 §6.3 |
| B2 | CanTp **STmin** | 0 | **10 ms**（应用）/ 0 ms（boot） | `1.General` CP_StMin = 10 ms |
| B3 | CanTp **填充字节** | 0xCC | **0x55** | 规范 §5："未使用的字节应使用0x55进行数据填充" |
| B4 | CanTp **接收缓冲** | **64 字节** | **≥ 1024** | 规范 §9.14.3.5 |
| B5 | N_As / N_Bs / N_Cr | 1000 / 1000 / 1000 ms | **70 / 150 / 150 ms** | 规范 §6.4 |
| B6 | N_WFTmax | 8 | **0**（不允许等待流控帧） | 规范 §6.3 |
| B7 | CAN1 波特率 | 500 kbps | **250 kbps** | 框图 p2 |
| B8 | CAN3 波特率 | — | **500 kbps** | 框图 p2 |

B4 是硬伤：`CANTP_CFG_DATA_SIZE = 64u`。规范要求 ECU 在 0x34 的响应里声明
`MaxNumberOfBlockLength ≥ 1024`，而缓冲只有 64 字节 —— 声明了也收不下。
改缓冲要连带确认 RAM 余量（当前 bss 6.7 KB，扩 1 KB 没问题）。

**N_WFTmax = 0** 意味着收到 FF 后必须**立刻**能给出 FC，不能"稍后再给"。
当前 CanTp 的接收是在主循环里处理的，如果主循环有长任务（比如整片 CRC 计算
6 ms），可能超 N_Bs。这条要在实现时实测。

### 4.1 M13 的一个语义错误

`7.Routine ID` 给出的四个例程：

| RID | 名称 | 谁能用 | 安全 |
|---|---|---|---|
| F001 | CheckProgramIntegrity | Bootloader 3101 | √3 |
| F002 | checkProgrammingPreconditions | **应用和 Bootloader 都可** | √0 |
| FF00 | eraseMemory | Bootloader 3101 | √3 |
| FF01 | **checkProgrammingDependencies**（检查编程依赖性） | Bootloader 3101 | √3 |

M13 里把 `0xFF01` 当"校验镜像 CRC"用了 —— **语义错了**。完整性校验是 F001。
0xFF01 是"检查编程依赖性"（检查各 ECU 软件版本之间的兼容性），是另一个东西。

`FF00` 的擦除请求参数也确认了：`X6 = 0x44 AddressLengthFormatId`，与 M13 的
`31 01 FF00 <addr4> <size4>` 一致，这部分是对的。

### 4.2 0x27 的算法文件缺失

规范 §9.3.4 原文：

> 种子及密钥均为4字节（32位）的数值。具体的安全加密算法由福田汽车与供应商共同
> 制定并由**《XX 诊断安全算法》**文件描述。

这份文件不在这批资料里。在拿到之前，`Dcm_CompareKey()` 只能继续恒通过，
但必须留好接口和失败计数框架（失败 3 次 → 0x36，10 s 内 → 0x37）。

## 6 一个容易漏掉的硬件契约

框图 p2 设计要求第 21 条：

> **标注硬件短路保护的通道：硬件短路保护后关闭输出，没有软件驱动此通道不能再打开。**

配合 DTC 清单可以看到：绝大多数输出通道都标了"硬件短路保护"。这意味着：

- 短路发生后，**软件写多少次都没用**，输出被硬件锁死
- 只能靠断电（或该通道的使能重新上电）恢复
- 所以 DTC 的"故障恢复条件"里写"关闭输出"是**软件动作**，而硬件已经先关了

**软件要做的**：短路 DTC 置位后，**停止对该通道的一切驱动尝试**（不要周期性
重试），否则会在日志里刷满"输出已关闭"，掩盖真正的故障。

这条对 `IoHwAb` / 输出驱动层的设计要求是"带锁存的状态"：一旦某个通道的
硬短路 DTC 置位，该通道进入 `LOCKED_OUT` 状态，直到下次上电。

## 7 建议的推进顺序（自下而上，不跳层）

按你的分层约定，**先把"契约"改对，再做功能**。顺序不能反 —— 契约错了，
上面所有层都要返工。

### 第 0 步：先决策两件事（阻塞后续全部工作）

| 决策 | 选项 | 影响 |
|---|---|---|
| **D1 刷写归属** | ① 按规范改到 boot（boot 扩到 96 KB，重划分区）<br>② 维持现状（app 刷写），在《ECU 诊断调查表》里申请偏离 | 决定 boot 分区大小、boot 代码量 |
| **D2 IDM 源地址** | 0x21（业务）还是 0x56（诊断/网络管理），或两者并存 | 决定 CanIf 过滤表与 CanTp 地址 |

### 第 1 步：通信契约（hal_can → CanIf → CanTp）

1. **CAN 通道重排**：CAN1 = 250k（整车网）、CAN3 = 500k（组合开关）、CAN2 关闭
2. **诊断 ID 改 29 位**：`0x18DA56F9` / `0x18DAF956` / `0x18DBFFF9`
3. **CanTp 参数**：BS=0、STmin=10ms、Padding=0x55、N_As/N_Bs/N_Cr=70/150/150、
   N_WFTmax=0、**缓冲 ≥ 1024**
4. **CanIf 过滤表**：按矩阵重新生成（IDM 只关心 24 条接收报文，不是全部 34 条）

验收：`uds_flash.py` 能连上（改 ID 后），单帧/多帧请求都有正常响应。

### 第 2 步：诊断能力补齐（Dcm → Dem）

1. 0x28 / 0x85 / 0x19(0x0A) —— 小项先做，成本低
2. 110 个 DTC 的 Dem 配置 + 0x19 完整响应
3. 0x2F（19 个 IO DID）—— 依赖第 3 步的 IO 层
4. 0x27 失败计数框架（算法等文件）

验收：`m6_check.py` 扩展，逐项打点。

### 第 3 步：IO 层（这次有真实依据了）

| 子步 | 内容 | 依据 |
|---|---|---|
| 3.1 | 继电器线包输出（约 22 路） | 框图 D1~D39 诊断 + `Xxx_RlyCoil_Ctrl` |
| 3.2 | HSD/LSD 输出 + 开路/短路检测 | DTC 清单里的电流门限（3.325 A / 0.097 A 等） |
| 3.3 | 模拟输入（蒸发温度、风门反馈、PT 传感器） | 框图 AD 标注 |
| 3.4 | **车窗开关 AD 多路复用**（1.2 kΩ 分压 + UP/DOWN） | 框图 p2 "1.2KΩ±1% UP / DOWN / AD" |
| 3.5 | 全桥驱动（风门电机 ×3） | 框图"全桥驱动方案：两个半桥驱动" |

### 第 4 步：业务功能（145 项）

按前缀分批，**先做输入最少的**：

| 批 | 功能组 | 项数 | 为什么这个顺序 |
