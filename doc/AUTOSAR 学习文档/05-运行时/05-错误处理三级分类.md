# 错误处理分类与报告路径

> [!tip] 结论
> 原文件名保留。Development、Runtime、Production 是常用分类，但 R25-11 还涉及 Extended Production Error、Transient Fault 等概念；不能把所有错误当成严重程度从低到高的三个等级。

## 一、分类与报告分别理解

| 类型 | 核心理解 | 典型报告入口 |
|---|---|---|
| Development Error | 开发／集成中的错误，例如非法参数和调用顺序 | `Det_ReportError` |
| Runtime Error | 运行时发生、需按模块规则处理的异常 | `Det_ReportRuntimeError` |
| Production / Extended Production Error | 与现场故障监控、事件存储和诊断相关 | Dem 对应事件接口与配置 |
| Transient Fault | 规范定义的瞬态故障类别 | `Det_ReportTransientFault` 等规定机制 |

具体错误属于哪类、何时检测、是否可裁剪，均由相应模块 SWS 的错误分类和条目决定。不能凭“总线超时”四个字统一判为 Runtime Error。

## 二、DET 不等于终止程序

`Det_ReportError()` 的职责是报告；是否日志、断点、Hook、返回或采取恢复动作，由 DET 实现、集成策略和调用模块规范决定。

文档中“程序流终止”应区分**拒绝当前服务／返回**与**终止 ECU 程序或复位**。非法请求可能需要报告 DET 并返回失败；不能因此推导“开发错误只报告 DET，不允许返回 E_NOT_OK”。应查看该 API 的实际返回规定。

Runtime Error 也不意味着永远只记日志继续执行原操作；可能要中止本次作业、恢复资源或进入降级。Production Error 也不意味着立即确认 DTC 或立即写 Flash。

## 三、DET 与 DEM

DET 有开发错误、运行错误、瞬态故障的报告路径；内部可以按配置和实现记录、通知，不是“绝不存储”。Dem 管理事件状态、去抖、操作周期、DTC、记录及持久化协调。

是否实现 Dem、支持哪些事件和记录由产品要求及标准合规范围决定，不能笼统说“所有 ECU 都因法规必须保留全部 DEM”。

## 四、不要把去抖、确认与老化合并成一个计数器

```text
监控结果 PREFAILED / PREPASSED
          ↓ 配置的去抖或监控内部去抖
事件 FAILED / PASSED
          ↓ 操作周期与确认规则
pending / confirmed 等 DTC 状态
          ↓ 配置的恢复、老化、清除规则
历史记录演进
```

不是每个事件都必须经过多次采样：监控也可以报告已去抖的 FAILED/PASSED。`testFailed` 与 `confirmedDTC` 是不同位，0x19 能否返回某个 DTC 取决于请求子功能、状态掩码等，不必等 confirmed 才可读。

## 五、开发建议

保持参数检查、作业状态返回和故障事件入口职责清晰。示例代码中的 `Adc_ReadChannel`、自定义错误枚举和 `Err_Report` 只能作为自建接口，不能冒充 AUTOSAR 标准 API。

仅 ADC 读取失败不能直接证明传感器开路。应分别考虑采集链路失败、输入电压超范围、可诊断的开路／短路条件，按电路和监控设计上报事件。

“软件本身不会磨损”是说明故障根因的教学表达，不表示实际运行不会因软错误、内存破坏、硬件故障或系统交互出现软件失效。
