# 看门狗与监控

> [!tip] 结论
> WdgM 评估监督实体，WdgIf 抽象看门狗实例，Wdg 驱动在允许的时间内按硬件窗口触发。触发条件参数的单位是毫秒，不是“喂狗次数”。

## 一、三层职责

```text
监督实体／检查点 → WdgM → WdgIf → Wdg → 硬件看门狗
```

WdgIf 的设备参数选择 watchdog 实例，Mode 用于另一个模式设置服务，不能把 `WdgIf_SetTriggerCondition(DeviceIndex, Timeout)` 的第一个参数写成 Mode。

## 二、三种监督

| 类型 | 检查 | 关键配置 |
|---|---|---|
| Alive | 规定参考周期内检查点到达次数 | ExpectedAliveIndications、MinMargin、MaxMargin、ReferenceCycle |
| Deadline | 起止检查点间时间是否满足约束，包括未到达终点的检测 | DeadlineMin / DeadlineMax |
| Logical | 检查点转移是否符合配置程序流 | 内部／外部转移、初始／终止检查点 |

Alive 下限 = `WdgMExpectedAliveIndications - WdgMMinMargin`；上限 = `WdgMExpectedAliveIndications + WdgMMaxMargin`。原文将 Min/Max 用反，已修正。

监督实体可以对应功能、Runnable 或一组执行单元，不必与每个 Task 一一对应。检查点选择应真正代表工作完成，避免空转也不断“打卡”。

## 三、触发条件的时间语义

`Wdg_SetTriggerCondition(uint16 timeout)` 的 timeout 表示允许服务看门狗的时间，单位毫秒。驱动内部维护触发计数／时间状态，在规定的触发时机更新并服务硬件。

例如 timeout=100 表示时间授权约为 100 ms，不能解释为“允许再喂 100 次”。WdgM 停止更新后，剩余授权时间与硬件超时、窗口、调用相位共同决定复位延迟。

## 四、状态与恢复

本地监督状态和全局状态不同。全局状态包含 OK、FAILED、EXPIRED、STOPPED、DEACTIVATED 等规范状态。EXPIRED 到 STOPPED 的过渡、容忍周期、设置触发条件为零以及立即复位行为按配置和 SWS 检查。

不能简化为“任何实体 FAILED 就立即复位”或“EXPIRED 总是当场停止喂狗”。通知实体恢复、记录 Dem、停止触发和立即 MCU 复位分别有其机制与条件。

## 五、监督不等于隔离

WdgM 能发现和促使处理一些执行故障，但不能阻止越界写、建立内存保护或证明 freedom from interference。没有 MPU 时的模块边界和 CRC 只能改善组织与检测，不是受保护分区的替代品。

是否有 ASIL 要求也不能直接推出必须采用哪一组参数；监督机制由系统故障分析、故障反应时间和验证决定。不存在统一“容差 20~30%、失败 3~5 次”的标准推荐值。

## 六、BCM 的最小方案

使用 FreeRTOS 时，可建立静态监督表：必要执行单元、预期周期／计数、关键起止点、故障动作和恢复规则。监督时基和喂狗路径要避免被同一个任务故障同时蒙蔽。

测量最坏负载、中断风暴、总线卡住、Flash 擦写期间的监督行为，再确定参数。正常休眠／唤醒、诊断长操作和升级阶段也需要明确监督模式交接。
