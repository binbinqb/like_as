# OS 与调度

> [!tip] 结论
> AUTOSAR OS 基于 OSEK/VDX，并增加 ScheduleTable、保护、多核等机制。静态配置的是对象和调度参数；运行时仍根据就绪状态、事件、优先级和抢占规则作调度决策。

## 一、Task 与 Runnable 不同

| 对象 | 等待事件 | 终止／链式激活 |
|---|---|---|
| Basic Task | 不能进入 `WaitEvent` 等待态 | 可以使用适用的 `TerminateTask` / `ChainTask` |
| Extended Task | 可以在规定上下文调用 `WaitEvent` | 同样有终止等服务，受调用级别约束 |

Runnable 是 RTE 管理的执行单元，不是 OS Task。Category 1 Runnable 不含等待点；Category 2 可含等待点，需要相应 Extended Task 映射。不能说所有 Runnable 必须运行在 Basic Task。见 [[03-RTE生成与Runnable映射]]。

## 二、调度规则

- 支持全抢占、非抢占及混合调度。非抢占 Task 仍可被允许的中断打断，并有规定的调度点。
- 同一核、相同优先级的 Task 按激活顺序执行；不同核独立调度，不保证全局激活顺序。不能说同优先级顺序未定义。
- Resource 提供优先级天花板机制。嵌套和释放顺序、服务调用限制应按 OS 规则检查，而非简单禁止所有嵌套。
- 配置中的数字优先级与供应商硬件中断编码不是一个概念。

## 三、四个可伸缩类

| 类 | 核心特征 |
|---|---|
| SC1 | 基础功能 |
| SC2 | SC1 加时间保护 |
| SC3 | SC1 加内存保护 |
| SC4 | 时间保护与内存保护均具备 |

**SC3 不等于 SC2 加内存保护；SC4 不等于 SC3 加多核。** 多核支持是另一个维度，规范明确多核 SC1、SC2 也支持 OS-Application。

## 四、Counter、Alarm、ScheduleTable

Counter 提供计数基准；Alarm 到期执行配置动作；ScheduleTable 组织相对表起点的 expiry points，用于协调激活 Task、设置事件等。

ScheduleTable 不等于 LIN 总线调度表。LIN 调度由 LinIf 等通信机制处理，OS 可以提供其执行所需的时基，但不能混为同一个表。

ScheduleTable 的隐式同步要求 Counter 已与同步时间基准关联；显式同步通过规定服务提供同步值。不能简单解释为“有 GPS 就自动对齐”。

## 五、中断与保护

Category 1 不使用一般 OS 服务；Category 2 由 OS 管理，并只允许调用规定的 OS 服务子集。中断处理保持短小，但“10 µs、100 µs”不是 AUTOSAR 通用硬阈值，预算应来自中断率、响应需求和测量。

时间保护监控执行、资源／中断锁定和到达间隔等预算；内存保护需要硬件、OS 与内存布局共同支持。两者不能替代系统层面的时序分析与故障恢复设计。

## 六、与 FreeRTOS 的边界

FreeRTOS 可以静态创建内核对象，也可按配置支持运行时创建和优先级调整。不能将“静态／动态”混同为是否采用实时优先级调度。AUTOSAR OS 和 FreeRTOS 都不因使用某个名字就自动保证截止期满足。

本项目采用 FreeRTOS 时，建立 OS 抽象和明确的调度设计；不声明其已经满足 AUTOSAR OS SWS。

## 七、BCM 的任务设计建议

功能文件按 `lighting.c/.h`、`button.c/.h`、`door_lock.c/.h` 等组织；Task 根据响应时限、阻塞、资源所有权和执行预算划分。一个 Task 可以顺序执行多个功能函数。

可先评估 IO 服务、通信、应用、诊断、存储这些执行域，短小且无阻塞的执行域可以合并。不要固定套用“通信永远最高”“NvM 永远 100 ms”。

| 需要确定 | 如何验证 |
|---|---|
| 周期、优先级、截止期 | 分析 WCET、干扰和阻塞，台架测量 |
| MUX 刷新周期 | 计入选通、I²C 完成、建立时间、ADC 转换 |
| 栈大小 | 最坏调用链与中断嵌套分析，辅以高水位测量 |
| 任务间数据 | 状态用一致快照，命令用有界队列，约定溢出策略 |
| 任务存活 | 检查点与独立时基监督，防止单纯后台喂狗掩盖卡死 |
