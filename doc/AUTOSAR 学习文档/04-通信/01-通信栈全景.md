# 通信栈全景

> [!tip] 结论
> 区分信号处理、I-PDU 路由、传输协议与 L-SDU 路由。短 UDS 消息仍走 CanTp，只是编码为 Single Frame；它不会因为“短”就绕过 TP 直接交给 Dcm。

## 一、R25-11 两条常见发送链路

```text
信号：SWC → RTE → Com → PduR → LSduR → CanIf → Can
诊断：Dcm → PduR → CanTp → LSduR → CanIf → Can
```

这是未展开 SecOC、IpduM 等可选模块的简图；接收与确认分别沿对应接口返回。**PduR 在 CanTp 的上侧，LSduR 在 CanTp 与 CanIf 之间。**

历史常见链路：`Dcm → PduR → CanTp → CanIf → Can`。不要写成 `CanTp → PduR → CanIf`。

## 二、模块职责

| 模块 | 处理对象 | 主要职责 |
|---|---|---|
| Com | 信号、信号组、I-PDU | 打包、发送触发、失效、监控、网关 |
| PduR | I-PDU / TP-SDU | 上下层接口适配、静态路由、所需缓冲 |
| CanTp | N-SDU / N-PDU | ISO-TP 分段、重组、流控和时序 |
| LSduR | 下层接口服务数据 | 通信服务与通信硬件抽象之间的路由 |
| CanIf | CAN PDU、控制器与收发器抽象 | PDU 映射、过滤、缓冲及规定通知 |
| Can | CAN 控制器资源 | 硬件操作、中断／轮询处理 |
| CanSM / ComM / CanNm | 状态与通信需求 | 总线状态、需求仲裁、网络管理，职责不同 |

CanNm 等模块的下层连接也应按 LSduR 和对应规范核对，不是任意一个报文都要同时送 Com、Dcm、NM。

## 三、不要用 8 字节划分“信号路径／TP 路径”

经典 CAN、CAN FD 的帧载荷容量不同，ISO-TP 还有 PCI 和可能的地址开销。Com 也支持基于 TP 的大 I-PDU。应依据配置和协议选择链路，而非单看数据长度。

Com 路径不意味着自动可靠或实时，TP 也不是任意长度、不确定时序的通道。二者都需要资源预算和明确的超时策略；ISO-TP 超时通常导致中止，不应笼统理解成自动重传。

## 四、接收与上下文

CAN 驱动通过规定的 `CanIf_RxIndication` 等上层回调通知数据；CanIf 再按当前版本交付 LSduR 等规定模块。Com 可配置即时或延后处理，CAN 驱动也可能使用轮询。不能固定描述为“所有接收必须 ISR 入队再主函数解包”。

数据在哪个上下文复制、缓冲何时失效、回调是否可重入，都要在每个 API 边界核对。

## 五、PduR 与 LSduR 的关系

两者是不同职责，不是重复命名。LSduR 规范说明它们功能相似，配置和实现可以整合在一个模块中；这不改变对外接口合同。

PduR 的路由来自静态配置，不按任意业务载荷即时计算路径；配置的 routing path group 可在运行时启停，所以“静态配置”也不等于“运行时所有状态永远不变”。

## 六、BCM 裁剪边界

采用自建 dbcom 与轻量通信框架时，可以按需求实现必要路由和状态管理，不必机械增加一层空函数。若声明对应 AUTOSAR 版本兼容，则必须证明规定接口、配置和行为一致，不能仅靠模块名。

J1939、LIN、UDS over CAN 是否存在，以项目通信规范为准；不能从“商用车 BCM”自动推断所有协议都必须实现。

## 七、自检

1. Dcm 与 CanTp 之间是谁？CanTp 与 CanIf 之间是谁？
2. 短 UDS 响应为什么仍需 TP 链路？
