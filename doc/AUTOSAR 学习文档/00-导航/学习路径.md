# 学习路径

> [!important] 2026-10-23 审查入口
> 先读 [[R25-11审查报告]] 与 [[逐篇审查记录]]，区分官方结论、教学简化和项目建议。与当前项目直接相关的扩展为 [[06-IO端点与采集路线设计]]、[[07-业务绑定诊断与任务落地]]。原文件名保留，官方 PDF 使用外部本地链接。


> [!tip] 结论
> 三条路径，按目的选：
> - **路径 A 建立认知**（2~3 天）→ 能画出骨架、解释每层为什么存在
> - **路径 B 上手写代码**（1 周）→ 能读 SWS、能按规范写 BSW 模块
> - **路径 C 项目落地**（配合项目）→ 明确"该实现哪几层、边界在哪"
>
> **不要按目录顺序从头读到尾**——那是按"知识分类"排的，不是按"学习顺序"排的。

## 路径 A：建立认知（2~3 天）

**目标**：能在白板上画出 AUTOSAR 骨架，并回答"为什么每一层都存在"。

| 天 | 读什么 | 读完能回答 |
|---|---|---|
| **第 1 天** | [[01-AUTOSAR要解决什么问题]]<br>[[02-第一性原理-功能与部署解耦]]<br>[[03-虚拟功能总线VFB]] | AUTOSAR 到底解决什么？VFB 是软件吗？ |
| **第 2 天** | [[04-分层哲学的由来]]<br>[[01-分层架构总览]]<br>[[07-BSW模块类型分类法]] | 为什么是四层？Driver 和 Manager 怎么分？ |
| **第 3 天** | [[05-组件风格与分层风格的分界]]<br>[[08-三种接口类型]]<br>[[01-方法论总览-V模型产物链]] | RTE 为什么必须存在？从功能到代码经过什么？ |

**检验标准**（能答上就算过关）：

1. 为什么 AUTOSAR 要规定"应用层不能直接调 MCAL"，而不是"建议不要"？
2. 同一个 Connector，映射到"同 Task"和"跨 ECU"，代码差多少？
3. 为什么 `CanIf` 用 C 函数接口就说明它不能跨 ECU？

## 读法建议

### 1. 每篇先看"结论"框

每篇开头的 `> [!tip] 结论` 就是全文摘要。
**如果结论你已经懂了，可以跳过正文**；不懂再往下读。

### 2. 表格优先

本库大量用表格做对比。**表格比段落信息密度高 3 倍**。
遇到表格，先看表头和第一列，再决定要不要细读。

### 3. 主动回答"自检"

每篇末尾有 2~3 个自检题。
**答不上来就回去重读**——这比"读完就忘"有效得多。

### 4. 不要试图记住所有细节

| 该记 | 不该记 |
|---|---|
| 判断依据（如"看变化源分层"） | 具体寄存器名 |
| 设计动机（为什么这样设计） | 具体参数默认值 |
| 边界（什么能做什么不能做） | 所有 API 签名 |
| 陷阱（哪里容易错） | 所有错误码 |

**细节查索引和规范，判断力才是自己的。**

### 5. 配合原文

每篇都标了 `source:`（来源文档）。遇到不确定的地方：

```
打开 doc/AUTOSAR-CP_R25-11官方资料/AUTOSAR_CP_<类型>_<主题>.pdf
→ 搜关键字 → 核对原文
```

规范导读类文档教你**怎么高效查**：
- [[01-规范文档体系-SWS-RS-EXP-TPS-TR]] — 查哪类
- [[02-如何读一份SWS]] — 怎么读

## 一个常见的学习陷阱

> [!warning] "我要先把 212 份文档读完"
> **这是最糟的学习方式。**
>
> | 事实 | 数字 |
> |---|---|
> | 文档总数 | 212 份 |
> | 总页数（估算） | 2 万页以上 |
> | 你需要读的 | 约 15 份 |
> | 你实际需要的知识 | 本库 59 篇 |
>
> **先建立框架（路径 A），再按需深入（路径 B/C）。**
> 框架没建立就钻细节，会陷入"知道很多名词但不理解体系"的状态。
