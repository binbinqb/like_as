# 规范项生命周期与版本

> [!tip] 结论
> AUTOSAR 每年 11 月发一版（`Ryy-mm`），其 major release 生命周期描述了四个阶段：**Development → Evolution → Maintenance → Issue Notice**。
> 每个规范条目有状态：**VALID / DRAFT / OBSOLETE**。
> **选版本的本质是选"成熟度 vs 新功能"的平衡点。**

## 一、发布生命周期四阶段

> Each major release goes through four consecutive steps within its life cycle:
> 1. **Development**: Between start of life cycle and the initial release
> 2. **Evolution**: Following the initial release with zero, one or several minor releases and/or revisions
> 3. **Maintenance**: **No new content is added** to a major release but only maintenance of the existing content
> 4. **Issue Notice**: **No more revisions** but zero, one or several issue notices, i.e., updates of the list of known issues until end of life cycle

```
Development → Evolution → Maintenance → Issue Notice → STOP
   不兼容       向后兼容      只修 bug      只更新已知问题
   扩展         扩展 + 修 bug
```

| 阶段 | 允许的变更 | 用于产品吗 |
|---|---|---|
| **Development** | 不兼容扩展 | ❌ 不要 |
| **Evolution** | 向后兼容扩展 + 修 bug | ⚠️ 可以，关注新增 |
| **Maintenance** | **只修 bug** | ✅ **推荐** |
| **Issue Notice** | 只更新已知问题清单 | ✅ 维护期 |

> [!important] 量产项目的版本选择原则
> **"最新"不等于"最好"。**
> - 新版本 = 新功能 + 新 bug + 工具链未必支持
> - Maintenance 阶段 = 功能稳定 + bug 已知 + 工具链成熟
>
> **经验：选"发布后 1~2 年"的版本**，即当前版本的前一两个。

## 二、两套版本号

### 2.1 平台版本（Ryy-mm）

> AUTOSAR applies a **four-digit numbering scheme `Ryy-mm`** to identify releases. The identifiers "yy" and "mm" depict the **year and month** of the release date.

| 版本 | 发布时间 |
|---|---|
| R20-11 | 2020 年 11 月 |
| R21-11 | 2021 年 11 月 |
| R22-11 | 2022 年 11 月 |
| R23-11 | 2023 年 11 月 |
| R24-11 | 2024 年 11 月 |
| **R25-11** | **2025 年 11 月（本库基于此）** |

**规律**：每年 11 月发布，所以中间数字永远是 11。

### 2.2 内部版本（R\<major\>.\<minor\>.\<revision\>）

> AUTOSAR additionally maintains an **internal release number** for different purposes (e.g., **usage in BSW modules** in Classic Platform).
> Its primary purpose is to identify a release as:
> - a **major release**: Valid and draft specification parts may be changed **backward incompatibly**
> - a **minor release**: ...
> - a **revision**: bug fixes only

| 类型 | 格式 | 变更性质 |
|---|---|---|
| Major | `R4.0.0` | 不兼容变更 |
| Minor | `R4.4.0` | 向后兼容扩展 |
| Revision | `R4.4.1` | 只修 bug |

### 2.3 两套版本号的映射

| 平台版本 | 内部版本 |
|---|---|
| R25-11 | R4.11.0；Schema AUTOSAR_00054 |
| R24-11 | R4.10.0；Schema AUTOSAR_00053 |
| ... | ... |

> [!warning] 版本不匹配是集成事故高发区
> - **文档**标平台版本（`R25-11`）
> - **代码**里的宏是内部版本（如 `R4.4.0`）
>
> 两者必须通过映射表换算。混用会导致"文档说支持、代码里没有"。
>
> **检查方法**：看模块头文件里的 `XXX_AR_RELEASE_MAJOR_VERSION` / `MINOR_VERSION` / `REVISION_VERSION`。

## 三、规范条目的三种状态

> The life cycle state of a specification item is found **after the specification item ID surrounded by curly brackets**:
> - **VALID**: the related entity is a **valid part** of the document. This is the default and also applies if no dedicated life cycle status is annotated.
> - **DRAFT**: the related entity is **newly introduced but still experimental**. This information is published but is **subject to change without backward compatibility guarantee**.
> - **OBSOLETE**: the related entity is **subject to be removed in one of the following releases without further notice**.

```
[SWS_Com_00011]           ← 无标注 = VALID
[SWS_Com_91025]{DRAFT}    ← 实验性
[SWS_Com_00099]{OBSOLETE} ← 将被移除
```

| 状态 | 含义 | 量产能用吗 | 建议 |
|---|---|---|---|
| **VALID** | 有效 | ✅ | 放心用 |
| **DRAFT** | 实验性，可能不兼容地改 | 按项目接受策略评估 | 不代表标准统一禁止量产，需冻结范围并分析兼容风险 |
| **OBSOLETE** | 后续版本可能移除 | 按基线与替代计划评估 | 不宜新引入，但不能等同本版本已经删除 |

> [!important] DRAFT 的杀伤力
> "**without backward compatibility guarantee**"
> 下个版本可能：
> - 改语义（同名不同义）
> - 改接口（参数变了）
> - 直接删除
>
> 使用 DRAFT 应明确当前版本冻结、迁移和验证策略，不能依赖跨版本兼容承诺。

## 四、版本升级的影响评估

### 4.1 升级时要看什么

| 检查项 | 在哪看 |
|---|---|
| 新增/删除的模块 | ReleaseOverview 2.2.1 / 2.2.4 |
| 重做的规范 | ReleaseOverview 2.2.5 |
| 移动的规范部分 | ReleaseOverview 2.2.6 |
| 重命名的规范 | ReleaseOverview 2.2.7 |
| 每个文档的变更历史 | 各文档的 Change History 章 |
| 已知技术缺陷 | ReleaseOverview 第 4 章 |

### 4.2 变更的三种类型

```
删除（Removed）
    ↓ 影响最大：用到的功能没了
不兼容修改（Changed, backward incompatible）
    ↓ 需要改代码
兼容扩展（Added, backward compatible）
    ↓ 一般无影响
```

> [!tip] 升级前必做的一件事
> **在 ReleaseOverview 里搜你用的所有模块名**，看有没有变动。
> 这是 30 分钟的活，能省几周的返工。

## 五、CP / AP / FO 的版本关系

> Each release of Classic and Adaptive Platform relies on a **dedicated version of Foundation**.
> This release of the Classic Platform depends on the standard Foundation in release **R25-11**.

```
        Foundation R25-11
         │            │
    CP R25-11    AP R25-11
```

| 规则 | 说明 |
|---|---|
| 一个 CP 版本对应一个 FO 版本 | 不能跨版本混用 |
| FO 定义了通用协议、通用需求 | CP/AP 共享 |
| 升 CP 必须同时升 FO | 版本配套 |

## 六、如何选版本（决策表）

| 项目状态 | 建议版本 |
|---|---|
| 全新项目、追求稳定 | OEM、供应商、工具与验证范围共同支持的版本；不能按发布年份自动推断 Maintenance |
| 需要某新特性 | 当前版本（评估 DRAFT 风险） |
| 维护期项目 | 保持原版本 + Issue Notice |
| 学习/研究 | **最新版**（看趋势） |
| 要过认证 | 选有成功案例的版本 |

### 一个实际考虑

| 因素 | 影响 |
|---|---|
| **BSW 供应商支持** | 供应商支持哪个版本，往往决定你的选择 |
| **工具链支持** | 建模/配置工具是否支持该版本的 ARXML schema |
| **团队经验** | 团队熟悉的版本，学习成本低 |
| **OEM 要求** | 客户可能指定版本 |

> [!warning] 现实约束往往大于技术最优
> 你"想用最新版"，但：
> - BSW 供应商只支持到 R22-11
> - 配置工具不支持新版 schema
> - OEM 规范基于 R20-11
>
> **最终版本是多方约束的交集，不是技术选型。**

## 七、版本信息在代码里的体现

AUTOSAR 模块通常有版本宏：

```c
/* Can.h */
#define CAN_AR_RELEASE_MAJOR_VERSION   4u
#define CAN_AR_RELEASE_MINOR_VERSION   4u
#define CAN_AR_RELEASE_REVISION_VERSION 0u

#define CAN_SW_MAJOR_VERSION           1u
#define CAN_SW_MINOR_VERSION           0u
#define CAN_SW_PATCH_VERSION           0u
```

| 宏 | 含义 |
|---|---|
| `AR_RELEASE_*` | **AUTOSAR 规范版本**（内部版本号） |
| `SW_*` | **软件实现版本**（供应商自己的） |

### 版本检查机制

```c
#if (CAN_AR_RELEASE_MAJOR_VERSION != 4u)
  #error "Can.h: version mismatch"
#endif
```

**用途**：防止"头文件是 v4.4，实现是 v4.2"的混用。

> [!tip] 集成时的第一个检查
> 编译报"version mismatch" → 说明不同模块的 AUTOSAR 版本不一致。
> **不要改宏绕过**，要统一版本。

## 八、变更历史的读法

每份 SWS 开头都有 Change History：

```
Date        Release   Changed by            Change Description
2025-11-27  R25-11    Release Management    • Added Transmission Request Queue for TP Channels
2024-11-27  R24-11    Release Management    • Changed lower layer to LSduR
                                            • Added detection of header violations
2023-11-23  R23-11    Release Management    • Added Extended Production Errors
```

**读法**：

| 关注 | 为什么 |
|---|---|
| 最近 2~3 个版本的变更 | 了解演进方向 |
| 与你相关的功能 | 判断是否需要升级 |
| `Removed` 类变更 | 检查自己是否用了 |
