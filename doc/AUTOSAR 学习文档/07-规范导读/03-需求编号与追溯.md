# 需求编号与追溯

> [!tip] 结论
> AUTOSAR 的每个需求、每个 API、每个配置参数都有**唯一 ID**，形成一条**可追溯的链**：
> **项目目标 → 需求（SRS）→ 规范（SWS）→ 配置（ECUC）→ 测试用例**
>
> 这条链的价值：**任何一行代码都能向上追溯到"为什么要这样做"。**

## 一、常见 ID 类型

| 前缀 | 例子 | 定义在哪 | 含义 |
|---|---|---|---|
| **`SRS_`** | `SRS_BSW_00161` | RS 文档 | **需求**（要什么） |
| **`SWS_`** | `SWS_Com_00011` | SWS 文档 | **规范条目**（怎么做） |
| **`ECUC_`** | `ECUC_Com_10032` | SWS 第 10 章 | **配置参数** |
| **`TPS_`** | `TPS_SWCT_01047` | TPS 文档 | **元模型约束** |
| **`TR_`** | `TR_METH_01044` | TR 文档 | **方法论需求** |
| **`constr_`** | `constr_1092` | TPS/SWS | **约束**（meta-model constraint） |

### 历史统计示意（非本轮可复现的唯一条目计数）

| 前缀 | 出现次数（前 20 份文档统计） | 说明 |
|---|---|---|
| `SWS_Dcm_` | 2558 | 诊断模块条目最多（800 页） |
| `TPS_SWCT_` | 2459 | SWC 模板约束 |
| `TPS_SYST_` | 1973 | System 模板约束 |
| `SWS_Dem_` | 1815 | |
| `SWS_Os_` | 1398 | |
| `ECUC_Dcm_` | 976 | 配置项 |
| `SRS_BSW_` | 881 | BSW 通用需求 |

## 二、ID 的内部结构

```
SWS_Com_00011
│   │   └── 序号（文档内唯一，通常是 5 位，也见 3~6 位）
│   └────── 主题/模块名
└────────── 类型前缀
```

### 命名的不一致（要知道）

| 模块 | 实际写法 | 备注 |
|---|---|---|
| Com | `SWS_Com_xxxxx` | 驼峰 |
| CanIf | `SWS_CANIF_xxxxx` | **全大写**（历史遗留） |
| CanNm | `SWS_CanNm_xxxxx` | 驼峰 |
| NvM | `SWS_NvM_xxxxx` | 驼峰 |
| Dcm | `SWS_Dcm_xxxxx` | 驼峰 |

> [!warning] 搜索时要注意大小写
> 搜 `SWS_CanIf` 找不到，要搜 `SWS_CANIF`。
> **AUTOSAR 的命名并不完全统一，这是历史演进的结果。**

## 三、追溯链

```
┌─────────────────────────────────────┐
│ Foundation: 项目目标、通用需求         │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│ RS: SRS_Can_01059                   │  ← "要什么"
│ "The CAN driver shall directly copy │
│  data from upper layer buffers"     │
└──────────────┬──────────────────────┘
               │ Requirements Tracing
┌──────────────▼──────────────────────┐
│ SWS: SWS_Can_00011                  │  ← "怎么做"
│ "The Can module shall directly copy │
│  the data from the upper layer..."  │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│ ECUC: ECUC_Can_xxxxx                │  ← "怎么配"
│ 配置参数定义                          │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│ 代码 / 配置 / 测试用例                │
└─────────────────────────────────────┘
```

### 在文档里怎么看这条链

**向上看**（SWS → RS）：

```
[SWS_Can_00011]
Upstream requirements: SRS_SPAL_12075, SRS_Can_01059   ← 这里
⌈The Can module shall directly copy...⌋
```

**向下看**（RS → SWS）：

在对应的 SWS 里搜索 `SRS_Can_01059`，能找到所有实现它的条目。

**横向看**（需求覆盖）：

每个 SWS 的 **第 6 章 Requirements Tracing** 有完整表格：

| Requirement | Description | Satisfied by |
|---|---|---|
| `SRS_Can_01059` | 直接拷贝数据 | `SWS_Can_00011` |
| 其他条目 | 按真实追溯表填写，不使用推测的连续 ID | 按 SWS 正文核对 |

> [!important] 第 6 章是被低估的宝库
> 想知道"这个模块为什么必须这样设计"，从第 6 章往上追。
> 往往能追到一条很具体的使用场景（Use Case）。

## 四、追溯的工程价值

| 场景 | 有追溯 | 没有追溯 |
|---|---|---|
| 客户问"你满足这条需求吗" | 5 分钟给出证据 | 一周翻代码 |
| 改一个需求 | 知道影响哪些模块 | 靠经验猜 |
| 审查"为什么这样实现" | 追溯到需求 | "一直这样" |
| 认证（ISO 26262 / ASPICE） | 直接出追溯矩阵 | 补文档半年 |
| 裁剪决策 | 知道裁掉的是哪条需求 | 不知道影响了什么 |

### 项目追溯要求（须按适用过程标准进一步核对）

以下双向追溯是项目建议结构；具体义务需按采用的 ISO 26262／Automotive SPICE 版本与过程范围核对：

```
需求 → 设计 → 实现 → 测试
  ↑                        │
  └────────────────────────┘
        （双向可追）
```

AUTOSAR 的 ID 体系天生支持这个。

## 五、在项目中实践追溯

以下 SRS_BCM_* 是项目自定义示例 ID，不是 AUTOSAR 官方条目；状态勾选和代码行号也是演示。

### 5.1 最小可行方案（不用专门工具）

**建立一张追溯表**（Excel 或 Markdown）：

| 需求 ID | 需求描述 | 实现位置 | 测试用例 | 状态 |
|---|---|---|---|---|
| `SRS_BCM_0001` | 近光灯 100ms 内响应 | `light_ctrl.c:120` | `TC_LIGHT_001` | ✅ |
| `SRS_BCM_0002` | 中控锁 15km/h 自动落锁 | `lock.c:88` | `TC_LOCK_003` | ✅ |
| `SRS_BCM_0003` | 睡眠电流 < 1mA | `power.c:200` | `TC_PWR_005` | ⚠️ 待测 |

### 5.2 代码里的追溯

```c
/**
 * @brief  近光灯控制
 * @req    SRS_BCM_0001  (近光灯 100ms 内响应)
 * @design DS_LIGHT_001 (状态机设计见 doc/design/light.md)
 * @test   TC_LIGHT_001
 */
void LightControl_LowBeam(void)
{
    ...
}
```

> [!tip] Doxygen 的 `@req` 标签不是标准的
> 但可以用 `@note` 或自定义标签，配合脚本提取。
> 关键是**有统一的约定**，而不是用什么标签。

### 5.3 用脚本做校验

```python
# 检查：代码里引用的需求 ID 是否都在需求库中存在
import re, glob

known = set(open('requirements.txt').read().split())
for f in glob.glob('src/**/*.c', recursive=True):
    for m in re.finditer(r'SRS_BCM_\d{4}', open(f).read()):
        if m.group() not in known:
            print(f'{f}: 未知需求 {m.group()}')
```

**这个脚本能防止"引用了不存在的需求"或"需求改了 ID 忘了同步"。**

## 六、需求的状态管理

AUTOSAR 规范项有生命周期状态：

> `[TR_ReleaseOverview]` The life cycle state of a specification item is found **after the specification item ID surrounded by curly brackets**:
> - **VALID**: valid part of the document（默认）
> - **DRAFT**: newly introduced but still **experimental**, subject to change without backward compatibility guarantee
> - **OBSOLETE**: subject to be **removed in one of the following releases**

```
[SWS_Com_91025]{DRAFT}
```

| 状态 | 能不能用 | 建议 |
|---|---|---|
| `VALID` | ✅ | 放心用 |
| `DRAFT` | 按项目风险策略 | 实验性、无向后兼容保证，不是标准统一禁止量产 |
| `OBSOLETE` | 按版本基线评估 | 不宜新引入，已有实现规划替换，区别于已移除 |

> [!warning] 用 DRAFT 条目的风险
> "subject to change **without backward compatibility guarantee**"
> 下个版本可能改语义、改接口、甚至删除。
> 将 DRAFT 使用纳入基线冻结、风险和升级兼容性记录。

## 七、需求条目的完整字段

一个规范条目可能包含：

```
[SWS_Com_00011]{VALID}
Upstream requirements: <真实上游需求ID>
Previous identifiers: <实际旧标识，若正文提供>        ← 改名前是什么
⌈
<需求正文>
⌋
Tags: atp.Status=draft                        ← 元模型标记
```

| 字段 | 用途 |
|---|---|
| **ID** | 唯一标识 |
| **状态** `{VALID}` | 生命周期 |
| **Upstream requirements** | 上游追溯 |
| **Previous identifiers** | 改名前 ID（搜索历史用） |
| **Tags** | 元模型标记（如 `atp.Status`） |

> [!tip] `Previous identifiers` 很实用
> 模块改名/合并后，老 ID 仍可搜索到新位置。
> 例：`LdCom` 并入 `Com` 后，`SWS_LDCOM_xxxxx` 会标注新 ID。

## 八、追溯矩阵的自动生成

如果你有 ARXML 模型，可以用脚本生成追溯矩阵：

```python
# 从 ARXML 提取需求追溯（概念示例）
import xml.etree.ElementTree as ET

ns = {'a': 'http://autosar.org/schema/r4.0'}
tree = ET.parse('model.arxml')

for elem in tree.iter():
    tag = elem.tag.split('}')[-1]
    if tag == 'TRACE':
        print(elem.findtext('a:SHORT-NAME', namespaces=ns))
```

上面的 TRACE 扫描仅为概念示例，不构成已验证的 AUTOSAR Schema 遍历器；应按实际模型元素、引用和工具导出格式实现。

## 九、对 BCM 项目的建议

| 阶段 | 追溯要求 |
|---|---|
| 需求分析 | 每条需求有唯一 ID（`SRS_BCM_xxxx`） |
| 设计 | 设计文档引用需求 ID |
| 编码 | 关键函数注释引用需求 ID |
| 测试 | 测试用例引用需求 ID |
| 变更 | 需求变更时更新所有引用 |

### 一个务实的起点

**不要一上来就搞全套工具链。** 从这三件事开始：

1. **需求编号**：给每条需求一个 ID（Excel 就够）
2. **代码注释**：关键函数写 `@req SRS_BCM_xxxx`
3. **测试用例**：用例名或描述里带需求 ID

**这三件事做到，就能回答"这条需求实现了吗、测了吗"。**
