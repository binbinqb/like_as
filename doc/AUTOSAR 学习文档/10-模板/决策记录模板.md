# 决策记录模板

> [!tip] 用途
> 记录两类决策：
> 1. **架构决策**（为什么这样分层、为什么用这个机制）
> 2. **裁剪决策**（为什么不做某个模块/功能）
>
> **为什么必须记录**：半年后你会忘记理由，新人会重新讨论一遍。

## 裁剪决策的专用格式

如果决策是"不做某模块/功能"，用这个补充块：

```markdown
## 裁剪信息

| 项 | 内容 |
|---|---|
| **模块** | |
| **裁剪层次** | L1 模块级 / L2 功能级 / L3 行为级 |
| **裁剪内容** | |
| **对外行为影响** | 对总线 / bootloader / 应用 / 诊断仪 的影响 |
| **风险等级** | 低 / 中 / 高 |
| **若将来需要** | 补做的工作量评估 |
```

### L1/L2/L3 的判定

| 层次 | 判定 | 风险 | 示例 |
|---|---|---|---|
| **L1 模块级** | 整个模块不做 | 低 | 不做 V2X |
| **L2 功能级** | 模块内某功能不做 | 中 | 不做 NvM 冗余块 |
| **L3 行为级** | 某对外行为简化 | **高** | 简化 TP 时序 |

> [!warning] L3 必须有"反对意见"
> 凡是 L3 裁剪，必须有人论证风险。
> 因为 L3 改的是**对外表现**，客户/诊断仪能看出来。

## 示例：一条完整记录

```markdown
# ADR-20261023：Mini-AUTOSAR 不实现完整 RTE 生成器

> [!tip] 一句话
> 我们决定 **手写薄封装代替 RTE 生成器**，因为 **单 ECU 部署固定，生成器的收益不足以抵消工具链成本**。

## 状态
| 状态 | 已采纳 |
|---|---|
| 决策日期 | 2026-10-23 |
| 影响范围 | 应用层与通信层之间 |

## 背景
- 单颗 CVM0146，无跨 ECU 部署需求
- 无 ARXML 建模工具
- 团队 1~2 人，无维护生成器的资源

## 选项对比
| 选项 | 做法 | 优点 | 缺点 | 成本 |
|---|---|---|---|---|
| A | 引入完整 RTE 生成器 | 标准、可扩展 | 工具链成本高、学习曲线陡 | 高 |
| B | 手写语义接口封装 | 简单、可控 | 无自动化、需自律 | 低 |
| C | 应用直接调通信层 | 最快 | 业务被通信污染 | 最低 |

## 决策
**选择 B。**

理由：
1. 单 ECU 部署下，RTE 生成的代码 90% 是直接赋值，手写宏即可
2. 保留"应用不感知通信"的核心价值（选项 C 丢掉了）
3. 若将来拆 ECU，只需替换 `rte_*.c` 的实现

## 后果
### 正面
- 无工具链依赖
- 接口完全可控
### 负面
- 需人工保证"应用层不 include 通信头文件"（靠 code review + 脚本）
- 无自动的部署一致性检查
### 跟进
- [ ] 写 include 依赖检查脚本
- [ ] 在 CI 里加检查

## 验证方式
| 验证项 | 方法 | 通过标准 |
|---|---|---|
| 应用层零依赖通信 | 搜 `#include` | 无 `dbc_`/`can_`/`hal_` |
| 换部署实现不改应用 | 替换 `rte_*.c` | 编译通过 |
````

## 使用建议

| 什么该记 | 什么不用记 |
|---|---|
| 有多种合理选项的决策 | 唯一解的事（如"用 C 不用汇编"） |
| 影响多个模块的决策 | 局部实现细节 |
| 有争议的决策 | 无争议的 |
| 会被人反复质疑的决策 | 显而易见的 |

> [!tip] 一个好判据
> **"如果三个月后有人问'为什么当初这样做'，我能答上来吗？"**
> 答不上来 → 该记。
