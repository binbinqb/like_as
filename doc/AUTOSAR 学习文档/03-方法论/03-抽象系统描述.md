# 抽象系统描述（功能视图）

> [!tip] 结论
> 抽象系统描述回答"**车要做什么**"，而不是"**软件怎么分**"。
> 它是可选的，但可用已有功能架构等输入承担相应分析，跳过某个可选产物不必然意味着跳过需求与架构思考。

## 一、官方定位

> `[TR_METH_01044]` The overall workflow starts with an **optional** activity.
> In this activity, the **Abstract System Description** is developed in advance, which represents the overall system from a **functional or abstract view (functional architecture)**.
> - On the one hand, this Abstract System Description might contain **VFB-related parts**. This information might serve as an input for the development of the VFB later and a **mapping between those two views** might be established.
>   Please note that during this step the functionality including ports is mapped to software components. Therefore **some ports used in the abstract view might not be used in the subsequent development**.
> - On the other hand, the Abstract System Description might contain information regarding the **topology** and the **mapping to ECUs**. This is then the basis for the development of the concrete System Description.

## 二、它和 VFB 视图的区别

```
Abstract View（功能视图）
┌──────────┐   ┌──────────┐   ┌──────────┐
│Function A│──▶│Function B│──▶│Function C│
└──────────┘   └──────────┘   └──────────┘
     功能块 + 信息流（"要做什么"）

            ↓ 映射（多对多，可重组）

VFB View（组件视图）
┌────────┐   ┌────────┐   ┌────────┐
│ SWC 1  │──▶│ SWC 2  │──▶│ SWC 3  │
└────────┘   └────────┘   └────────┘
     软件组件 + 端口（"软件怎么分"）
```

| 维度 | Abstract View | VFB View |
|---|---|---|
| 单位 | 功能（Function） | 软件组件（SWC） |
| 关心 | 输入什么、输出什么、什么逻辑 | 谁提供、谁消费、怎么连 |
| 与硬件 | 无关 | 无关 |
| 映射关系 | **多对多** | — |
| 稳定性 | 高（功能不常变） | 中（软件结构会调整） |

## 三、为什么允许"多对多"

这是抽象视图的核心价值：**功能分解 ≠ 软件分解**。

### 情况 1：一个功能拆成多个 SWC

```
功能：车灯控制
  ├─ SWC: 灯光开关采集
  ├─ SWC: 灯光逻辑决策
  └─ SWC: 灯光输出驱动
```

**为什么拆**：这三部分变化频率不同（开关采集随硬件变，逻辑随需求变，输出随执行器变）。

### 情况 2：多个功能合成一个 SWC

```
功能：门锁控制 + 车窗防夹 + 后视镜折叠
  └─ SWC: 车门域控制器逻辑
```

**为什么合**：共享大量状态（车门开闭、钥匙位置），强行拆开会导致大量内部通信。

### 情况 3：功能块在软件里不存在

某些功能块在实现时被"吸收"到 BSW 或硬件里：

| 功能块 | 实现方式 |
|---|---|
| "信号去抖" | 吸收到 IoHwAb |
| "报文超时检测" | 吸收到 Com 的 Deadline Monitoring |
| "PWM 生成" | 吸收到 MCAL 的 Pwm 模块 |

> [!important] 这就是原文说的
> "**some ports used in the abstract view might not be used in the subsequent development**"
> 抽象视图里的某些端口，在 VFB 视图里会消失 —— 因为它被 BSW 承担了。
> **这不是错误，是正常的实现决策。**

## 四、什么时候需要抽象系统描述

| 场景 | 需要吗 | 理由 |
|---|---|---|
| 全新平台、功能复杂 | ✅ 强烈推荐 | 先理清功能再谈软件，避免架构被实现细节绑死 |
| 已有平台迭代 | ⚠️ 可选 | 功能架构已稳定，可直接改 VFB |
| 功能安全项目 | ✅ 推荐 | ISO 26262 要求功能层面分析（HARA 在功能层） |
| 多供应商协作 | ✅ 推荐 | 功能视图是"中立语言"，便于分工 |
| 单人小项目 | ❌ 可跳过 | 直接设计 SWC 更高效 |

## 五、抽象系统描述里放什么

| 元素 | 说明 | 例子 |
|---|---|---|
| **功能块（Function）** | 一个功能单元 | "近光灯控制" |
| **信息流（Information Flow）** | 功能块之间的数据流 | "车速 → 近光灯控制" |
| **功能端口** | 功能块的输入/输出 | "环境光强度输入" |
| **功能层次** | 功能的分解树 | 车灯 → 近光/远光/转向 |
| **（可选）拓扑** | ECU 与网络 | 用于后续 System Description |
| **（可选）到 ECU 的映射** | 粗粒度 | "车灯功能在 BCM" |

> [!note] 注意"可选拓扑"这一点
> 原文说抽象系统描述"might contain information regarding the **topology** and the **mapping to ECUs**"。
> 也就是说：**抽象视图可以和拓扑信息一起描述**，作为后续 System Description 的输入。
> 这打破了"必须先功能后部署"的教条 —— 实际上，功能架构和部署拓扑常常是同时确定的。

## 六、BCM 项目怎么用

### 6.1 从功能清单出发

| 功能域 | 功能块 | 输入 | 输出 |
|---|---|---|---|
| 灯光 | 近光灯控制 | 开关、环境光、车速、电源模式 | 近光灯 PWM 占空比 |
| 灯光 | 转向灯控制 | 转向开关、危险开关、点火状态 | 左/右转向灯通断 |
| 灯光 | 室内灯控制 | 车门状态、钥匙状态、光照 | 室内灯亮度 |
| 门锁 | 中控锁控制 | 钥匙信号、门状态、车速 | 锁/解锁命令 |
| 雨刮 | 雨刮控制 | 雨量、车速、开关 | 雨刮速度档位 |
| 电源 | 电源模式管理 | KL15/KL30、唤醒源 | 电源模式、休眠命令 |

### 6.2 识别"共享信息流"

```
车速 ──┬──▶ 近光灯控制
       ├──▶ 转向灯控制（车速>阈值时自动回位）
       ├──▶ 中控锁控制（车速>15 自动落锁）
       └──▶ 雨刮控制（车速影响间歇时间）
```

**这类"一对多"的信息流，是后续设计的关键**：
- 如果车速来自 CAN，就是一个信号广播给多个 SWC
- 如果每个 SWC 都去解析 CAN 报文 → 严重重复
- 正确做法：**一个 SWC 负责解析，其他 SWC 从它取**

> [!tip] 抽象视图的最大价值
> 它让你在写代码前就看到"哪些信息被多处使用"，
> 从而设计出正确的**信息枢纽**（而不是让每个模块各自解析总线）。

### 6.3 从功能到 SWC 的映射决策

| 功能块 | 拆/合 | SWC |
|---|---|---|
| 近光灯控制 | 拆 | `LightSwitchAcq` + `LowBeamLogic` + `LightOutput` |
| 转向灯控制 | 拆 | `TurnSwitchAcq` + `TurnLogic` + `LightOutput`（共享输出） |
| 中控锁 | 合 | `CentralLocking`（内部含采集/逻辑/输出） |
| 车速分发 | 单独 | `VehicleSpeedProvider` |

**决策依据**：
- 变化频率是否不同 → 拆
- 是否共享大量状态 → 合
- 是否被多处依赖 → 单独成组件

## 七、交付物形态（不一定要 ARXML）

| 项目规模 | 抽象系统描述的形态 |
|---|---|
| 大型（正式 AUTOSAR） | ARXML（`SystemDescription` 的功能部分）+ 建模工具 |
| 中型 | 结构化文档（功能清单 + 信息流表 + 框图） |
| 小型 | 一页纸的功能框图 + 数据流表 |

> [!important] 形态不重要，内容重要
> 关键是三件事：
> 1. **功能块边界清晰**（每个功能块职责单一）
> 2. **信息流标注清楚**（谁给谁什么数据）
> 3. **共享信息被识别**（哪些数据被多处使用）
>
> 这三件事做到，用 Excel 也够；做不到，用最贵的工具也没用。
