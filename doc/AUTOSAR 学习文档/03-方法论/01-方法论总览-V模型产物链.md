# 方法论总览：V 模型产物链

> [!tip] 结论
> AUTOSAR 方法论的本质是：**用任务、角色、输入和产物组织开发；可标准化的模型以 ARXML 交换，代码与测试仍含手写和非 ARXML 产物。**
> 工具生成 RTE 与配置等产物，应用算法、驱动实现及集成验证仍需工程开发。
> 方法论支持迭代、复用与不同组织分工，下面的直线链用于导航，不是唯一强制流水线。

## 一、完整产物链

```
【需求】功能需求 / 系统规范
   │
   ▼
① Abstract System Description（抽象系统描述）
   │  功能视图：功能块 + 功能块之间的信息流
   │  可选，但推荐
   ▼
② VFB System Description（VFB 系统描述）
   │  组件视图：SWC + Port + Connector（不含 ECU、不含网络）
   ▼
③ System Description（系统描述）
   │  加入拓扑：ECU 列表 + 网络 + 映射（哪个 SWC 在哪颗 ECU）
   │  加入通信矩阵
   ▼
④ System Extract（系统摘取）
   │  按"供应商边界"切出的子系统视图（给供应商的部分）
   ▼
⑤ ECU System Description / ECU Extract
   │  单颗 ECU 的完整视图（该 ECU 上所有 SWC + 连接 + 需要的 BSW）
   ▼
⑥ ECU Configuration（ECU 配置）
   │  每个 BSW 模块的参数（预编译/链接/后构建）
   ▼
⑦ Generate（生成）
   │  RTE 代码 + BSW 配置代码
   ▼
⑧ Build（编译链接）
   │  .elf / .hex
   ▼
⑨ Integration & Test（集成测试）
```

> [!note] 这条链的关键特征
> **输入输出明确、可追溯，并对适用产物采用机器可读模型。**
> - 可迭代：集成反馈可以驱动上游模型修订，应保持产物版本和影响分析一致
> - 可追溯：每个产物都能追到它的输入
> - 可交换：ARXML 支持标准模型交换，不排斥需求、测试和实现的其他载体

## 二、各阶段详细说明

### ① Abstract System Description（抽象系统描述）

> In this activity, the Abstract System Description is developed in advance, which represents the overall system from a **functional or abstract view (functional architecture)**.
> On the one hand, this Abstract System Description might contain **VFB-related parts** ... and a **mapping between those two views** might be established.
> On the other hand, the Abstract System Description might contain information regarding the **topology** and the **mapping to ECUs**.
> —— TR_Methodology, `[TR_METH_01044]`

| 项 | 内容 |
|---|---|
| 视角 | 功能（"要做什么"），不是软件（"怎么做"） |
| 内容 | 功能块、功能块之间的信息流 |
| 可选性 | **可选**，但推荐（尤其新系统） |
| 与 VFB 的关系 | 可建立映射（功能块 → SWC） |
| 产物 | 功能架构 ARXML（或需求文档 + 模型） |

**关键**：这一步**允许功能与软件组件不是一一对应**。一个功能可能拆成多个 SWC，多个功能可能合成一个 SWC。

### ② VFB System Description

> The VFB is an abstraction of the communication between software components. It provides a dedicated view of all the software components the system contains, **independent of any ECUs and networks**.
> —— `[TR_METH_01045]`

| 项 | 内容 |
|---|---|
| 视角 | 组件（"软件怎么分"），仍不含部署 |
| 内容 | SWC 实例、Port、Connector、接口定义 |
| 不含 | ECU、网络、总线、调度 |
| 产物 | VFB 系统描述 ARXML |

**这是"功能→软件"的第一次落地。**

### ③ System Description

> The VFB is refined into a system by defining a **topology of ECUs and networks** and **deploying software components to the ECUs**.
> Additionally, the **communication matrices**, which are required to interconnect the distributed features, are derived.
> —— `[TR_METH_01046]`

| 项 | 内容 |
|---|---|
| 新增 | ECU 列表、网络拓扑、SWC → ECU 映射、通信矩阵 |
| 关键决策 | **哪个 SWC 落在哪颗 ECU**（这是架构决策，影响成本/性能/线束） |
| 产物 | System Description ARXML（含 System Mapping） |

> [!important] 这一步是"功能"与"部署"的正式联姻
> 映射决定了：
> - 哪些 Connector 可实现为本地调用（仍需核对执行成本）
> - 哪些 Connector 变成 CAN 报文（要带宽、要延迟）
> - 哪些 Connector 变成以太网通信（要协议栈）
>
> **映射做错，后面所有优化都是在弥补架构错误。**

### ④ System Extract

> The primary organization hands over **System Extracts**, which represent the subsystems of the whole system. These subsystems contain **subsystem VFBs**, which are parts of the overall VFB.
> —— `[TR_METH_01047]`

| 项 | 内容 |
|---|---|
| 是什么 | 从整体系统里"切"出来给某个供应商的部分 |
| 谁产出 | OEM / 一级供应商 |
| 谁消费 | 下游供应商 |
| 内容 | 该子系统相关的 SWC、接口、连接（含跨边界连接） |

**这是 OEM 与供应商之间的正式接口契约。**

### ⑤ ECU Extract / ECU System Description

| 产物 | 谁产出 | 内容 |
|---|---|---|
| **ECU Extract** | 系统集成方 | 单颗 ECU 上需要的所有信息（SWC 实例、连接、BSW 需求） |
| **ECU System Description** | 供应商 | 把 OEM 给的 System Extract **转换成自己的结构** |

> Additionally, the software component structure of the System Extracts delivered by the primary organization can be **transformed into a different structure** for each ECU by the receiving organization (ECU System Description).
> In this case the System Extract of the primary organization can be considered as a **requirement** and the subsystem ... can be seen as a **solution**, which has to fulfill the delivered requirements.
> —— `[TR_METH_01049]`

> [!important] "要求 vs 方案"的比喻极精辟
> - OEM 给的 System Extract = **要求**（我要这些功能、这些接口）
> - 供应商的 ECU System Description = **方案**（我用这套 SWC 结构实现）
> - 两者结构可以**不同**，只要满足要求

### ⑥ ECU Configuration

| 输入 | 输出 |
|---|---|
| ECU Extract | 每个 BSW 模块的配置参数 |
| BSW 模块的配置规范（`TPS_ECUConfiguration`） | 配置 ARXML |

**包含三类配置**（→ [[01-配置三态]]）：

| 类型 | 绑定时间 | 例子 |
|---|---|---|
| Pre-compile | 编译前 | 是否启用开发错误检测 |
| Link-time | 链接时 | 配置结构体地址 |
| Post-build | 刷写后 | PDU 路由表、标定参数 |

### ⑦ Generate

| 生成物 | 生成器 | 依据 |
|---|---|---|
| `Rte_*.c/h` | RTE 生成器 | SWC 描述 + 映射 + 配置 |
| `*_Cfg.c/h` | BSW 配置生成器 | 各模块配置 |
| `*_PBcfg.c` | 后构建配置生成器 | 后构建参数 |

### ⑧ Build

编译链接，产出可执行文件。

### ⑨ Integration & Test

集成测试、HIL 测试、标定。

## 三、三种开发路径

方法论不是一个固定流程，而是三种可选路径：

### 路径 1：单阶段（OEM 自己做全部）

```
① → ② → ③ → ⑤ → ⑥ → ⑦ → ⑧ → ⑨
```

适用：OEM 自己做 ECU，或一级供应商全包。

### 路径 2：两阶段（OEM + 供应商）

```
OEM:      ① → ② → ③ → ④（System Extract）
                          ↓ 交付
供应商:                    ⑤ → ⑥ → ⑦ → ⑧
```

适用：主流整车开发模式。→ 详见 [[06-两阶段开发与OEM供应商分工]]

### 路径 3：子系统并行

```
OEM:  ① → ② → ③ ─┬→ ④a（子系统A）→ 供应商A
                   ├→ ④b（子系统B）→ 供应商B
                   └→ ④c（子系统C）→ 供应商C
```

> The development of the system can be achieved directly in one phase or in **several phases**.
> —— `[TR_METH_01046]`

## 五、为什么这条链能"自动化"

因为每个环节都被 SPEM 元模型形式化了：

| 元素 | 作用 | 例子 |
|---|---|---|
| **Task** | 可分配的工作单元 | "Configure BSW and RTE" |
| **Work Product** | 输入/输出产物 | "ECU Configuration" |
| **Role** | 谁做 | "ECU Integrator" |
| **Tool** | 用什么做 | "配置工具" |

→ 详见 [[02-SPEM元模型]]

**因为每个 Task 的输入输出都是明确定义的 ARXML，工具才能自动串起来。**

## 六、这条链在现实中会在哪断

| 断点 | 症状 | 后果 |
|---|---|---|
| ①→② 缺失 | 直接从需求跳到代码 | 功能与软件结构脱节 |
| ② 用 Excel 代替 | 接口靠文档约定 | 集成时接口不匹配 |
| ③ 映射靠拍脑袋 | 没评估通信负载 | 总线负载超 80%，后期返工 |
| ④ 交付物不完整 | Extract 缺跨边界连接 | 供应商反复问 OEM |
| ⑤ 供应商私自改结构 | 不满足 Extract 要求 | 集成失败 |
| ⑥ 配置手工改 | Cfg 文件被直接编辑 | 下次生成被覆盖，改动丢失 |
| ⑦ 生成物不入版本库 | 无法复现 | "上次能编过，这次不行" |

> [!warning] 最常见的一处断裂
> **手工修改生成代码（`Rte_*.c` 或 `*_Cfg.c`）。**
> 下次生成会覆盖，改动永久丢失，且没人知道曾经改过。
> **正确做法**：改配置源头，重新生成。
