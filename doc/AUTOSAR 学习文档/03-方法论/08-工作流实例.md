# 工作流实例：车轮速度系统

> [!tip] 结论
> AUTOSAR 官方给了一个**用于说明方法论的小案例**（是否可直接运行需另核对源码、工具和目标板）：电位器 → ADC → CAN → 计算 → LED。
> 它麻雀虽小五脏俱全：5 个 SWC、2 颗 ECU、2 个 System Extract、完整的 ARXML。
> **把这一个案例吃透，比读十份规范更有用。**

## 一、案例系统

### 功能描述（原文）

> The basis function of the system is that a **wheel speed** which is simulated by a **potentiometer**, converted by an **ADC** module of the **WheelSpeed ECU**, transmitted via **CAN** to the **VehicleSpeed ECU** and the calculated **vehicle speed** is indicated by **two LEDs** by a **DIO** module.

```
[电位器] ──模拟电压──▶ [WheelSpeed ECU]
                          ADC 采集
                             │
                             │ CAN 报文（轮速）
                             ▼
                      [VehicleSpeed ECU]
                         车速计算
                             │
                        DIO 输出
                             ▼
                        [LED1] [LED2]
```

### 组件构成（5 个 SWC）

> ...the function is defined by **five software components** in one system composition.
> Two **SensorActuatorSwComponentTypes** for the interaction with outer world,
> one **SwComponentType** for the internal calculation and
> two **EcuAbstractionSwComponentType** for the abstraction of the hardware.

| ECU | SWC | 类型 | 职责 |
|---|---|---|---|
| WheelSpeed | `CPT_WhlSpdSnsr` | SensorActuator | 轮速传感器信号处理 |
| WheelSpeed | `CPT_WhlSpdVirt` | EcuAbstraction | 抽象 ADC 硬件访问 |
| VehicleSpeed | `CPT_VehSpdCalc` | Application | 轮速 → 车速计算 |
| VehicleSpeed | `CPT_VehSpdActr` | SensorActuator | 车速 → LED 信号 |
| VehicleSpeed | `CPT_VehSpdVirt` | EcuAbstraction | 抽象 DIO 硬件访问 |

> [!important] 这个分解体现了清晰的职责分离
> - **EcuAbstraction SWC** 贴着硬件（ADC/DIO）
> - **SensorActuator SWC** 做"物理 ↔ 语义"转换
> - **Application SWC** 做纯计算
> - 中间通过 RTE 的 Port 连接，**没有任何组件知道对方在哪颗 ECU**

## 二、切分：从系统到两个 Extract

> The overall system composition is separated in two `SYSTEM_EXTRACT`s assigned each to a separate ECU.
> These `SYSTEM_EXTRACT`s are provided to **two different suppliers**.
> On the supplier side the `SYSTEM_EXTRACT` is imported and all required data are added to generate a sub-system for an ECU which will be later **integrated in the complete system by the original requester**.

```
          系统描述（OEM）
    ┌──────────────────────────┐
    │  TopLevelComposition     │
    │  ├─ WheelSpeed 子组合    │
    │  └─ VehicleSpeed 子组合  │
    └───────────┬──────────────┘
                │ 切分
        ┌───────┴────────┐
        ▼                ▼
  SystemExtract 1   SystemExtract 2
   → 供应商 A        → 供应商 B
   (WheelSpeed)      (VehicleSpeed)
        │                │
        ▼                ▼
   ECU 子系统 A      ECU 子系统 B
        └───────┬────────┘
                ▼
        集成回完整系统
```

> [!note] 这就是 [[06-两阶段开发与OEM供应商分工]] 的最小实例
> 一颗 ECU 一个 Extract，一个供应商。**责任边界 = 文件边界**。

## 三、两种设计方法（本节最重要）

官方明确给了 **top-down** 和 **bottom-up** 两条路，并说明第一版只交付了 top-down 的产物。

### 3.1 Top-Down：先定接口，再填实现

> The system designer of the "TopLevelComposition" can design the system in such a way that
> • **exchangeability on application side** and
> • **decoupling of data mapping between network architecture and application architecture**
> are achievable.
> He creates the "TopLevelComposition" based on the `RootSwCompositionPrototype` and references the `CompositionSwComponentType` as the top-level software composition.

**关键做法**：

> The `RootSwComposition` will usually **not contain all atomic software components** that are used in a complete VFB system.
> **Instead, the focus is on the interfaces between the components or whole compositions.**
> The system design could even contain **only compositions and their ports**.

> An essential aspect of this architectural approach is to **decouple the DataMapping of the network communication from that of the implemented applications**.
> The `PortPrototype`s realizing the network communication are defined at the "TopLevelComposition".
> The corresponding DataMapping, implemented by the subclass `SenderReceiverToSignalMapping`, is also defined referring to the **outer PortPrototypes**.

```
TopLevelComposition
├── 外部 Port（绑定到 CAN 信号）  ← 网络通信在这里定义
│       │ delegation（委托）
│       ▼
└── 内部 Port（组件真实接口）      ← 应用架构在这里定义
```

> From a VFB based point of view the **outer PortPrototypes are delegated to the inner PortPrototypes**.

**收益**：

> The benefit of the described design approach is that actually the **software component architecture inside the root composition can be changed without affecting the DataMappings and thus the network definition**.
> Therefore the **supplier of the embedded software compositions or software components can act independently**.

| 收益 | 机制 |
|---|---|
| **应用可换** | 内部结构变了，外部 Port 不变 |
| **网络定义稳定** | DataMapping 绑在外部 Port 上，不受内部变化影响 |
| **供应商独立** | 供应商改内部实现，不需要 OEM 改系统描述 |

> [!important] 这就是"委托（Delegation）"的威力
> 外部 Port 是一个"插座"，内部 Port 是"电器"。
> 换电器只要插头一样就行，墙上的插座不用动。

### 3.2 Bottom-Up：先有组件，再往上组

> The system design is created bottom-up.
> In order to assemble applications from AUTOSAR components (`AtomicSwComponentType`), **compositions can be build up hierarchically**, until the outermost `CompositionSwComponentType` forms a kind of top-level composition.
> This mainly bases on `[constr_3031]`, which tells that the unique feature of the complete system description is, that it **doesn't have any outside ports**, but all the software components contained in it are **connected to each other (`AssemblySwConnector`)**.

```
第一步：原子组件
  [SWC A]  [SWC B]  [SWC C]

第二步：组装成子组合
  ┌─────────────────┐
  │ Comp1: A ──▶ B  │
  └─────────────────┘

第三步：再往上组
  ┌───────────────────────────┐
  │ Comp2: Comp1 ──▶ C        │
  └───────────────────────────┘

第四步：顶层组合（无外部端口，全部内部连接）
```

> [!tip] 两种方法怎么选
> | | Top-Down | Bottom-Up |
> |---|---|---|
> | 起点 | 系统接口、网络矩阵 | 已有组件/复用组件 |
> | 适合 | OEM 主导、多供应商 | 供应商内部、平台复用 |
> | 接口稳定性 | 高（先冻结） | 低（随组装变化） |
> | 变更影响 | 内部变化不外溢 | 变化可能影响上层 |
> | 与本库用户偏好 | — | 可用于已有组件复用；不假定用户固定采用此工作习惯 |
>
> **实践中常常混用**：OEM 用 top-down 定边界，供应商在边界内用 bottom-up 组装。

## 四、这个案例能学到什么

### 4.1 完整链路走一遍

| 步骤 | 产物 | 对应文档 |
|---|---|---|
| 1. 功能定义 | 功能框图（电位器→车速→LED） | [[03-抽象系统描述]] |
| 2. 组件设计 | 5 个 SWC + Port | [[10-软件组件SWC九种类型]] |
| 3. 组合与连接 | TopLevelComposition | [[03-虚拟功能总线VFB]] |
| 4. 系统描述 | System（category = SYSTEM_DESCRIPTION） | [[04-VFB系统描述与系统设计]] |
| 5. 切分 | 2 个 SYSTEM_EXTRACT | [[05-SystemExtract与ECUExtract]] |
| 6. 供应商开发 | ECU 子系统 | [[06-两阶段开发与OEM供应商分工]] |
| 7. 集成 | 完整系统 | — |

> 原文注：`The category property of System shall indicate the role of this work product. Here the category SYSTEM_DESCRIPTION is used. See [TPS_SYST_01003]`

### 4.2 一个容易忽略的细节：System 的 category

`System` 元素有个 `category` 属性，标明这份描述的角色：

| category 值 | 含义 |
|---|---|
| `SYSTEM_DESCRIPTION` | 完整系统描述（OEM 产出） |
| `SYSTEM_EXTRACT` | 子系统切片（给供应商） |
| `ECU_EXTRACT` | 单 ECU 物料清单 |

**同一个元模型类，用 category 区分角色。** 这是 AUTOSAR 复用的典型手法。

### 入门示例的文件结构（值得照抄）

```
30_MeasurementCalibration/10_Introductory/
├── model/
│   ├── ApplicationDataTypes.arxml    # 应用数据类型
│   ├── PlatformTypes.arxml           # 平台类型 → C 类型
│   ├── CompuMethods.arxml            # 换算方法
│   ├── UnitsAndPhysicalDimensions.arxml
│   ├── PortInterfaces.arxml          # 端口接口
│   ├── SwcController.arxml           # SWC 定义
│   ├── SwcComposition.arxml          # 组合与连接
│   ├── DataTypeMappings.arxml
│   ├── SwAddrMethods.arxml           # 标定访问方式
│   ├── EcucConf.arxml                # ECU 配置
│   └── FlatMap.arxml                 # 扁平映射
└── gen/
    └── Rte_McSupportData.arxml       # 生成的 RTE 描述
```

> [!tip] 学习建议
> 1. 先用文本编辑器打开 `SwcController.arxml`，对照 [[07-ARXML产物格式]] 的解剖表读一遍
> 2. 再看 `SwcComposition.arxml`，理解"类型 vs 实例"
> 3. 最后看 `System.arxml`，理解"部署"
> 4. 如果有工具（如 Arctic Core、ETAS ISOLAR），导入试一遍

## 六、把案例映射到 BCM

假设用同样的思路设计"车灯控制"：

| 案例中的角色 | BCM 的对应 |
|---|---|
| 电位器（轮速输入） | 灯光开关 / 环境光传感器 |
| ADC 采集 | ADC 采集开关电压 / 光照 |
| WheelSpeed ECU 的 SensorActuator | `LightSwitchAcq`（开关采集） |
| CAN 传输 | CAN 报文（开关状态广播） |
| VehicleSpeed ECU 的 Application | `LightLogic`（灯光逻辑决策） |
| DIO 输出 LED | PWM 输出驱动车灯 |
| 两颗 ECU | 若单 ECU，则全在一个系统里 |

### 关键差异

| 差异点 | 案例 | BCM 实际 |
|---|---|---|
| ECU 数量 | 2 颗 | 1 颗（BCM 自身） |
| 通信 | 简单 CAN | 多报文／协议待实际矩阵确认 |
| 输出 | 2 个 LED（DIO） | PWM 调光 + 高边驱动 + 诊断 |
| 诊断 | 无 | UDS + DTC |
| 睡眠 | 无 | 必需（暗电流要求） |
| 变体 | 无 | 多车型配置 |

> [!important] 不要被"案例太简单"误导
> 案例的价值在于**结构**，不在于规模。
> 将它扩展到多报文、多路 PWM、完整诊断，结构是一样的 —— 只是组件更多、配置更复杂。
> **先在小案例上把结构走通，再放大到真实项目。**
