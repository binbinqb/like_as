# 标准化边界：什么进标准，什么不进

> [!note] 项目上下文
> 未经本轮实际工程输入验证的“现状”、器件、数量和工具信息，均按示例或待确认假设阅读；不代表已审查 SDK、原理图、DBC 或现有业务代码。


> [!tip] 结论
> AUTOSAR 的标准化有一条清晰的判据：**应用接口参考分解重视跨供应商边界；这不能推广为 AUTOSAR 所有标准化对象的唯一判据。**
> 组织内部可按供应商自己的稳定接口规范组织，因为标准化的代价是冻结自由度。

这条判据解释了大量看似"标准没管到"的空白，也解释了为什么 AUTOSAR 既庞大又留白。

## 一、官方说得很直白

`EXP_AIBodyAndComfort` 在定义车身域分解时，写了一段极其坦诚的话：

> The intent is for the decomposition to get **not to atomic SW-Cs but to "purchasable" SW-Cs** ...
> These SW-Cs will be obtained as a unit so that all the internal (and hence **not AUTOSAR standardized**) interfaces are controlled by a single vendor, even if there are SW-Cs within the bought unit that reside on different ECUs.
> **All interfaces between SW-Cs from different vendors should be standardized.**
> —— EXP_AIBodyAndComfort, 2.1 Objectives

拆出三层信息：

| 层级 | 是否标准化 | 理由 |
|---|---|---|
| **跨供应商** 的接口 | 参考文档建议标准化，强度不得将 should 改成 shall | 否则无法集成 |
| **供应商内部** 的接口 | 保留具体实现自由，也可以制定内部标准 | 保留供应商实现自由度 |
| 分解粒度 | 到"可采购单元"为止 | 再细就是供应商内部事务 |

> [!important] "purchasable" 这个词是钥匙
> 分解粒度不是由技术决定的，是由**采购合同**决定的。
> 这解释了为什么车身域的 `CentralLocking` 是一个大的组合，而不是拆成 20 个原子组件——
> 参考文档以可采购边界说明分解意图，实际采购范围由项目决定。

## 二、标准化边界的四个层次

把 AUTOSAR 的标准化对象按"冻结程度"排一下：

| 层次 | 标准化的对象 | 冻结程度 | 例子 |
|---|---|---|---|
| **1. 语法层** | 文件格式、元模型 | 完全冻结 | ARXML Schema、`TPS_*Template` |
| **2. 语义层** | 接口的含义、行为 | 强约束（SHALL） | `SWS_*` 的功能需求、API 语义 |
| **3. 结构层** | 分层、模块划分 | 框架冻结，细节可扩 | 四层架构、模块列表 |
| **4. 实现层** | 具体代码怎么写 | **不冻结** | 内部数据结构、算法、私有函数 |

**关键**：内部实现仍受规范行为、资源与集成约束，并非绝对自由。

> [!note] 这解释了"SWS 为什么那么厚"
> 因为 SWS 主要在冻结第 2 层（语义）。每个 API 的前置条件、后置条件、错误码、时序、状态机都要写死，
> 才能保证 A 家的 COM 和 B 家的 PduR 能拼在一起。

## 三、为什么"过度标准化"是灾难

| 过度标准化的后果 | 机制 |
|---|---|
| **抑制创新** | 一旦冻结，改进要等下一个 release（一年一次） |
| **规范膨胀** | 每个细节都要写清楚，文档从 100 页涨到 1000 页 |
| **实现僵化** | 供应商无法针对自己的硬件优化 |
| **兼容负担** | 一旦发布就不能改，只能加 |

AUTOSAR 的应对策略是**分层冻结 + 明确留白**：

```
┌────────────────────────────────────────┐
│ 可扩展区（厂商差异化）                    │  ← Vendor specific
├────────────────────────────────────────┤
│ 可选区（MAY / OPTIONAL）                 │  ← 配置决定
├────────────────────────────────────────┤
│ 强制区（SHALL / SHALL NOT）              │  ← 标准冻结
└────────────────────────────────────────┘
```

## 四、三类"留白"及其用途

AUTOSAR 故意留了三种口子，用途完全不同：

### 留白 1：Complex Driver（结构性留白）

> non-standard modules can be integrated into AUTOSAR-based systems as Complex Drivers
> **further layers cannot be added**

| 特点 | 说明 |
|---|---|
| 位置 | 明确的（ECU Abstraction 与 MCAL 之间，可访问硬件） |
| 用途 | 标准模块无法实现的功能（特殊时序、专有协议） |
| 代价 | 失去可移植性 |
| 判据 | **"标准模块组合真的做不到吗？"** |

### 留白 2：Vendor Specific 配置项（参数性留白）

SWS 里大量参数标着 `[Vendor specific]`，含义是"标准不管，厂商自己定"。

| 用途 | 例子 |
|---|---|
| 性能调优 | 队列深度、缓冲区大小 |
| 硬件适配 | 特定 MCU 的优化开关 |
| 差异化功能 | 厂商增强的调试能力 |

### 留白 3：Standardized Interface 的边界（接口性留白）

> When software modules communicate through a "standardized interface", it is **NOT possible any more to route the communication** between the software-modules through a network.

含义：**此处是特指不使用 AUTOSAR Interface 技术的 Standardized Interface，不能泛指所有 C 函数**。这是一个有意的取舍：

| 选择 | 得到 | 失去 |
|---|---|---|
| 用 Standardized Interface | 简单、快、无序列化开销 | 不能跨 ECU |
| 用 AUTOSAR Interface | 可跨 ECU、可重定位 | 需要 RTE、有开销 |

## 五、判据表：一个东西该不该进标准

用这五个问题判断：

| # | 问题 | 若"是" | 若"否" |
|---|---|---|---|
| 1 | 会跨越组织边界吗？（OEM↔供应商、供应商↔供应商） | 倾向标准化 | 不必标准化 |
| 2 | 有多家实现需要互操作吗？ | 必须标准化 | 可不标准化 |
| 3 | 换实现会影响到别人吗？ | 必须标准化 | 自由 |
| 4 | 标准化后会不会抑制关键创新？ | 谨慎，只冻结必要部分 | 可以标准化 |
| 5 | 不标准化的集成成本由谁承担？ | 由集成方承担 → 往往被迫标准化 | 由实现方承担 → 不必 |

> [!tip] 用这个表看你的项目
> `hal_can.h` 的接口该不该冻结？
> 1. 会跨组织边界吗？（如果 SDK 由第三方提供）→ 是
> 2. 有多家实现吗？→ 未来可能有（换 MCU）
> 3. 换实现影响别人吗？→ 是（上层全受影响）
> → **应该标准化并冻结**，这正是你 `hal_*.h` 零 SDK 依赖的设计意图。

## 六、AUTOSAR 没标准化的东西（清单）

反向清单同样有价值，它告诉你"这些事得自己定"：

| 未标准化 | 原因 | 你要自己定 |
|---|---|---|
| 应用层功能分解 | 各 OEM 功能定义不同 | BCM 该拆成哪些功能模块 |
| 内部算法 | 商业机密 | 灯光渐变曲线、雨刮间歇算法 |
| 内存布局细节 | 与 MCU/链接器强相关 | 链接脚本、段分配 |
| 任务划分与优先级 | 与具体时序需求相关 | OS Task 设计 |
| 调度表 | 与整车时序相关 | 主函数周期、偏移 |
| 诊断故障码含义 | OEM 自定义 | DTC 定义、清除条件 |
| 标定参数含义 | 各项目不同 | A2L 定义 |
| 测试方法 | 不在标准范围 | 单元测试、HIL 用例 |

> [!warning] 最常见的误区
> 以为"用了 AUTOSAR，架构就自动好了"。
> 事实：**AUTOSAR 只保证了"接口能对接"，不保证"分解合理"。**
> 一个糟糕的 SWC 分解 + 完美的 AUTOSAR 实现 = 一个难以维护的系统。
> 分解质量靠架构能力，不靠标准 → [[02-车身域标准SWC分解]] 是少数给了参考答案的地方。
