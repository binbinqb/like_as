# 第一性原理：功能与部署解耦

> [!tip] 结论
> AUTOSAR 的本文采用的主要理解视角是：**把"功能是什么"和"功能跑在哪"分开描述，中间靠生成代码缝合。**
> 官方把这个能力叫 **relocatability（可重定位性）**。分层、VFB、RTE、ARXML、方法论，全是这一条的实现手段或配套设施。

## 一、两组视图：同一套系统的两个"投影"

`TR_VFB` 开篇给出的世界观，是整个标准的地基：

> In AUTOSAR, an application is modeled as a composition of interconnected components.
> The "virtual functional bus" is the communication mechanism that allows these components to interact.
> The components are mapped on specific system resources (ECUs).
> —— TR_VFB, Chapter 2

它定义了**两个必须同时存在、但彼此独立的视图**：

| | VFB 视图（功能视图） | ECU 视图（实现视图） |
|---|---|---|
| **描述什么** | 有哪些组件、组件之间传什么 | 这些组件跑在哪颗 MCU 上、走哪条总线 |
| **谁关心** | 功能架构师 / 系统工程师 | ECU 集成工程师 / 供应商 |
| **产物** | VFB System Description | ECU Extract + 配置 |
| **稳定性** | 相对稳定（功能不常变） | 频繁变化（换硬件、换网络、换车型） |
| **变更影响** | 小 | 大 |

> [!important] 关键洞察
> 现实工程中，**功能变更慢、部署变更快**。
> 如果不分离，每次部署变更都会污染功能代码——这就是传统开发"改一个硬件方案要动全部业务逻辑"的病根。
> 分离的目标是尽量限制部署变更对业务源码的影响；仍须检查时序、硬件能力、数据和服务约束。

## 二、解耦在标准里是怎么被强制的

不只是"建议分离"，而是靠三条硬机制：

### 机制 1：组件只能通过 Port 说话

组件类型（`ApplicationSwComponentType`）**没有**任何"我是 CAN 节点""我的寄存器地址是 0x4000"这类信息。它只有 Port。

> A port always belongs to exactly one component and represents a point of interaction between a component and other components.
> —— TR_VFB, 3.1 Components

组件的实现（C 代码）里，读数据是 `Rte_Read_xxx()`，写数据是 `Rte_Write_xxx()`。**它永远不知道数据从哪来**。

### 机制 2：连接器的实现由映射决定，不由组件决定

同一个 Connector（连接两个组件的线），在不同映射下会生成完全不同的代码：

| 映射情况 | RTE 生成什么 | 组件代码是否变化 |
|---|---|---|
| 两个组件在同 ECU、同分区 | 直接内存拷贝 / 函数调用 | 不变 |
| 两个组件在同 ECU、不同 Task | 加临界区保护 / 队列 | 不变 |
| 两个组件在不同 ECU、走 CAN | 调 Com / PduR / CanIf 全套 | 不变 |
| 两个组件在不同 ECU、走以太网 | 调 SoAd / TcpIp / EthIf | 不变 |

> The RTE must provide a complete environment for the component.
> —— TR_VFB, 3.8

**这就是 RTE 存在的唯一理由**：把"连接"这件部署相关的事，全部吸收到自己身上。

### 机制 3：绑定时间可推迟（Late Binding）

标准允许连接关系在**不同阶段**才确定：

| 绑定时间 | 什么时候定 | 灵活性 | 代价 |
|---|---|---|---|
| Pre-compile | 编译前 | 最低 | 无运行时开销 |
| Link time | 链接时 | 中 | 间接寻址 |
| Post-build | 刷写后 / 运行时 | 最高 | 查表 + 指针解引用 |

→ 详见 [[01-配置三态]]

## 三、代价：解耦不是免费的

这是很多教材不讲的，但对做工程决策至关重要。

| 代价 | 具体表现 | 缓解手段 |
|---|---|---|
| **间接层开销** | 一次信号读取从"读变量"变成"函数调用 + 可能加锁" | 同 Task 同核时 RTE 生成直接访问；按合法映射优化关键路径；跨分区按规定使用 IOC |
| **代码体积膨胀** | RTE 生成代码 + 配置表占 Flash/RAM | 裁剪未用特性；ICC1 一致性类 |
| **调试变难** | 看不到"谁调用了我"，调用链藏在生成代码里 | 保留 RTE 生成物并纳入版本管理；用 DLT/日志 |
| **工具链强依赖** | 没有配置工具几乎无法手工维护 ARXML | 小项目用"手写等价物"（见 [[03-Mini-AUTOSAR分层映射]]） |
| **学习曲线** | 概念多、术语多、抽象层级多 | 本库存在的意义 |

> [!warning] 判断标准
> **解耦的价值 ∝ 部署变更的频率 × 系统规模。**
> - 单 ECU、功能稳定、一辈子不换硬件 → 解耦收益低，AUTOSAR 反而是负担
> - 多 ECU、多车型、多供应商、生命周期 10 年 → 解耦收益巨大，AUTOSAR 是必需品
>
> BCM 属于后者：一个平台要覆盖多个车型配置（高低配差异），所以值得。

## 四、一个反直觉的推论：组件应该"不知道自己被复用"

`TR_VFB` 里有个细节常被忽略：

> AUTOSAR supports multiple instantiation of components. This means that there can be 2 of the same component in a vehicle system...
> These components will typically have their own separate internal state (stored in separate memory locations) but might for example share the same code.
> —— TR_VFB, 3.1

含义：**组件代码必须是"可重入 + 状态外置"的**。

| 写法 | 是否符合 | 原因 |
|---|---|---|
| 函数内 static 状态 | 单实例可以；多实例需独立上下文 | 只有确实使用多实例时才必须避免共享该状态 |
| 状态放在 RTE 管理的实例内存里，通过 `Rte_` API 访问 | ✅ | 每个实例独立 |
| 用 `Rte_Instance` 句柄区分实例 | ✅ | 标准支持多实例 |

这条直接对应 [[03-RTE生成与Runnable映射]] 里的 Runnable 设计约束。

## 五、落到 BCM：你的代码该怎么切

用这条第一性原理去审视现有 BCM 代码，只问一个问题：

> **这段代码，如果换一颗 MCU 或换一套通信矩阵，需要改吗？**

| 代码片段 | 需要改吗 | 归属层 |
|---|---|---|
| `GPIO_SetPin(PORT_A, 5)` | 换 MCU 要改 | MCAL / HAL 平台实现 |
| `if (light_sw == ON) { lamp_on(); }` | 不需要改 | 应用层 |
| `msg.data[0] = (uint8_t)(brightness & 0xFF)` | 换矩阵要改 | 通信层（COM / Signal Binding） |
| `switch (vehicle_mode) { case SLEEP: ... }` | 不需要改 | 应用层 / 模式管理 |
| `NvM_WriteBlock(BLK_CFG, &cfg)` | 不需要改 | 应用层（通过 NvM 接口） |
| `FLASH_Program(addr, data)` | 换 MCU 要改 | MCAL |

**凡是"要改"的，都不该出现在应用层。** 这就是分层的判据，比背定义有用得多。
