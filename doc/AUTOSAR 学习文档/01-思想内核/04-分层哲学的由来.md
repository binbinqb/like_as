# 分层哲学的由来

> [!tip] 结论
> AUTOSAR 分层的依据**不是功能分类，而是"变化源分类"**。
> 每一层负责吸收一种特定的变化，让上层对这类变化免疫：
>
> | 层 | 吸收的变化 |
> |---|---|
> | MCAL | 换 MCU 型号 |
> | ECU Abstraction | 换板级硬件布局 |
> | Services | 与硬件无关、但要平台能力 |
> | RTE | 换个部署方案（本地↔远程） |
> | Complex Drivers | 标准表达不了的东西 |

背定义只能记住"有哪几层"，理解变化源才能判断"这段代码该放哪层"。

## 一、官方给的两种视图

`EXP_LayeredSoftwareArchitecture` 从粗到细给了三个视图：

### Top view（最高抽象）

```
┌─────────────────────────────┐
│      Application Layer      │
├─────────────────────────────┤
│  Runtime Environment (RTE)  │
├─────────────────────────────┤
│     Basic Software (BSW)    │
├─────────────────────────────┤
│        Microcontroller      │
└─────────────────────────────┘
```

> The AUTOSAR Architecture distinguishes on the highest abstraction level between three software layers: Application, Runtime Environment and Basic Software which run on a Microcontroller.

### Coarse view（四层 BSW）

```
        Application
             ↕
            RTE
             ↕
   ┌─────────────────┐
   │  Services Layer │
   ├─────────────────┤
   │ ECU Abstraction │    ← Complex Drivers 贯穿 ECU Abstraction 与 MCAL
   ├─────────────────┤
   │      MCAL       │
   └─────────────────┘
        Microcontroller
```

### Detailed view（按功能域再切）

BSW 每层再按功能域切：

| 层 | 功能域 |
|---|---|
| Services | System Services / Memory Services / Communication Services / Off-board Communication Services / Crypto Services |
| ECU Abstraction | I/O HW Abstraction / Memory HW Abstraction / Communication HW Abstraction / Onboard Device Abstraction / Crypto HW Abstraction |
| MCAL | Microcontroller Drivers / Memory Drivers / I/O Drivers / Communication Drivers / Wireless Communication Drivers / Crypto Drivers |

> [!note] 分层是二维的
> **纵向是抽象层次，横向是功能域。**
> 同一功能域跨越多层：CAN 在 MCAL 是 CanDrv，在 ECU Abstraction 是 CanIf，在 Services 是 CanTp/CanSM/ComM。
> 看架构图时要同时看两个维度，否则会问"CanIf 到底算哪层"——它既是通信域，又在 ECU 抽象层。

## 二、每层到底在"吃什么变化"

这是本库最重要的分析视角。

### MCAL：吸收 MCU 差异

> `[SRS_BSW_00161]` The AUTOSAR Basic Software shall provide a microcontroller abstraction layer which provides a standardized interface to higher software layers.
> **Rationale**: Portability and reusability. Encapsulate implementation details of a specific microcontroller from higher software layers.
> **Use Case**: Exchange microcontroller ST10 with STAR12 without affecting higher software layers.

| 特征 | 说明 |
|---|---|
| 里面有什么 | 寄存器操作、中断使能、DMA 配置、时钟树 |
| 职责边界 | 不放产品业务策略；驱动本身可以有作业状态机、数据格式处理与错误判断 |
| 换 MCU 时 | 优先限制硬件相关代码变更，同时检查启动／链接／OS port／板卡资源与时序 |
| 接口特点 | 标准化（`Adc_ReadGroup`、`Spi_WriteIB` 等），与具体 MCU 无关 |

**判据**：这段代码里出现寄存器名、地址常量、厂商头文件 → 属于 MCAL。

### ECU Abstraction：吸收板级差异

> `[SRS_BSW_00162]` ...a hardware abstraction layer which provides a stable interface to higher software layers which is **independent from the ECU hardware layout**.
> **Use Case**: Change the hardware layout of the ECU (e.g. **PortA.5 → PortD.7**) without affecting software layers interfacing with the hardware abstraction layer.

| 特征 | 说明 |
|---|---|
| 里面有什么 | 通道映射、外部器件驱动（外置 EEPROM、SBC、外部看门狗） |
| 核心价值 | 板子改了（引脚挪了、换了个外部芯片），上层不动 |
| 典型模块 | IoHwAb、CanIf、LinIf、MemIf、Fee、外部收发器驱动 |
| 判断依据 | **依赖"板子怎么画的"，但不依赖"MCU 是什么"** |

> [!important] 最容易被忽视的一层
> 很多项目把 ECU Abstraction 和 MCAL 合并，结果"换个引脚定义要改业务代码"。
> `PortA.5 → PortD.7` 这个例子看着简单，它保护的正是**硬件工程师改板、软件不用改**这个能力。
> 详见 [[03-ECU抽象层]]。

### Services：提供与硬件无关的平台能力

> The Services Layer ... offers: Operating system functionality, Vehicle network communication and management services, Memory services (NVRAM management), Diagnostic Services (UDS, error memory), ECU state management, mode management, program flow monitoring.
> **Properties**: Implementation: mostly µC and ECU hardware **independent**.

| 特征 | 说明 |
|---|---|
| 里面有什么 | OS、COM、DCM、DEM、NvM、EcuM、BswM、WdgM、DET |
| 核心价值 | 这些能力"每个 ECU 都需要"，且与硬件无关，所以标准化 |
| 上层接口 | 完全硬件无关 |

**判据**：这个功能是不是"任何 ECU 都可能要用、且与具体硬件无关"？是 → Services。

### Complex Drivers：吸收"标准表达不了"的东西

> `[SRS_BSW_00164]` Only the Operating System, complex drivers and modules of the microcontroller abstraction layer are allowed to implement interrupt service routines.

这是标准留的**唯一合法后门**，但它有严格约束：

| 允许 | 不允许 |
|---|---|
| 实现 ISR | 被应用层直接调用（应通过 RTE 或标准接口） |
| 直接访问硬件 | 绕过 MCU 抽象去做本可以标准化的事 |
| 满足特殊时序（如电机 FOC、特殊协议） | 成为"懒得设计"的垃圾桶 |

> [!warning] CDD 是技术债，不是设计自由
> CDD 的移植成本取决于硬件相关范围，需量化评估，不能一律视为可移植性归零。判断标准：
> **"这个功能是否真的无法用标准模块组合实现？"**
> 同时评估迁移、特殊时序和资源约束；CDD 不是仅在理论上完全无法组合标准模块时才可使用。详见 [[06-复杂驱动CDD]]。

### RTE：吸收部署差异

RTE 不在 BSW 层里，它**横跨**在应用与 BSW 之间：

> The RTE is a layer providing communication services to the application software.
> **Above the RTE the software architecture style changes from "layered" to "component style".**
> **Task**: Make AUTOSAR Software Components **independent from the mapping to a specific ECU**.

这句话是理解 AUTOSAR 的钥匙 → 展开见 [[05-组件风格与分层风格的分界]]。

## 三、纵向规则：谁能调谁

`EXP_LayeredSoftwareArchitecture` 的 "General Interfacing Rules" 给了明确约束：

### 纵向（跨层）

| 规则 | 说明 |
|---|---|
| 一层可以访问其**正下方**一层所有接口 | 正常调用 |
| **应避免**跳过一层 | 性能原因可接受，但要记录 |
| **禁止**跳过两层或以上 | 架构红线 |
| **禁止**绕过 MCAL | 绝对红线 |
| 模块可访问**其他功能域**的下层模块 | 例如外部 EEPROM 驱动用 SPI |
| 所有层都可访问 System Services | 例外通道（如 DET、Dem） |

### 横向（同层）

| 层 | 横向接口 |
|---|---|
| Services | ✅ 允许（如 DEM 用 NvM 存故障） |
| ECU Abstraction | ✅ 允许（CDD 可用其他 BSW 模块） |
| **MCAL** | ❌ **禁止硬编码横向接口**，只能用可配置通知（callback） |

> `[SRS_BSW_00005]` Modules of the µC Abstraction Layer (MCAL) may not have hard coded horizontal interfaces. Necessary interactions (e.g. GPT triggered ADC conversion) shall be implemented by using **statically configurable notifications (callbacks)**.
> **Rationale**: Avoidance of strong coupling, ease of integration, better structure.

> [!tip] 为什么 MCAL 禁止横向调用
> 如果 Adc 直接调 Gpt，两者就焊死了：换一个 GPT 实现要改 ADC。
> 用回调（配置时指定函数指针），依赖关系从"代码级"降级为"配置级"，耦合大幅降低。
> **这条对你的 HAL 层设计有直接指导意义** → [[03-Mini-AUTOSAR分层映射]]

完整规则展开见 [[09-横向纵向接口规则]]。

## 四、分层的"物理证据"：接口类型

判断一个模块属于哪层，最硬的办法是看它对外用什么接口：

| 接口类型 | 谁用 | 是否可跨网络 | 典型 |
|---|---|---|---|
| AUTOSAR Interface | 应用组件之间 | ✅ 可以 | SWC 之间的 Port |
| Standardized AUTOSAR Interface | 应用访问 BSW 服务 | ✅ 理论上可以 | NvM、Dem、Dcm 服务端口 |
| Standardized Interface | BSW 模块之间 | ❌ **不能** | `Adc_ReadGroup()`、`Can_Write()` |

> A "Standardized Interface" ... Because of this, "standardized interfaces" are typically used between software-modules which are **always on the same ECU**.
> When software modules communicate through a "standardized interface", it is **NOT possible any more to route the communication** between the software-modules through a network.

**推论**：看到 `Std_ReturnType Xxx_Yyy(...)` 这种 C 函数签名 → 一定是 Standardized Interface → 只能同 ECU → 说明这是 BSW 内部或 BSW 到 RTE 的边界。

展开见 [[08-三种接口类型]]。

## 五、五条容易踩线的判据

| 现象 | 违反了哪条 | 正确做法 |
|---|---|---|
| 应用层 `#include "MCU_regs.h"` | 绕过 MCAL | 通过 IoHwAb / RTE Port |
| HAL 层里写 `if (speed > 100)` 业务判断 | 层次污染 | 判断上移到应用 |
| MCAL 模块互相直接调用 | MCAL 禁止横向 | 用配置回调 |
| 为了"复用"在 BSW 和 App 之间加一层 | 不允许新增层 | 归入 ECU Abstraction 或 CDD |
| 应用层直接实现 ISR | `[SRS_BSW_00164]` | ISR 放 MCAL/CDD，通过 RTE 通知 |

## 六、自检

1. `Fee`（Flash EEPROM Emulation）属于哪层？为什么不是 MCAL？
2. 一个外置 SPI 接口的 EEPROM 驱动该放哪层？它调用了谁？
3. 为什么允许"所有层访问 System Services"，这不会破坏分层吗？

> 提示：第 1 题想"它依赖 MCU 还是依赖板子"；第 3 题想"System Services 提供的是什么性质的能力"。
