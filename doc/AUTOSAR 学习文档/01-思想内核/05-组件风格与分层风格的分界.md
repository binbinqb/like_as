# 组件风格与分层风格的分界

> [!note] 项目上下文
> 未经本轮实际工程输入验证的“现状”、器件、数量和工具信息，均按示例或待确认假设阅读；不代表已审查 SDK、原理图、DBC 或现有业务代码。


> [!tip] 结论
> AUTOSAR 是**两套架构风格拼起来的**：RTE 以下是"分层"，RTE 以上是"组件"。
> 分界线不是随意的——**两种视角服务于不同职责；不能将它们理解成软件设计上普遍互斥的风格**。

## 一、官方原话里的转折

`EXP_LayeredSoftwareArchitecture` 在讲 RTE 时用了一句极其关键的话：

> **Above the RTE the software architecture style changes from "layered" to "component style".**

这句话藏着一个设计决断：AUTOSAR 没有强行把应用也塞进分层里，而是**承认两种风格并存，并划出边界**。

## 二、两种风格的对照

| 维度 | 分层风格（Layered） | 组件风格（Component） |
|---|---|---|
| **调用依据** | "你在我下面，所以我能调你" | "我需要这个能力，通过端口申请" |
| **依赖方向** | 依赖**具体的层** | 依赖**抽象的接口** |
| **变化时的影响** | 层次调整 → 大量代码要改 | 换实现 → 只换绑定的组件 |
| **可见性** | 知道自己上下是谁 | 只知道接口，不知道对端是谁 |
| **复用方式** | 整层复用 | 单组件复用 |
| **典型代表** | BSW（MCAL/ECU Abstraction/Services） | SWC（应用组件） |
| **AUTOSAR 里的接口** | Standardized Interface（C 函数） | AUTOSAR Interface（Port） |

## 三、为什么不能统一成一种

### 假设"全用分层"

应用组件就会变成"最上面那一层"，于是：

| 问题 | 后果 |
|---|---|
| 组件必须知道自己在第几层 | 换个部署位置就要改代码 |
| 组件必须知道自己下面是谁 | 无法跨 ECU 复用（跨 ECU 时"下面"完全不同） |
| 层与层之间是固定的 | 无法支持一个组件被多个组合复用 |
| 无法表达"1 个发送者 → N 个接收者" | 分层是"上下"关系，不是"发布订阅"关系 |

**致命点**：分层的隐含前提是"**我上面的代码运行在我下面代码的同一台机器上**"。一旦跨 ECU，这个前提就崩了。

### 假设"全用组件"

BSW 就会变成"一堆组件"，于是：

| 问题 | 后果 |
|---|---|
| 每个驱动都要建模成组件 | 巨大的配置负担，为 3 行寄存器代码写一套 ARXML |
| 组件支持同步／异步等交互，不能只按异步解释 | 驱动需要确定性时序，事件模型不匹配 |
| 组件间通过 RTE 通信 | 每次读寄存器都要过一遍 RTE，性能不可接受 |
| ISR 无法用组件表达 | 中断是分层世界里的事 |

**致命点**：组件的抽象成本高，而**驱动是高频、低延迟、强时序**的，抽象不起。

### 所以：按"变化频率 + 调用频率"切

| 判据 | 结论 |
|---|---|
| 调用频率极高、延迟敏感 | 用分层，直接函数调用 |
| 功能逻辑复杂、变化频繁 | 用组件，通过端口解耦 |
| 需要跨 ECU 复用 | 必须是组件 |
| 需要精确时序控制 | 结合硬件、驱动与调度预算设计；应用 Runnable 也有时序需求 |

## 四、RTE 就是那个"翻译官"

RTE 的职责可以精确描述为：**把组件风格的请求，翻译成分层风格的调用**。

| 组件侧（声明） | RTE 生成的动作 | BSW 侧（执行） |
|---|---|---|
| `Rte_Write_Port_Signal(v)` | 若本地：写共享变量 / 调用接收 Runnable | 直接内存操作 |
| `Rte_Write_Port_Signal(v)` | 若远程：调 `Com_SendSignal()` | Com → PduR → LSduR → CanIf → Can |
| `Rte_Call_Port_ReadNvm(...)` | 调 `NvM_ReadBlock()` + 等待/回调 | NvM → MemIf → Fee → MemAcc → Mem |
| `Rte_Switch_Mode(m)` | 调 `Rte_Switch()` → 触发 ModeSwitchEvent | 模式机实例更新 |

> [!important] 一个推论
> **RTE 的代码量取决于"跨边界的有多少"，而不是"组件有多少"。**
> 全本地、同 Task 的系统，RTE 几乎退化成宏；跨网络多、跨核多的系统，RTE 会非常庞大。
> 这也解释了为什么小项目"手写 RTE 等价物"是可行的 → [[03-Mini-AUTOSAR分层映射]]。

## 五、边界的三个具体标志

怎么在代码里认出这条边界？

| 标志 | 位置 | 说明 |
|---|---|---|
| `Rte_*.h` 头文件 | 边界正中 | 应用只 include 这个，不 include 任何 BSW 头 |
| `Rte_Start()` / `Rte_Stop()` | 边界初始化 | EcuM 调用，标志 RTE 接管调度 |
| 命名风格切换 | 边界两侧 | 上层 `Rte_`、`Swc_`；下层 `Can_`、`Com_`、`NvM_` |

反例（越界）：

```c
/* ❌ 应用层直接调 BSW —— 破坏组件风格 */
#include "Com.h"
void MySwc_Run(void) {
    Com_SendSignal(SIG_ID, value);   /* 应用知道了通信机制 */
}

/* ✅ 通过 RTE —— 应用不知道数据怎么出去 */
#include "Rte_MySwc.h"
void MySwc_Run(void) {
    Rte_Write_Pp_LightCmd(value);    /* 本地还是远程，RTE 决定 */
}
```

## 六、对 BCM 项目的启示

以下以拟议的自建分层为讨论对象，不作为当前代码已经实现的事实。要不要引入组件风格？

| 场景 | 建议 |
|---|---|
| 单 ECU、功能固定 | **不必**引入组件风格。分层 + 一个薄的"信号绑定层"即可 |
| 未来可能拆多 ECU | 至少让业务层**不直接依赖通信数据结构**（把 DBC 信号翻译隔离在一层） |
| 有多个车型配置 | 用配置表管理差异；绑定阶段需单独确定，不能直接等同 post-build |

> [!note] 关键不是"像不像 AUTOSAR"
> 而是"**你的业务代码有没有被部署细节污染**"。
> 如果业务层里出现了 `msg.data[2] & 0x0F`，那不管分几层，解耦都没做到。
> 详见 [[03-Mini-AUTOSAR分层映射]]。
