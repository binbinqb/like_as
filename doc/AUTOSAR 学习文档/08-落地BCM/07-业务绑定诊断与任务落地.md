# 业务绑定、诊断与任务落地

> [!abstract] 范围
> 本文是项目设计建议，使用 AUTOSAR 的职责边界校验思路。当前没有读取 MCU SDK、dbcom 源码或产品 DBC，因此以下接口名与任务划分是候选，不是已实现能力。

## 一、业务模块保持一个功能一组文件

```text
app/lighting.c + lighting.h
app/button.c   + button.h
app/door_lock.c + door_lock.h
```

模块内部可用 static 函数与状态。多个实际实例才考虑上下文对象，重复规则确实稳定后才提取公共库。文件数、SWC 数和 Task 数不必相等。

## 二、DBC 到业务的合同

| 网络信号 | 转换与检查 | 业务输入 |
|---|---|---|
| LightRequest | 枚举映射、无效编码、超时 | 网络灯光请求及有效期 |
| VehicleSpeed | 原始／物理值转换、单位、品质 | 带有效性的车速 |
| LockCommand | 命令类型、序号／重复语义 | 门锁命令事件 |

pack/unpack 不做产品策略。通信适配不直接控制负载。灯光模块结合网络请求、本地按钮、自动策略和车辆模式产生请求，再由输出控制权／保护约束得到最终执行命令。

信号状态用一致快照；不能丢的动作命令用有界队列或事件计数，定义满队列、重复和超时处理。网络值相同不一定意味着“没有新命令”，应由协议的请求语义决定。

发送回报要区别目标请求、已提交硬件命令和实际反馈。需要三个量就定义三个量，不用一个变量覆盖所有含义。

## 三、故障、诊断与存储

```text
输入/输出监控 → Event → 故障管理 RAM 状态与记录
                             ↓ 持久化策略
                            NvM

UDS 0x19/0x14 → 诊断服务 → 故障管理
UDS 实时 DID → 样本/诊断快照
UDS 下线例程 → 异步测试状态机 → 输出仲裁/采集服务
```

去抖、确认、老化、记录捕获和 NV 保存分别配置。实时 DID 不经 NVM 中转；跨多帧响应的数据快照在事务期间保持一致，并有固定容量和超时释放规则。

## 四、RAM 与 NV 的分配

| 对象 | 首选存放 | 何时持久化 |
|---|---|---|
| 原始采样、解释后信号、质量 | 静态 RAM | 通常不持久化 |
| HSD 诊断值与故障寄存器采样 | 静态 RAM | 故障触发时按冻结帧配置捕获 |
| UDS 响应与例程状态 | 静态有界缓冲／池 | 通常不持久化 |
| 强制控制权 | RAM | 不跨复位保持，除非需求明确另行设计 |
| DTC、冻结帧、扩展记录 | RAM＋NV | 故障管理按策略提交 |
| 编码／标定／生产结果 | RAM 工作副本＋NV | 确认变更或生产要求时提交 |

静态／动态分配决定内存获得方式，NV 决定掉电保留，不能把它们当作三选一。

## 五、诊断控制权

定义控制入口、允许条件、会话／权限、最长持有时间、输出保护和归还规则。诊断开始、正常业务请求变化、硬件故障、诊断超时、会话切换及复位都要有确定结果。

诊断请求不能绕开过流保护。安全访问只是一种可能的诊断权限机制，具体以产品服务矩阵为准。

## 六、FreeRTOS 候选执行域

| 执行域 | 内容 | 设计约束 |
|---|---|---|
| IO | 扫描、设备事务完成、样本发布、输出提交 | 不忙等，维护共享路线所有权 |
| 通信 | 帧处理、中间件、映射与状态 | 控制突发处理量和缓冲 |
| 应用 | 按明确顺序调用各功能 MainFunction | 不直接阻塞在总线／Flash |
| 诊断 | 协议、快照、异步测试上下文 | 通过请求使用资源 |
| 存储 | 持久化作业、校验和恢复 | 评估 Flash 对 CPU／中断的实际影响 |

这五个是职责域，不强制五个 Task。短小无阻塞的域可以合并，精确时序采样可能由硬件定时／DMA 驱动。优先级来自截止期与阻塞分析，不固定“通信高于一切”。

## 七、验收一条完整链路

先验证按钮／CAN 请求到输出反馈，再注入：采样过期、I²C 失败、MUX 延迟、队列满、网络请求失效、诊断控制超时、DTC 清除后掉电、存储作业失败。

验证结果记录需求来源、配置版本、输入／输出时间、数据品质和异常恢复，不能仅用“灯亮了”作为全部平台验收。
