# 常见落地误区

> [!tip] 结论
> AUTOSAR 落地失败，**很少是因为"不懂标准"，多数是因为"理解偏了"**。
> 本文列出 12 个高频误区，每个都有：**表现 → 后果 → 正确做法**。
> 建议在新项目启动会上逐条过一遍。

## 一、架构类误区（4 个）

### 误区 1：把分层做成"目录分层"

| | 内容 |
|---|---|
| **表现** | 建了 `app/`、`hal/`、`mcal/` 目录，但代码里到处互相 include |
| **后果** | 换 MCU 时发现要改 80% 的文件 |
| **根因** | 分层只落实到"文件放哪"，没落实到"谁能依赖谁" |
| **正确做法** | ① 明确依赖规则 ② **写脚本检查**（见 [[03-Mini-AUTOSAR分层映射]]）③ CI 里拦截 |

```python
# 最小的检查：App 层不能 include hal_ / sdk
if 'app/' in path and re.search(r'#include\s+"(hal_|cvm)', src):
    error('分层违规')
```

> [!important] 判据
> **"换一颗 MCU，要改几个文件？"**
> 应尽量限制在硬件相关适配与配置，但启动、链接、OS port、资源和时序可能一起变化；文件数不能单独判定架构是否失败。

### 误区 2：跳过 RTE，应用直接读写报文

| | 内容 |
|---|---|
| **表现** | 业务代码里出现 `msg.data[2] & 0x0F`、`can_send(0x100, buf)` |
| **后果** | 换通信矩阵要改业务逻辑；无法单测；无法换通信方式 |
| **根因** | "反正只有一个 ECU，没必要抽象" |
| **正确做法** | 加一层薄封装（`rte_signals.c`），业务只调 `Rte_Read_*` |

```
❌ App → dbc_comm → Can
✅ App → Rte_* → dbc_comm → Can
         ↑ 只多这一层，但换来部署自由
```

### 误区 3：把配置当成一层

| | 内容 |
|---|---|
| **表现** | `App → cfg → chip → hal → mcal`，把 cfg 放在依赖链中间 |
| **后果** | ① 配置改了要重编译整条链 ② cfg 里逐渐长出逻辑 |
| **根因** | 把"数据"和"层"混为一谈 |
| **正确做法** | cfg 是**横切数据**，通过参数传入，不在依赖链上 |

→ 见 [[03-Mini-AUTOSAR分层映射]] 第一节

### 误区 4：在 CDD 里重写一遍 MCAL

| | 内容 |
|---|---|
| **表现** | CDD 里直接操作寄存器（如自己写 ADC 采样） |
| **后果** | 换 MCU 要重写 CDD；两套驱动并存；维护成本翻倍 |
| **根因** | "CDD 可以访问硬件，所以我自己写" |
| **正确做法** | CDD 只放**高时序算法**，底层仍调 MCAL 的 API |

> `[SRS_BSW_00164]` CDD 可以实现 ISR，但**不应该重复实现已有的驱动功能**。
> 判断：**这个操作 MCAL 已经提供了吗？** 提供了 → 用它。

## 二、实现类误区（5 个）

### 误区 5：把 Runnable 当线程用

| | 内容 |
|---|---|
| **表现** | Runnable 里 `while(1)` 或 `delay_ms()` |
| **后果** | 整个 Task 卡死，同 Task 的其他 Runnable 全部停摆 |
| **根因** | 把 Runnable 理解成"独立执行单元" |
| **正确做法** | Runnable 每次只做"一个周期的工作量"；需要延时用**状态机 + 计数** |

```c
/* ❌ */
void Swc_Run(void) {
    while (1) { do_work(); delay(10); }
}

/* ✅ */
void Swc_Run(void) {
    static uint16_t cnt = 0;
    switch (state) {
        case IDLE:  if (++cnt >= 10u) { cnt = 0; state = WORK; } break;
        case WORK:  do_work(); state = IDLE; break;
    }
}
```

### 误区 6：中断里做重活

| | 内容 |
|---|---|
| **表现** | ISR 里解析报文、查表、调用业务函数 |
| **后果** | 中断延迟大，高优先级中断被阻塞，丢帧 |
| **根因** | "中断里处理完省事" |
| **正确做法** | ISR 只**置标志 + 拷数据**，处理放 Task |

> `[SRS_BSW_00325]` The runtime of ISR and functions in interrupt context shall be **kept short**.
> Where an ISR is likely to take a long time, an **OS task should be used** instead.

| ISR 时长 | 建议 |
|---|---|
| < 10 µs | 可以直接处理 |
| 10~100 µs | 只置标志 |
| 耗时超出分析预算 | 考虑延后到 Task；100 µs 不是标准通用阈值 |

### 误区 7：发送缓冲用栈上变量

| | 内容 |
|---|---|
| **表现** | `uint8_t buf[8]; Can_Write(hth, &pdu_with_buf);` 然后函数返回 |
| **后果** | 异步发送时数据已被覆盖 → 发出去的帧内容错乱/偶发 |
| **根因** | 不理解 CAN 发送是异步的 |
| **正确做法** | 用**静态/持久缓冲**，直到 TxConfirmation 后才能复用 |

> `[SWS_Can_00011]` It is **the responsibility of the upper layer to keep the buffer consistent** until the transmission is confirmed.

### 误区 8：忽略返回值

| | 内容 |
|---|---|
| **表现** | `(void)Can_Write(...)`、`Com_SendSignal(...)` 不检查返回 |
| **后果** | 发送失败无人知道；数据无效被当有效用 |
| **根因** | "反正不会失败" |
| **正确做法** | 每个可能失败的操作都要有明确路径（处理/记录/上报） |

```c
/* ❌ 无声失败 */
(void)Can_Write(hth, &pdu);

/* ✅ 至少记录 */
if (Can_Write(hth, &pdu) != E_OK) {
    ERR_RUNTIME(ERR_MOD_CAN, ERR_CAN_TX_FULL);
}
```

> **"不处理"也是一种决策，必须显式。**

### 误区 9：NvM 没写完就睡眠

| | 内容 |
|---|---|
| **表现** | 关机流程调了 `NvM_WriteAll()` 就往下走，不等完成 |
| **后果** | 数据丢失或块损坏（掉电时正在擦写） |
| **根因** | 不知道 `NvM_WriteAll` 是异步的 |
| **正确做法** | 用 RUN 请求包住，等写完再释放 |

```c
EcuM_RequestRUN(ECUM_USER_NVM);
NvM_WriteAll();
while (NvM_GetErrorStatus(&blk) == NVM_REQ_PENDING) { /* 等 */ }
EcuM_ReleaseRUN(ECUM_USER_NVM);
```

→ 见 [[06-NVM数据管理]]

## 三、流程类误区（2 个）

### 误区 10：先写代码，后补架构

| | 内容 |
|---|---|
| **表现** | "先把功能跑通，架构以后再整理" |
| **后果** | 架构永远补不上；后期重构成本 > 重写 |
| **根因** | 进度压力 |
| **正确做法** | **先定接口边界**（哪怕只画在白板上），再写实现 |

> [!important] 一个低成本的折中
> 如果实在没时间做完整设计，**至少做一件事**：
> **先写头文件**（`hal_xxx.h`、`rte_xxx.h`），把接口定下来。
> 实现可以后补，接口改了成本最高。

### 误区 11：照抄 DBC 设计接口

| | 内容 |
|---|---|
| **表现** | 端口定义直接按 DBC 的信号名/位宽，业务层用原始值 |
| **后果** | 矩阵一变全改；业务代码里到处是 `* 0.01` 换算；语义丢失 |
| **根因** | "省事" |
| **正确做法** | **端口定义语义（物理量、范围、单位），映射时才决定布局** |

```
❌ struct { uint16_t sig_0x1234; uint8_t sig_bit_2; }
✅ struct { Rte_SpeedType speed_kmh; Rte_SwitchStateType light_sw; }
```

→ 见 [[04-VFB系统描述与系统设计]] 第四节

## 四、认知类误区（1 个）

### 误区 12：以为"用了 AUTOSAR 就安全/可靠/好维护"

| | 内容 |
|---|---|
| **表现** | 把 AUTOSAR 当成"质量保证" |
| **后果** | 架构糟糕 + 完美 AUTOSAR 实现 = 难以维护的系统 |
| **根因** | 混淆"标准"和"质量" |
| **正确做法** | 标准只保证**接口能对接**，不保证**分解合理** |

| AUTOSAR 保证 | AUTOSAR 不保证 |
|---|---|
| 接口能对接 | 功能分解是否合理 |
| 配置能一致 | 任务划分是否合理 |
| 行为可预期 | 时序是否满足 |
| 模块可替换 | 代码是否好懂 |
| — | **是否安全**（那是 ISO 26262 的事） |

> [!warning] 最危险的心态
> **"这是标准做法"** —— 标准里也有过时方案，也有不适合你场景的方案。
> 每一条都要问：**它在保护什么？我的场景需要吗？**

## 五、一张自查表

新项目启动时，逐条打勾：

| # | 检查项 | 是 |
|---|---|---|
| 1 | 依赖规则写下来了吗（谁能 include 谁） | ☐ |
| 2 | 有自动检查脚本吗 | ☐ |
| 3 | 业务层有语义接口吗（不碰报文/寄存器） | ☐ |
| 4 | cfg 是数据不是层吗 | ☐ |
| 5 | CDD 里没有重复实现 MCAL 吗 | ☐ |
| 6 | Runnable 里没有阻塞吗 | ☐ |
| 7 | ISR 都 < 10 µs 吗 | ☐ |
| 8 | 发送缓冲是持久的吗 | ☐ |
| 9 | 返回值都处理了吗 | ☐ |
| 10 | 关机等 NvM 写完了吗 | ☐ |
| 11 | 接口先定后写代码了吗 | ☐ |
| 12 | 端口是语义化的吗 | ☐ |

**12 条里超过 3 条打不上勾，架构风险已经不低了。**

## 六、如果真的踩坑了

| 症状 | 最可能的原因 | 先查什么 |
|---|---|---|
| 换 MCU 要改大量代码 | 分层没落地（误区 1） | 搜 `#include` 依赖 |
| 换通信矩阵要改业务 | 缺 RTE（误区 2） | 搜 `msg.data` |
| 偶发数据错乱 | 缓冲不持久（误区 7） | 查发送缓冲生命周期 |
| 任务卡死 | Runnable 阻塞（误区 5） | 查 Runnable 里的循环/延时 |
| 丢帧 | ISR 太长（误区 6） | 用 GPIO 翻转测 ISR 时长 |
| 关机丢配置 | NvM 未完成（误区 9） | 查 WriteAll 是否等待 |
| 诊断不通 | TP 时序/SN（见 [[06-CanTp传输协议]]） | 抓包看 FC/SF/CF |
| 睡眠不了 | RUN 请求未释放 | 打印所有 RUN 请求者 |
