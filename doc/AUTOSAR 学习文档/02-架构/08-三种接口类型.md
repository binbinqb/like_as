# 三种接口类型

> [!tip] 结论
> 这三类是分层架构文档对接口的分类，不是所有 `PortInterface` 元模型类型的枚举。判据是是否采用 AUTOSAR 端口建模技术，以及语法、语义是否由标准定义；不能仅靠 C 函数签名或是否带指针判断。

## 一、三类接口

| 类型 | 定义 | 常见位置 |
|---|---|---|
| AUTOSAR Interface | 用端口接口描述交换的信息，描述独立于具体语言、ECU 和网络 | SWC 之间，也可涉及 BSW |
| Standardized AUTOSAR Interface | 语法和语义由 AUTOSAR 标准化的 AUTOSAR Interface | 应用访问 AUTOSAR 服务 |
| Standardized Interface | 不使用上述端口接口技术的标准化 API，通常绑定 C 等语言 | BSW 模块之间、RTE 与 BSW 之间 |

普通 AUTOSAR Interface 不一定是项目私有接口；应用接口也可能来自标准化的应用接口模型。第二类强调接口的语法和语义均被 AUTOSAR 标准化。

## 二、为什么不能看见 C 函数就判定“不可跨 ECU”

`Rte_Read_*`、`Rte_Write_*`、`Rte_Call_*` 也是生成出来的 C 接口，其背后可以是本地通信或经通信栈实现的跨 ECU 连接。需要回到模型中的接口、连接、部署和通信映射判断。

`Can_Write()` 本身是本地 BSW API，不会自动成为网络 RPC。把它包装成自己的远程服务，是额外设计，不是标准接口天然可路由。

| 观察到的对象 | 正确理解 |
|---|---|
| `Can_Write(Hth, PduInfo)` | 本地 CAN 驱动 API；实际类型和错误行为查 CAN SWS |
| `NvM_WriteBlock(BlockId, SrcPtr)` | NvM 的本地 BSW API |
| `Rte_Call_*()` | 生成的服务调用入口；是否远程需检查模型与部署约束 |
| `SenderReceiverInterface` | 端口接口元模型，可支持本地或跨 ECU 通信，但有映射约束 |
| `DATA_REFERENCE` 参数 | 指针传递语义有专门限制，不能自动序列化指针指向的数据 |

## 三、可建模不等于可任意远程部署

NvM、Dem 等服务往往依赖本 ECU 的块、事件、指针和状态。不能因为采用 Standardized AUTOSAR Interface，就断言标准允许将任意服务移动到另一 ECU。需要逐个检查服务规范、位置约束、数据类型、错误和时序语义。

同步也不等于本地，异步也不等于远程。同步 C API 可能仅同步完成请求受理，实际硬件作业仍然异步进行。

## 四、自建 BCM 框架中的应用

应用通过语义接口读取“车速有效值”“按钮状态”，不要暴露 `msg.data[]`、CAN ID、引脚号或 I²C 地址。语义接口可以用简洁的 C 函数实现，不必为了名称模仿完整 RTE。

`uint8` 是否合适取决于取值、单位和有效性约定；增加一个 typedef 并不会自动实现解耦。需要同时明确数据初值、超时、错误、并发和更新时机。
