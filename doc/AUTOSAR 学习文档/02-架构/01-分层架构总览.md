# 分层架构总览

> [!tip] 结论
> 最高层视图是 Application、RTE、BSW。BSW 的粗粒度划分包括 Services、ECU Abstraction、MCAL，以及跨越硬件到 RTE 的 Complex Drivers 区域；不能把 CDD 理解成又一层必须逐级经过的水平层。

## 一、逻辑分层

```text
Application SWC ── 端口／接口合同
         │
        RTE
         │
Services：OS、EcuM、BswM、Com、PduR、CanTp、NvM、Dcm、Dem…
         │
ECU Abstraction：IoHwAb、MemIf、Fee/Ea、LSduR、CanIf、收发器等
         │
MCAL／硬件访问：Mcu、Port、Dio、Adc、Pwm、Gpt、Can、Spi、I2c 等
         │
       硬件

CDD：根据具体接口与资源规则连接 RTE、BSW、硬件
库：在调用者上下文提供相应功能，按各库 SWS 检查状态与依赖
```

这是职责简图，不是所有允许调用关系的穷尽。ServiceSwComponentType 是 BSW 服务在模型中的表示，不意味着将服务实现搬到应用层。Crypto Driver 也不能同时被当作 Csm 等上层服务。

## 二、两条必须按版本区分的链路

| 功能 | R25-11 常见路径 |
|---|---|
| CAN 信号发送 | SWC → RTE → Com → PduR → LSduR → CanIf → Can |
| CAN 诊断发送 | Dcm → PduR → CanTp → LSduR → CanIf → Can |
| 非易失数据 | NvM → MemIf → Fee/Ea → MemAcc → Mem，具体拓扑查存储规范 |

Fls/Eep 的旧链路用于理解历史实现；R25-11 发布概览已列其规范为 removed。LdCom 功能并入 Com，不能继续作为本版本独立现行模块画在主图里。

MemAcc 是硬件无关的内存访问部分，Mem 是硬件相关部分；内部／外部 Memory Driver 的位置和连接应按具体存储架构核对，不能因文件名包含 Mem 就一律归为 ECU Abstraction。

## 三、换硬件时到底改什么

目标是限制变更扩散，不是保证“只改 MCAL 就永远完成迁移”。驱动适配、板级路由、链接与启动、资源映射、时序预算、存储布局和工具配置都可能变化。

应用是否可保持源码不变，取决于接口语义、硬件能力、资源和时序要求是否仍满足。RTE 与 BSW 配置通常需要重新生成和验证。

## 四、接口与模块类型是另外两个维度

三类接口定义见 [[08-三种接口类型]]。Driver / Interface / Handler / Manager 描述职责特征，不是强制互斥的文件分类；也不能根据“是否做数据判断”机械决定全部模块层次。见 [[07-BSW模块类型分类法]]。

## 五、ICC 不等于任意自研框架自动合规

| 类 | 架构文档中的含义 |
|---|---|
| ICC1 | 内部私有 BSW 结构不规定，不要求按独立标准模块／簇组织 |
| ICC2 | 按所声明的簇组织与约束 |
| ICC3 | 以规定模块接口和行为组织 |

架构文档同时要求外部行为按 ICC3 规范，以及 ICC1/2 配置相对系统描述的兼容性。不能只满足几条 CAN 报文就声称 ICC1，也不能据此推导“不需要描述与生成合同仍完全合规”。

本项目以 SDK 和 FreeRTOS 为基础时，合理定位为借鉴 AUTOSAR 的框架；是否声明具体兼容范围另行建立证据。详见 [[12-库函数与ICC一致性类]]。
