# 横向纵向接口规则

> [!tip] 结论
> 分层规则用于约束依赖，具体调用仍需结合模块 API、回调、系统服务、CDD 及多核机制检查。不能将一张自制矩阵作为完整的规范许可表。

## 一、架构文档中的一般规则

| 方向 | 一般规则 |
|---|---|
| 纵向 | 可以访问下一层接口；应避免绕过一层；不允许绕过两层及以上；不允许绕过 MCU 抽象的一般路径 |
| 跨功能域 | 允许使用较低层另一功能组的模块，例如外部器件通过 Spi 访问 |
| 系统服务 | 各层可以与系统服务交互，但要遵守具体 API／上下文合同 |
| Services 横向 | 允许，例如 Dem 使用 NvM |
| ECU Abstraction 横向 | 允许，按各模块规范使用 |
| MCAL 横向 | 禁止硬编码耦合；必要交互可用静态可配置通知等规定机制 |

这些是一般架构规则；CDD 的硬件访问和已定义的特殊接口要单独处理。“禁止绕过 MCAL”不能被解释为连标准允许的 CDD 硬件访问也禁止。

## 二、回调不是非法向上依赖

ADC、CAN、SPI 等驱动通过规定或配置的 notification/callback 将结果交付上层。这种反向控制流是接口合同的一部分，与底层硬编码依赖业务模块不同。

例如驱动调用 `CanIf_RxIndication` 是规定的上层通知，不应因为调用箭头向上就判违规。

MCAL 的配置回调也不能自动使任意初始化互调合理。仍需检查调用上下文、重入、初始化顺序和资源所有权。

## 三、系统服务没有本文自造的固定白名单

原文“只有 Det、Dem、查询类 OS、SchM 算系统服务”缺乏依据。BswM 可以接收下层规范定义的状态通知；OS 也不只提供查询接口。合法性以实际规范和集成合同为准，不能先按名称禁止。

## 四、自建框架中的检查方式

1. 先定义逻辑职责：应用、信号／服务、设备、MCU 适配、厂商 SDK。
2. 明确公共类型、公共算法库、配置、回调头文件和内部头文件的区别。
3. 按目录与实际 include 搜索路径解析依赖，检查跨层实现调用。
4. 对每个例外记录用途、接口、调用上下文和验证。

仅搜索文件名是否包含 `can`、`hal` 不能成为可靠的架构检查器；合法语义接口可能带这些子串，间接依赖也可能漏检。示例脚本应明确标为演示，不声称其已经覆盖 CI 检查。

## 五、应用边界

应用可以依赖自己功能的 `.h`、语义信号类型、经过约定的服务和无硬件依赖算法库。不要机械要求所有应用文件只 include 一份 RTE 头。

业务不应暴露寄存器、SDK 类型、引脚、总线地址、DBC 位布局。若自建框架选择直接 C 语义接口，只要职责与合同清晰，不必为了名字再加一层空转发。

## 六、自检

1. 驱动回调上层为什么不等于违反分层？
2. BswM 接收状态通知为什么不能用“下层不准调用 BswM”否定？
3. 路径依赖检查和文件名子串检查有什么区别？
