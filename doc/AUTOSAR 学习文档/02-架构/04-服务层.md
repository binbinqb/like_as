# 服务层

> [!tip] 结论
> 服务层是 BSW 的最高层，提供**六类平台能力**：OS、通信、存储、诊断、状态/模式管理、程序流监控。
> 判断一个模块是否属于服务层：**它是不是"每个 ECU 都可能要用，且与具体硬件无关"的能力？**

## 一、官方定义

> The Services Layer is the **highest layer of the Basic Software** ... it offers:
> - **Operating system** functionality
> - **Vehicle network communication and management** services
> - **Memory services** (NVRAM management)
> - **Diagnostic Services** (including UDS communication, error memory and fault treatment)
> - **ECU state management, mode management**
> - **Logical and temporal program flow monitoring** (WdgManager)
>
> **Task**: Provide basic services for applications, RTE and basic software modules.
> **Properties**:
> - Implementation: mostly **µC and ECU hardware independent**
> - Upper Interface: **µC and ECU hardware independent**
> —— EXP_LayeredSoftwareArchitecture

## 三、服务层内部的四种协作模式

### 模式 1：统一入口 → 多后端（MemIf / ComM）

```
        NvM
         ↓
       MemIf          ← 统一接口
       ↙    ↘
    Fee      EA       ← 多个后端实现
```

上层只调 `MemIf_Write()`，MemIf 根据配置路由到 Fee 或 EA。

**同类模式**：`ComM` 统一收集通信需求 → 分发到各 `XxSM`。

### 模式 2：仲裁与编排（BswM）

```
多个 ModeRequest 源 ──→ BswM ──→ 多个 Action
（EcuM、ComM、SWC、Dcm）   （规则引擎）   （启停通信、切换调度表、设置引脚）
```

BswM 负责配置的模式仲裁和动作编排，其他模块仍有自身状态和策略：它把"条件"与"动作"解耦，条件是配置的，动作是配置的，规则通过配置生成或由相应实现执行。

→ 详见 [[02-模式管理EcuM与BswM]]

### 模式 3：分层封装（CanTp → PduR → Com）

职能单一、层层递进，每层只做一件事：

| 模块 | 输入 | 输出 | 做什么 |
|---|---|---|---|
| Com | 信号值 | I-PDU | 打包、超时、发送模式 |
| PduR | I-PDU | I-PDU / N-PDU | 路由（谁发给谁） |
| CanTp | N-PDU（>8B） | N-PDU（分帧） | 分段/重组 |

### 模式 4：大数据与专用路径（按版本和接口）

某些大数据流不值得走 Com 的信号打包（开销大），旧版可能采用 LdCom；R25-11 相关能力并入 Com，XCP 等则按其专用接口配置。

## 四、服务层的三个特殊地位

### 地位 1：所有层都能访问 System Services

> All layers may interact with system services.

| 谁能访问 | 访问什么 | 例子 |
|---|---|---|
| MCAL | Det | 驱动里报开发错误 |
| ECU Abstraction | Det、Dem | 通信错误上报 |
| Services 内部 | 互相 | Dem 用 NvM 存故障 |
| 应用 | Dem（通过 RTE） | 应用报故障事件 |

**这是分层的唯一系统性例外**，因为系统服务是"全局基础设施"。

### 地位 2：服务层可以横向互调

> Services Layer: **horizontal interfaces are allowed**.
> Example: Error Manager saves fault data using the NVRAM manager.

| 允许的横向调用 | 原因 |
|---|---|
| Dem → NvM | 故障码要持久化 |
| Dcm → Dem | 读/清故障码 |
| Dcm → Com | 诊断响应发送 |
| ComM → Nm | 通信需求驱动网络管理 |
| BswM → 几乎所有 | 它就是编排者 |

### 地位 3：服务层不实现 ISR

> `[SRS_BSW_00164]` Only the Operating System, complex drivers and modules of the MCAL are allowed to implement interrupt service routines.

服务层的"中断响应"通过 OS 的 ISR → Task 激活实现，不自己写 ISR。

## 五、主函数（Main Function）机制

服务层模块大多有周期性主函数，由 `SchM`（BSW Scheduler）调度：

| 模块 | 主函数 | 典型周期 |
|---|---|---|
| Com | `Com_MainFunctionTx()` / `Rx()` | 5~10 ms |
| PduR | `PduR_MainFunction()` | 5~10 ms |
| CanTp | `CanTp_MainFunction()` | 1~5 ms（影响 TP 时序） |
| Dcm | `Dcm_MainFunction()` | 5~10 ms |
| Dem | `Dem_MainFunction()` | 10~100 ms |
| NvM | `NvM_MainFunction()` | 5~20 ms |
| BswM | `BswM_MainFunction()` | 5~10 ms |
| EcuM | `EcuM_MainFunction()` | 10~50 ms |
| WdgM | `WdgM_MainFunction()` | 与监督周期匹配 |

> [!warning] 主函数周期是"隐性时序契约"
> - `CanTp_MainFunction` 周期直接影响 `N_Bs`/`N_Cr` 超时判断精度。
>   周期与实现应满足具体 TP 时序；STmin 是最小间隔，发送得更慢本身不违反 STmin，但仍受 N_* 超时及系统吞吐要求限制。
> - `Com_MainFunctionTx` 周期影响周期报文的抖动。
> - 这些周期在配置里定，**改了要重新评估时序**。

→ 详见 [[04-OS与调度]]

## 六、服务层的裁剪建议（对 BCM）

| 模块 | 是否必需 | 说明 |
|---|---|---|
| Os | ✅ 必需 | 即使不用 OS，也需要一个最小调度 |
| EcuM / BswM | ✅ 必需 | 睡眠唤醒是 BCM 核心 |
| Com / PduR | ✅ 必需 | 通信基础 |
| CanIf / Can / CanTp | ✅ 必需 | CAN 通信 + 诊断 |
| Dcm / Dem | ✅ 必需 | 法规要求 UDS 诊断 |
| NvM / Fee / MemAcc / Mem | ✅ 必需 | 配置/故障码持久化 |
| **Nm / ComM** | ⚠️ 视平台 | 若有网络管理需求（睡眠协调）则必需 |
| **WdgM** | ⚠️ 视安全等级 | 有功能安全要求时必需 |
| **SecOC / E2E** | ⚠️ 视平台 | 有网络安全/完整性要求时 |
| **Eth 全套** | ❌ 通常不需要 | 除非有以太网骨干 |
| **V2X / ChrgM / DDS** | ❌ 不需要 | 与本项目无关 |
| **XCP** | 🔧 开发期 | 标定测量需要，量产可裁 |

> [!tip] 裁剪的判据不是"能不能省"
> 而是"**省掉之后，对外行为是否还符合 ICC3**"（见 [[12-库函数与ICC一致性类]]）。
> 例如：若产品要求 0x19 和对应 DTC 行为，就要提供所需故障管理能力；是否必须采用标准 Dem 及哪些服务必选由产品和合规范围决定。
