# 产品线工程

> [!note] 项目上下文
> 未经本轮实际工程输入验证的“现状”、器件、数量和工具信息，均按示例或待确认假设阅读；不代表已审查 SDK、原理图、DBC 或现有业务代码。


> [!tip] 结论
> AUTOSAR 的配置机制（三态 + 变体）本质上是**软件产品线工程（SPL）在汽车领域的落地**。
> 产品线的核心是：**识别共性与可变性，把共性做成平台，把可变性做成配置。**

## 一、什么是软件产品线

| 传统模式 | 产品线模式 |
|---|---|
| 每个车型单独开发 | 一个平台 + 多套配置 |
| 代码复制粘贴 | 代码共享，差异配置化 |
| 改一个 bug 要改 N 个项目 | 改一处，全部受益 |
| 成本 ∝ 车型数 | 成本 = 平台成本 + N × 配置成本 |

```
        平台（共性）
    ┌────────────────────┐
    │  核心功能、架构、驱动  │
    └─────────┬──────────┘
              │ + 可变性配置
    ┌─────────┼─────────┬─────────┐
    ▼         ▼         ▼         ▼
  低配版    中配版    高配版    出口版
```

## 二、三个核心活动

### 2.1 共性分析（Commonality Analysis）

找出"所有产品都一样的部分"。

| 层次 | 共性 | 可变 |
|---|---|---|
| 架构 | 分层结构、接口规范 | 具体模块 |
| 通信 | 协议栈、TP 机制 | 报文矩阵 |
| 诊断 | UDS 服务框架 | DTC 列表、DID |
| 存储 | NvM 机制 | 块定义 |
| 功能 | 基础灯光、门锁 | 高级功能（记忆、自动） |

### 2.2 可变性建模（Variability Modeling）

用**特征模型**描述"哪些可以变、怎么变、有什么约束"。

```
BCM 特征模型
├── [必选] 基础灯光
│   ├── [必选] 近光/远光
│   ├── [可选] 自动大灯
│   └── [可选] 大灯随动
├── [必选] 中控锁
│   ├── [必选] 遥控解锁
│   └── [可选] 无钥匙进入
├── [可选] 座椅记忆
│   └── [requires] 电动座椅
└── [可选] 天窗控制
```

| 关系 | 含义 |
|---|---|
| **必选（mandatory）** | 所有产品都有 |
| **可选（optional）** | 可有可无 |
| **备选（alternative）** | 多选一 |
| **requires** | A 需要 B |
| **excludes** | A 与 B 互斥 |

> [!important] 约束必须显式
> "选了座椅记忆就必须有电动座椅" —— 如果这个约束不写进模型，
> 配置工具就无法校验，会生成非法组合。
> **特征模型的价值就在这些约束上。**

### 2.3 可变性实现（Variability Implementation）

把特征映射到技术手段：

| 特征类型 | 实现手段 | AUTOSAR 对应 |
|---|---|---|
| 功能有无 | 组件变体 | Variation Point（Post-build） |
| 参数不同 | 配置数据 | Post-build 配置 |
| 硬件不同 | 驱动配置 | Link-time 配置 |
| 完全不同的实现 | 不同组件 | 组件变体（Pre-compile） |

## 三、AUTOSAR 提供的支撑

| SPL 需求 | AUTOSAR 机制 |
|---|---|
| 描述可变性 | Variation Point + Condition |
| 管理变体组合 | Predefined Variant |
| 分层绑定 | 五种绑定时间 |
| 配置交付 | ARXML（可跨组织传递） |
| 工具链自动化 | 元模型 + 生成器 |

> [!note] AUTOSAR 没提供的
> | 缺失 | 你要自己做 |
> |---|---|
> | 特征模型 | 用专门工具（pure::variants、FeatureIDE）或 Excel |
> | 变体矩阵管理 | 配置管理系统（Git + 分支策略） |
> | 变体测试策略 | 测试用例选择（不是全组合测） |
> | 成本模型 | 商业决策 |

## 四、BCM 平台化的实践路径

### 阶段 1：单项目（现状）

```
一个车型 → 一套代码 → 一堆 #define
```

**问题**：第二个车型来了 → 复制粘贴 → 分叉 → 维护地狱。

### 阶段 2：配置化（推荐起点）

```
一套代码 + 配置表
├── cfg_vehicle.h        # 车型相关（编译期）
├── cfg_io_map.c         # IO 映射（链接期/表驱动）
└── cfg_feature.c        # 功能开关（表驱动）
```

**关键动作**：
1. 把所有"车型相关"的硬编码抽出来，变成配置项
2. 配置项集中管理，不散落在业务代码里
3. 配置项有默认值 + 校验

### 阶段 3：平台化

```
平台代码（不含任何车型信息）
    +
车型配置包（每车型一个）
    +
生成工具（从配置生成代码/表）
```

**判据**：平台代码里搜索不到任何车型名/项目名。

### 阶段 4：产品线（完整 SPL）

```
特征模型（形式化）
    ↓
变体配置（Predefined Variant）
    ↓
自动生成（配置 + 代码 + 文档 + 测试用例）
    ↓
变体测试（按特征选测，不全组合）
```

## 五、变体爆炸与测试策略

### 5.1 组合爆炸

```
5 个可选特征 → 2^5 = 32 种组合
10 个可选特征 → 1024 种
20 个可选特征 → 100 万种（不可能全测）
```

### 5.2 测试策略

| 策略 | 说明 | 覆盖率 |
|---|---|---|
| **全组合** | 测所有组合 | 100%（不可行） |
| ** pairwise（两两组合）** | 任意两个特征的组合都覆盖 | 高（通常 80%+ 缺陷） |
| **最小变体集** | 选覆盖所有特征的最小集合 | 中 |
| **风险优先** | 只测高风险组合 | 视情况 |

> [!tip] pairwise 是一种候选组合测试方法
> pairwise 覆盖二因素组合，不能据此保证覆盖高阶交互、边界或安全相关故障。
> 可与约束、风险优先级、需求测试和关键组合测试结合，不宣称通用缺陷覆盖比例。
>
> 工具：PICT（微软）、ACTS（NIST）

### 5.3 增量测试

| 变更 | 需要重测什么 |
|---|---|
| 新增一个可选特征 | 该特征 + 与它交互的特征 |
| 修改公共代码 | **全部变体**（影响面最大） |
| 修改某变体配置 | 该变体 |

## 六、配置管理

### 6.1 版本矩阵

```
        软件版本
        v1.0  v1.1  v2.0
车型 A   ✓     ✓     ✓
车型 B   ✓     ✓     ✓
车型 C   -     ✓     ✓
```

**要求**：任何时刻能回答"车型 X 用的是哪个软件版本 + 哪套配置"。

### 6.2 分支策略

| 策略 | 适用 |
|---|---|
| **主干开发 + 特性开关** | 推荐（避免分支分叉） |
| **每车型一分支** | ❌ 不推荐（合并地狱） |
| **发布分支** | 用于已交付版本维护 |

> [!warning] "每车型一分支"是最常见的错误
> 短期看方便，长期看：
> - bug 修复要 cherry-pick 到 N 个分支
> - 分支间代码差异越来越大
> - 最终无法合并
>
> **正确做法**：主干一套代码，用配置区分车型。分支只用于"已发布版本的维护"。

### 6.3 配置的可追溯性

每个交付的 ECU 应该能追溯：

| 追溯项 | 存在哪 |
|---|---|
| 软件版本 | 诊断 DID（如 0xF189） |
| 变体编码 | NvM 块 + 诊断 DID |
| 配置哈希 | 启动时校验（见 [[01-ECU启动流程]]） |
| 生产日期/批次 | NvM |

## 七、成本模型

产品线的经济性：

```
传统模式成本 = N × 单车型成本
产品线成本   = 平台建设成本 + N × 配置成本 + 维护成本

盈亏平衡点：N > 平台建设成本 / (单车型成本 - 配置成本)
```

| 因素 | 影响 |
|---|---|
| 车型数量多 | 产品线更划算 |
| 车型差异小 | 产品线更划算 |
| 平台建设投入大 | 需要足够多的车型摊薄 |
| 生命周期长 | 产品线收益更大 |

**经验值**：**3 个以上车型、生命周期 5 年以上，产品线开始划算。**

## 八、落到你的项目

| 现状 | 建议动作 |
|---|---|
| 单车型、配置靠 `#define` | 1. 建立"配置项清单"（列出所有可变点） |
| 即将支持第二车型 | 2. 把车型相关代码抽到独立文件 |
| 已有 2~3 车型 | 3. 建立配置表 + 生成工具 |
| 多车型 + 多市场 | 4. 引入 Predefined Variant + 变体编码 |

### 一个立即可做的小事

**建立"可变点清单"**：

| # | 可变点 | 当前实现 | 绑定时间 | 影响范围 |
|---|---|---|---|---|
| 1 | 是否有天窗 | `#define HAS_SUNROOF` | Pre-compile | 天窗控制模块 |
| 2 | 门数 | `#define DOOR_COUNT` | Pre-compile | IO 映射、逻辑 |
| 3 | 灯光 PWM 频率 | 硬编码 200Hz | 应改为配置 | 灯光输出 |
| 4 | DTC 列表 | 硬编码数组 | 应改为 Post-build | 诊断 |

**这张表就是产品线工程的起点。** 没有它，一切"平台化"都是空谈。
