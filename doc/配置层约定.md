## 0 为什么换掉手写（三条实测教训）

这不只是"用上 as-master 的工具"，是因为手写 C 表在真实矩阵规模下**必然会错**：

| 里程碑 | 踩的坑 | 如果当初是生成的 |
|---|---|---|
| M8 | `CanIf_RxDispatch` 用二分查找，加报文时表序错乱，某条报文自己收不到 | `extract()` **强制按 `id & 0x1FFFFFFF` 排序**，且启动时检测 `canid & mask` 重叠 |
| M10 | Motorola 信号的 `BitPosition` 填 0，读到 `0x9180`（左移 7 位） | 生成 `sig["start"] & 7`，**算不出错** |
| M14 | 标准帧硬件掩码忘了 `<< 18`，变成"全收邮箱"，后面所有同类型报文静默丢失 | 硬件掩码在 JSON 里显式写，不靠手算位移 |

M14 那次压测里，386 个信号只有 3 个是手写的；真实矩阵有 372 个信号——
**手工抄 372 个字节偏移，错一个是"信号值对不上"，查起来比死机还难**。

## 1 生成器怎么接进来的

### 1.1 文件来源

```
tools/generator/          ← 从 as-master 原样拷贝（927 KB，53 个 .py，31 个生成器）
```

保留全部模块而不裁剪，理由：`BL.py`（bootloader 生成器）正好对应刷写改到 boot
的需求；裁剪会造成 `__init__.py` 的 import 断裂，省下的体积不值得。

### 1.2 唯一的上游改动：`RoD.py` 去掉 `pycrc` 依赖

```python
# 原：from pycrc.algorithms import Crc
#     CrcEng = Crc(width=16, poly=0x1021, ...); crc = CrcEng.table_driven(data)

def Calcaulte_Crc16(data):
    crc = 0xFFFF
    for b in data:
        crc ^= (b << 8)
        for _ in range(8):
            if crc & 0x8000:
                crc = ((crc << 1) ^ 0x1021) & 0xFFFF
            else:
                crc = (crc << 1) & 0xFFFF
    return crc
```

**为什么改**：`pycrc` 只为算一个标准 CRC-16/CCITT-FALSE。构建链多一个
`pip install` 依赖，换机器就要重装。

**怎么验证等价**：标准测试向量 `b"123456789"` → `0x29B1`（已通过）。

### 1.3 循环导入：**不能**在 `building.py` 顶层 import generator

```
building.py → from generator import Generate   ← 错！
generator/__init__.py → from .Rte import Gen
Rte.py → from building import *                ← 回到 building，此时 generator 未初始化完
→ ImportError: cannot import name 'Generate' from partially initialized module
```

**正确做法**：`building.py` 里已有 `def generate(cfgs, force=False)`（约 2636 行），
它在**函数体内** `from generator import Generate`。这是 as-master 原本的设计，
不要动它。

### 1.4 外部依赖

| 依赖 | 用途 | 状态 |
|---|---|---|
| **PLY 3.11** | `generator/dbc/ascyacc.py` 用 LALR 解析 DBC | 已装（纯 Python，装一次） |
| ~~pycrc~~ | ~~RoD 的 CRC~~ | **已去掉** |
| pandas / openpyxl | `Dcm.py` / `Dem.py` 的 Excel 导入 | 已装（读通信矩阵要用） |

> PLY 缺失的表现是 `ModuleNotFoundError: No module named 'ply'`，构建时直接报错，

## 2 目录布局与"配置源 vs 生成物"的边界

```
app/platform/cvm0146/src/config/
  dbc/
    can1.dbc                 ← 整车网（实车 CAN1，250 kbps）
    can0.dbc                 ← 组合开关（实车 CAN3，500 kbps）
  CanIf/
    CanIf.json               ← 配置源（入库）
    GEN/                     ← 生成物（.gitignore 排除）
      CanIf_Cfg.c  CanIf_Cfg.h  CanIf.json（展开后的中间版，供人核对）
  PduR/PduR.json  → GEN/
  Com/Com.json    → GEN/
  CanTp/  Dcm/  Dem/  CanNm/  NvM/     ← 待建
```

**为什么 DBC 要拷到 `config/dbc/`**：

- `doc/福田系统设计/` 是参考资料，可能不随代码发布（而且里面还有公司内部文件）
- DBC 是**构建输入**，理应随代码走
- 缺点：要手工同步。约定：**系统设计更新 DBC 时，同时更新这一份**，
  并在提交信息里写清版本号（如 `can1.dbc @ 通信矩阵 V0.4_20251031`）

**为什么生成物不入库**：

改了 JSON 却忘了提交生成的 `.c`，是这类工具最典型的"仓库不一致"。
生成物根本不在版本库里，这个问题就不可能发生。`--gen` 可强制重新生成。

## 3 配置格式（已实测跑通的三份）

### 3.1 `CanIf.json` —— 最小形态

```json
{
  "class": "CanIf",
  "RxPacketPoolSize": 0,
  "TxPacketPoolSize": 0,
  "RxPacketDataSize": 64,
  "TxPacketDataSize": 64,
  "networks": [
    {
      "name": "CAN1",
      "me": "BCM",
      "dbc": "../dbc/can1.dbc",
      "RxPdus": [],
      "TxPdus": []
    }
  ]
}
```

`me` = DBC 里 `BO_ ... <sender>` 的那个名字。**本节点发的报文判 TX，其余判 RX。**

派生的 PDU 命名规则：`CAN1_<MSGNAME>_RX` / `_TX`（全大写，非字母数字转下划线）。

**实测结果**：CAN1 网络 → **34 条 RX + 6 条 TX**，宏 `CANIF_CAN1_*` 共 40 条，
按 ID 升序。

### 3.2 `PduR.json` —— 自动推导 + 手工路由

```json
{
  "class": "PduR",
  "routines": [
    { "name": "P2P_RX", "from": "CanTp", "to": "Dcm" },
    { "name": "P2P_TX", "from": "Dcm",  "to": "CanTp" }
  ],
  "networks": [
    { "name": "CAN1", "me": "BCM", "network": "CAN", "dbc": "../dbc/can1.dbc" }
  ]
}
```

- `networks` 里的报文路由**自动推导**：本节点发 → `Com → CanIf`；否则 `CanIf → Com`
- `routines` 是**手工的**，用于诊断（CanTp↔Dcm）这类不来自 DBC 的路由

**实测结果**：`PduR_Cfg.c` 25 KB，`PduR_Cfg.h` 2.4 KB。

### 3.3 `Com.json` —— `use_dbc` 自动导入信号

```json
{
  "class": "Com",
  "networks": [
    {
      "name": "CAN1", "network": "CAN", "device": "cvm0146", "port": 0,
      "baudrate": 250000, "me": "BCM",
      "use_dbc": true, "dbc": "../dbc/can1.dbc",
      "messages": []
    }
  ]
}
```

`messages` 留空 = 全量从 DBC 导入；需要覆盖某条报文时再往里写。

**实测结果**：

| 产物 | 规模 |
|---|---|
| `Com_Cfg.c` | **519 KB**（372 个信号的完整配置） |
| `Com_Cfg.h` | 35 KB，467 个宏 |
| `Com.json`（展开版） | 158 KB，可人工核对 |
| `bswcom.py` | 102 KB，RTE 接口模板（当前用不上） |

信号配置抽查（与 DBC 原文对照）：

```
DBC: SG_ BCM_LowBeamSts : 4|2@1+ (1,0) [0|3] ""
生成: BitPosition = 4   BitSize = 2   COM_LITTLE_ENDIAN   COM_UINT8
      ptr = &Com_PduData_BCM_LCSF_TX[0]（字节 0）
```

> **本项目的 372 个信号全部是 Intel 字节序**（`@1`），与 J1939-71 的规定一致
> （多字节参数用小端）。M10 那个 Motorola `BitPosition` 的坑在这个项目不会出现，
> 但生成器对 Motorola 也走同一套 `start & 7` 逻辑，换成别的项目照样正确。

## 4 未解决的问题：`hoh`（硬件对象句柄）

### 4.1 现象

生成的 `CanIf_Cfg.c` 里 **40 条 PDU 的 `hoh` 全是 0**。

原因在 `extract()`：`hrh` 是**每网络**递增的，不是每报文：

```python
pdu = {"name": rn, "id": msg["id"], "hoh": hrh, "up": "PduR"}   # hrh 在循环里不变
```

AS 的模型是"一个 hoh = 一个硬件接收对象"，可以有多条 PDU 共享。

### 4.2 为什么在 FlexCAN 上不可行

`hoh` 对应一个 RX 邮箱，而**一个邮箱只有一个掩码**。34 条不同 PGN 的报文
配 `hoh=0` 时，那个邮箱只能匹配其中一条。

### 4.3 硬件的真实约束（M14 实测）

- 按 **PF 分组**（掩码 `0x03FF0000`，屏蔽优先级 P + PS + SA）可以把 34 条收进 **6 个邮箱**
- 硬件掩码用 `0x03FF0000`（**不含优先级**，这样同一 PGN 不同优先级的帧都能收）
- 软件层（CanIf）的 mask 仍用 `0x1FFFFFFF` **精确匹配**

**两层分工**：硬件按 PF 段放行（宽），软件按完整 ID 过滤（窄）。

### 4.4 解决方案（下一步实施）

**核心思路：一份规则 → 两个产物，天然一致。**

在 `CanIf.json` 的 network 里加一张分组表：

```json
"hohGroups": [
  { "hoh": 2, "id": "0x18F00000", "mask": "0x03FF0000", "comment": "PF=0xF0" },
  { "hoh": 3, "id": "0x18FD0000", "mask": "0x03FF0000", "comment": "PF=0xFD" },
  { "hoh": 4, "id": "0x18FE0000", "mask": "0x03FF0000", "comment": "PF=0xFE" },
  { "hoh": 5, "id": "0x18FF0000", "mask": "0x03FF0000", "comment": "PF=0xFF" }
]
```

写一个前置脚本 `tools/gen_hoh.py`：

1. 读 `CanIf.json` + `hohGroups`
2. 给每条 PDU 按 `id & mask` 匹配分组，填上 `hoh` → 输出 `CanIf.gen.json`
3. **同时**用同一张表生成 `Can_Cfg.c` 的邮箱表（`CanHw_MsgCfgType` 数组）+ `Can_HwCfg.h` 的 ID 宏

这样 `CanIf` 和 `Can_Cfg` 不可能漂移——它们来自同一份 `hohGroups`。

> 这正是 M8 那个 `CanIfCfg_CheckRxOrder()` 自检想解决的问题的**根本解**：
> 不是"配错了再检查"，而是"配不错"。

### 4.5 为什么不直接改 as-master 的 `CanIf.py`

改它可以少一层，但会给上游合并带来持续成本。**保持生成器原样**，
在它前面加一层自己的预处理，是更划算的取舍。

## 5 手写 vs 生成的边界

**判断标准：AS 有对应模块的 → 生成；平台/芯片私有的 → 手写。**

| 配置 | 方式 | 理由 |
|---|---|---|
| `CanIf_Cfg` | **生成** | AS 标准模块，表结构与 as-master 逐字段一致 |
| `PduR_Cfg` | **生成** | 同上 |
| `Com_Cfg` | **生成** | 372 个信号，手写不现实 |
| `CanTp_Cfg` | 生成（待建） | AS 有 `CanTp.py` |
| `Dcm_Cfg` | 生成（待建） | AS 有 `Dcm.py`；但福田 Excel 的 sheet 名与 AS 模板不同，需转换 |
| `Dem_Cfg` | 生成（待建） | 110 个 DTC |
| `CanNm_Cfg` | 生成（待建） | CAN3 才用 |
| `NvM_Cfg` | 生成（待建） | 当前用厂商 FEE 引擎，结构不同，要评估 |
| **`Can_Cfg`** | **手写**（将来由 `gen_hoh.py` 派生） | **FlexCAN 邮箱表是芯片私有概念，AS 里没有** |
| **`Can_HwCfg.h`** | **手写** | 同上（ID/掩码/HTH 定义） |
| **`Port_Cfg`** | **手写** | 引脚映射是板级私有 |
| **`Adc_Cfg`** | **手写** | 通道/采样时间是芯片私有 |
| **`Fee_Cfg` / 厂商 NvM** | **手写** | 厂商引擎，不走 AS 接口 |

## 6 接入构建的步骤（下一轮）

当前生成器**未接入** `build.bat`，是手工调用的。接入需要一次性替换整链，
不能逐个换（原因：生成的 `PduR_Cfg.c` 引用 `COM_CAN1_*` 宏，那些宏来自生成的
`Com_Cfg.h`；单独换 PduR 会编译失败）。

```python
# app/platform/cvm0146/SConscript，现在：
"CanIf": Glob("src/config/CanIf_Cfg.c"),
# 改成：
"CanIf": Glob("src/config/CanIf/CanIf.json"),
```

`RegisterConfig()` 会自动：
1. 调 `generate()` 生成到 `GEN/`
2. 把 `GEN/CanIf_Cfg.c` 加进编译
3. 把 `$CanIf_Cfg` 加进 CPPPATH（指向 `GEN/`）

**接入顺序（每一步都要能编译通过再走下一步）**：

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | `gen_hoh.py` + `CanIf.json` 加 hohGroups，验证 hoh 分配与 `Can_Cfg` 一致 | 中（Can_Cfg 要跟着改） |
| 2 | 一次性替换 CanIf + PduR + Com，删掉手写的那三份 | **高**（表结构、宏名全换，app 层要跟着改） |
| 3 | 上板验证：收发、诊断、信号值 | 中 |
| 4 | 再逐个加 CanTp / Dcm / Dem / CanNm | 低（独立性强） |

第 2 步为什么风险高：`App_CanIfRxIndication` 这个回调在生成器里没有对应物
（生成器只会输出 `PduR_CanIfRxIndication` 或 `<Up>_RxIndication`）。
需要用 `"up": "User_App"` 让生成器输出 `User_App_RxIndication`，
再在 app 里实现这个函数（转发给现有的 `App_CanIfRxIndication`）。

## 7 复现步骤（换一台机器）

```sh
# 1. 确认依赖
python -c "import ply, pandas, openpyxl; print('ok')"

# 2. 一条命令：生成 + 注入 + 一致性断言（A4）
python tools/a4_gen_check.py --sync

# 3. 产物在各自的 GEN/ 下；Com 的产物被拷到 config/Com_Cfg.c|h
```

`--sync` 会把 `GEN/` 的产物拷进 `config/`（只有 `Com` 是这种形态）。
不带 `--sync` 时，若副本与产物不一致，C4 会 FAIL 并提示。

### 7.1 三条硬规矩（A4 落地后不再靠自觉）

1. **不许在生成物里写时间戳**（`GenHeader` 已去掉）。带时间戳的产物
   第二遍生成就和第一遍不同，"重新生成无 diff"这个判据永远不成立。
2. **不许手改 `@generated` 区块内的内容**。`CanIf_Cfg.c` / `PduR_Cfg.c` 里
   `@generated BEGIN … END` 之外随便改，之内一定被脚本覆盖。
3. **`config/Com_Cfg.c|h` 是生成物入库**。改信号要改 `Com/Com.json` 或
   `dbc/can1.dbc`，然后 `python tools/a4_gen_check.py --sync`；
   直接改 `.c` 会在下一次生成时静默消失。
