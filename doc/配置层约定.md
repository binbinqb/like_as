## 0 为什么换掉手写（三条实测教训）

这不只是"用上 as-master 的工具"，是因为手写 C 表在真实矩阵规模下**必然会错**：

| 里程碑 | 踩的坑 | 如果当初是生成的 |
|---|---|---|
| M8 | `CanIf_RxDispatch` 用二分查找，加报文时表序错乱，某条报文自己收不到 | `extract()` **强制按 `id & 0x1FFFFFFF` 排序**，且启动时检测 `canid & mask` 重叠 |
| M10 | Motorola 信号的 `BitPosition` 填 0，读到 `0x9180`（左移 7 位） | 生成 `sig["start"] & 7`，**算不出错** |
| M14 | 标准帧硬件掩码忘了 `<< 18`，变成"全收邮箱"，后面所有同类型报文静默丢失 | 硬件掩码在 JSON 里显式写，不靠手算位移 |

M14 那次压测里，386 个信号只有 3 个是手写的；真实矩阵有 372 个信号——
**手工抄 372 个字节偏移，错一个是"信号值对不上"，查起来比死机还难**。

## 1 生成器怎么接进来的

### 1.1 文件来源

```
tools/generator/          ← 从 as-master 原样拷贝（927 KB，53 个 .py，31 个生成器）
```

保留全部模块而不裁剪，理由：`BL.py`（bootloader 生成器）正好对应刷写改到 boot
的需求；裁剪会造成 `__init__.py` 的 import 断裂，省下的体积不值得。

### 1.2 唯一的上游改动：`RoD.py` 去掉 `pycrc` 依赖

```python
# 原：from pycrc.algorithms import Crc
#     CrcEng = Crc(width=16, poly=0x1021, ...); crc = CrcEng.table_driven(data)

def Calcaulte_Crc16(data):
    crc = 0xFFFF
    for b in data:
        crc ^= (b << 8)
        for _ in range(8):
            if crc & 0x8000:
                crc = ((crc << 1) ^ 0x1021) & 0xFFFF
            else:
                crc = (crc << 1) & 0xFFFF
    return crc
```

**为什么改**：`pycrc` 只为算一个标准 CRC-16/CCITT-FALSE。构建链多一个
`pip install` 依赖，换机器就要重装。

**怎么验证等价**：标准测试向量 `b"123456789"` → `0x29B1`（已通过）。

### 1.3 循环导入：**不能**在 `building.py` 顶层 import generator

```
building.py → from generator import Generate   ← 错！
generator/__init__.py → from .Rte import Gen
Rte.py → from building import *                ← 回到 building，此时 generator 未初始化完
→ ImportError: cannot import name 'Generate' from partially initialized module
```

**正确做法**：`building.py` 里已有 `def generate(cfgs, force=False)`（约 2636 行），
它在**函数体内** `from generator import Generate`。这是 as-master 原本的设计，
不要动它。

### 1.4 外部依赖

| 依赖 | 用途 | 状态 |
|---|---|---|
| **PLY 3.11** | `generator/dbc/ascyacc.py` 用 LALR 解析 DBC | 已装（纯 Python，装一次） |
| ~~pycrc~~ | ~~RoD 的 CRC~~ | **已去掉** |
| pandas / openpyxl | `Dcm.py` / `Dem.py` 的 Excel 导入 | 已装（读通信矩阵要用） |

## 2 目录布局与"配置源 vs 生成物"的边界

```
app/platform/cvm0146/src/config/
  dbc/
    can1.dbc                 ← 整车网（实车 CAN1，250 kbps）
    can0.dbc                 ← 组合开关（实车 CAN3，500 kbps）
  CanIf/
    CanIf.json               ← 配置源（入库）
    GEN/                     ← 生成物（.gitignore 排除）
      CanIf_Cfg.c  CanIf_Cfg.h  CanIf.json（展开后的中间版，供人核对）
  PduR/PduR.json  → GEN/
  Com/Com.json    → GEN/
  CanTp/  Dcm/  Dem/  CanNm/  NvM/     ← 待建
```

**为什么 DBC 要拷到 `config/dbc/`**：

- `doc/福田系统设计/` 是参考资料，可能不随代码发布（而且里面还有公司内部文件）
- DBC 是**构建输入**，理应随代码走
- 缺点：要手工同步。约定：**系统设计更新 DBC 时，同时更新这一份**，
  并在提交信息里写清版本号（如 `can1.dbc @ 通信矩阵 V0.4_20251031`）

**为什么生成物不入库**：

改了 JSON 却忘了提交生成的 `.c`，是这类工具最典型的"仓库不一致"。
生成物根本不在版本库里，这个问题就不可能发生。`--gen` 可强制重新生成。

## 3 配置格式（已实测跑通的三份）

### 3.1 `CanIf.json` —— 最小形态

```json
{
  "class": "CanIf",
  "RxPacketPoolSize": 0,
  "TxPacketPoolSize": 0,
  "RxPacketDataSize": 64,
  "TxPacketDataSize": 64,
  "networks": [
    {
      "name": "CAN1",
      "me": "BCM",
      "dbc": "../dbc/can1.dbc",
      "RxPdus": [],
      "TxPdus": []
    }
  ]
}
```

`me` = DBC 里 `BO_ ... <sender>` 的那个名字。**本节点发的报文判 TX，其余判 RX。**

派生的 PDU 命名规则：`CAN1_<MSGNAME>_RX` / `_TX`（全大写，非字母数字转下划线）。

**实测结果**：CAN1 网络 → **34 条 RX + 6 条 TX**，宏 `CANIF_CAN1_*` 共 40 条，
按 ID 升序。

### 3.2 `PduR.json` —— 自动推导 + 手工路由

```json
{
  "class": "PduR",
  "routines": [
    { "name": "P2P_RX", "from": "CanTp", "to": "Dcm" },
    { "name": "P2P_TX", "from": "Dcm",  "to": "CanTp" }
  ],
  "networks": [
    { "name": "CAN1", "me": "BCM", "network": "CAN", "dbc": "../dbc/can1.dbc" }
  ]
}
```

- `networks` 里的报文路由**自动推导**：本节点发 → `Com → CanIf`；否则 `CanIf → Com`
- `routines` 是**手工的**，用于诊断（CanTp↔Dcm）这类不来自 DBC 的路由

**实测结果**：`PduR_Cfg.c` 25 KB，`PduR_Cfg.h` 2.4 KB。

### 3.3 `Com.json` —— `use_dbc` 自动导入信号

```json
{
  "class": "Com",
  "networks": [
    {
      "name": "CAN1", "network": "CAN", "device": "cvm0146", "port": 0,
      "baudrate": 250000, "me": "BCM",
      "use_dbc": true, "dbc": "../dbc/can1.dbc",
      "messages": []
    }
  ]
}
```

`messages` 留空 = 全量从 DBC 导入；需要覆盖某条报文时再往里写。

**实测结果**：

| 产物 | 规模 |
|---|---|
| `Com_Cfg.c` | **519 KB**（372 个信号的完整配置） |
| `Com_Cfg.h` | 35 KB，467 个宏 |
| `Com.json`（展开版） | 158 KB，可人工核对 |
| `bswcom.py` | 102 KB，RTE 接口模板（当前用不上） |

信号配置抽查（与 DBC 原文对照）：

```
DBC: SG_ BCM_LowBeamSts : 4|2@1+ (1,0) [0|3] ""
生成: BitPosition = 4   BitSize = 2   COM_LITTLE_ENDIAN   COM_UINT8
      ptr = &Com_PduData_BCM_LCSF_TX[0]（字节 0）
```

> **本项目的 372 个信号全部是 Intel 字节序**（`@1`），与 J1939-71 的规定一致
> （多字节参数用小端）。M10 那个 Motorola `BitPosition` 的坑在这个项目不会出现，
> 但生成器对 Motorola 也走同一套 `start & 7` 逻辑，换成别的项目照样正确。

## 4 未解决的问题：`hoh`（硬件对象句柄）

### 4.1 现象

生成的 `CanIf_Cfg.c` 里 **40 条 PDU 的 `hoh` 全是 0**。

原因在 `extract()`：`hrh` 是**每网络**递增的，不是每报文：

```python
pdu = {"name": rn, "id": msg["id"], "hoh": hrh, "up": "PduR"}   # hrh 在循环里不变
```

AS 的模型是"一个 hoh = 一个硬件接收对象"，可以有多条 PDU 共享。

### 4.2 为什么在 FlexCAN 上不可行

`hoh` 对应一个 RX 邮箱，而**一个邮箱只有一个掩码**。34 条不同 PGN 的报文
配 `hoh=0` 时，那个邮箱只能匹配其中一条。

### 4.3 硬件的真实约束（M14 实测）

- 按 **PF 分组**（掩码 `0x03FF0000`，屏蔽优先级 P + PS + SA）可以把 34 条收进 **6 个邮箱**
- 硬件掩码用 `0x03FF0000`（**不含优先级**，这样同一 PGN 不同优先级的帧都能收）
- 软件层（CanIf）的 mask 仍用 `0x1FFFFFFF` **精确匹配**

**两层分工**：硬件按 PF 段放行（宽），软件按完整 ID 过滤（窄）。

### 4.4 解决方案（下一步实施）

**核心思路：一份规则 → 两个产物，天然一致。**

在 `CanIf.json` 的 network 里加一张分组表：

```json
"hohGroups": [
  { "hoh": 2, "id": "0x18F00000", "mask": "0x03FF0000", "comment": "PF=0xF0" },
  { "hoh": 3, "id": "0x18FD0000", "mask": "0x03FF0000", "comment": "PF=0xFD" },
  { "hoh": 4, "id": "0x18FE0000", "mask": "0x03FF0000", "comment": "PF=0xFE" },
  { "hoh": 5, "id": "0x18FF0000", "mask": "0x03FF0000", "comment": "PF=0xFF" }
]
```

写一个前置脚本 `tools/gen_hoh.py`：

1. 读 `CanIf.json` + `hohGroups`
2. 给每条 PDU 按 `id & mask` 匹配分组，填上 `hoh` → 输出 `CanIf.gen.json`
3. **同时**用同一张表生成 `Can_Cfg.c` 的邮箱表（`CanHw_MsgCfgType` 数组）+ `Can_HwCfg.h` 的 ID 宏

这样 `CanIf` 和 `Can_Cfg` 不可能漂移——它们来自同一份 `hohGroups`。

> 这正是 M8 那个 `CanIfCfg_CheckRxOrder()` 自检想解决的问题的**根本解**：
> 不是"配错了再检查"，而是"配不错"。

### 4.5 为什么不直接改 as-master 的 `CanIf.py`

改它可以少一层，但会给上游合并带来持续成本。**保持生成器原样**，
在它前面加一层自己的预处理，是更划算的取舍。

## 6 接入构建（02.8，已落地）

### 6.1 没有照原计划把 JSON 塞进 `RegisterConfig`

本节原先的方案是：

```python
"CanIf": Glob("src/config/CanIf/CanIf.json")   # ← 最后没这么做
```

看起来最省事，实际走不通，三个理由都是实测出来的：

| 理由 | 具体情况 |
|---|---|
| 生成链是**有顺序的整体** | 五步：生成 → 注入（`sync_can` → `sync_canif` → `sync_pdur`，顺序有依赖）→ 拷入 Com → a4 断言 → 67 项对账。`RegisterConfig` 是**按库**触发、谁先 parse 谁先跑，表达不了这个序 |
| 三个文件是**手写 + `@generated` 区块** | `Can_Cfg.c` / `CanIf_Cfg.c` / `PduR_Cfg.c` 的区块外是人工设计说明（M14 的掩码教训、邮箱分组原理）。换成 `GEN/` 输出，这些注释就没了 |
| `Com_Cfg.c` 是"生成后拷入入库" | 编译单元从 `config/Com_Cfg.c` 换成 `GEN/Com_Cfg.c`，`CPPDEFINES`、`$Com_Cfg` 包含路径、`a4` 的 C4 判据全要跟着动，收益为零 |

**改用的做法**：把"配置生成"声明成一个 SCons **节点**（`.gen.stamp`），
让每个目标文件都依赖它。

```
build.bat → scons → SConstruct ──(--generate)→ ConfigSync() 后退出
                         │
                         └─ Building() → GetConfigStamp(env)
                                           │  env.Command(".gen.stamp", 70 个输入, 动作)
                                           ↓
                         Library.objs()  ─ 每个 .o  env.Depends(o, .gen.stamp)
                         Application.build() ─ App 自己的 .c 也显式 env.Object()
                                              后挂 Depends
                                           ↓
                              动作：tools/config.py sync
                                           ↓
                                  tools/gen_gate.py 判定
                          ┌────────────────┼────────────────┐
                     skip(0.5 s)       run(7.2 s)      blocked(rc≠0)
```

### 6.1.1 为什么是 stamp，而不是把 7 个产物声明成 Command 的 target

那 7 个文件里有 `Can_Cfg.c` / `CanIf_Cfg.c` / `PduR_Cfg.c` —— **手写 + `@generated` 区块**，
而且**是入库文件**。一旦成为 SCons 的 target，`scons -c` 会把它们从工作区删掉。
stamp 只表达"这批输入已经处理过"，一个产物都不碰。

### 6.1.2 依赖是双向可查的

| 事实 | 怎么验证 |
|---|---|
| 动作声明了 70 个输入（4 JSON + 2 DBC + 4 脚本 + 59 生成器 `.py`） | `scons --app=App -n --tree=derived` 第一行就是它们 |
| `.gen.stamp` 是 **56 个目标文件**的前置 | 同上，`--tree` 里数 `.gen.stamp` 出现次数 |
| 输入变了才跑动作 | 改一行 JSON → `[GEN] 输入变化：…`；不改 → 连 `[SKIP]` 都不打印（动作根本不执行） |

依赖清单不在这里维护：`ConfigInputs()` 直接复用 `gen_gate.INPUT_*`。
两处各写一份的话，"门禁认得的输入"和"SCons 认得的输入"会慢慢分叉。

> **客户 DBC 缺失时**：它不在输入清单里，SCons 不会报"源文件缺失"，
> 构建退回使用已入库产物。哪天 DBC 补进来，清单变化 → stamp 重建 → 自动生成。
> 这条替代了原来的"解析期降级分支"，并且不需要为它写特例。

### 6.2 判定表（`gen_gate.check()`，唯一实现）

| 情况 | 结论 | 动作 |
|---|---|---|
| 输入指纹变了 / 产物漂移 / 无状态 | `run` | 跑五步，成功后落状态 |
| 输入与产物都没变 | `skip` | 0.5 s 过（判定本身 36 ms） |
| 缺 DBC + 无状态 | `degrade` | 用已入库产物构建（新克隆的正常路径） |
| 缺 DBC + 输入变了 | `blocked` | **rc=2 停止构建**，不拿旧配置冒充新配置 |
| 缺 JSON / 注入脚本 | `blocked` | 同上 |
| `--force` / `--gen` | `run` | 无条件重生成 |

输入指纹覆盖：4 份 JSON（`Can`/`CanIf`/`PduR`/`Com`）+ 2 份 DBC +
`tools/generator/**/*.py` + 3 个注入脚本 + `config.py`。
产物指纹覆盖生成链会重写的 7 个入库文件（实测 `generate --force` 前后
比对 `config/` 全部 59 个文件的 mtime 得出，不是从脚本里读出来的）。

### 6.3 用法

```sh
build.bat --app=App              # 日常：配置没变就跳过，变了自动生成后再编
build.bat --app=App --gen        # 强制重生成（等价 config.py generate --force）
build.bat --generate             # 只同步配置，不编译（不带 --app 也行）
python tools/config.py sync --check   # 只报告判定，不写文件
```

`--generate` 的短路点在 **`SConstruct` 里、`SConscript()` 之前**。为什么：
不带 `--app` 时 `BUILD_DIR` 没有 app 子目录，各 SConscript 的 `variant_dir`
会撞在一起，`@register_application` 第二次执行直接抛
`KeyError: app App already registered`。

`scons -c` 不会跑生成动作 —— 它只清 target，而 stamp 的 target 就是那个
`.gen.stamp` 文件（已 gitignore）。实测 `build.bat --app=App -c` 输出里
生成相关行数为 0。

### 6.4 顺带修掉的两个真缺陷

**① `Com_Cfg.c` 的工作区版本是 CRLF，仓库里是 LF**

| 位置 | 大小 | 行尾 |
|---|---|---|
| 工作区 `config/Com_Cfg.c` | 527,384 B | CRLF × 16,834 |
| 仓库 blob | 510,550 B | LF |

差值 16,834 B **正好等于行数**。原因是生成器以文本模式写文件，Windows 下
`\n` 被翻译成 CRLF；而 `.gitattributes` 规定 `*.c text eol=lf`，git 会把
差异归一，所以 `git status` 看不见。

后果：**"重新生成无 diff"只在 git 层成立，字节层不成立**。
门禁的产物比对因此一律先做 LF 归一 —— 否则 CRLF 的产物会永远被判成漂移，
每轮构建都白跑一遍 7 s。

根治办法是给生成器的 `open()` 加 `newline="\n"`（`Board.py` 已经这么改过），
但那要动 30 多个生成器文件，属于独立任务，本期不做。

**② `.gendb.pkl` 的缓存键不含生成器源码**

`CalcHash()` 原先只哈希 JSON + 引用的 DBC。于是"改了生成器、JSON 没动"时，
`Generate()` 判定"没变化"，直接返回上次结果 —— **改了却不生效，且没有提示**。

怎么发现的：往 `Com.py` 插一行注释输出当探针，连跑两遍 `Com_Cfg.c`
一个字节都没变。`a4_gen_check` 的 C1（幂等）也抓不到 ——
它证明的是"稳定地一致"，不是"稳定地更新"。

修法：`_gen_src_digest()` 把 `tools/generator/**.py`（除 PLY 自动生成的
`parsetab.py`）算进缓存键，进程内只算一次（1.3 MB，约 10 ms）。

修完的实测（探针仍在 `Com.py` 里）：

```
[GEN] 输入变化：tools/generator/__init__.py
CC 行数: 1                                    ← 只重编 Com_Cfg.c
探针在 Com_Cfg.c: 1
text 241084  data 1712  bss 15040             ← 注释不影响镜像
```

撤掉探针再构建：`CC 行数: 1`、探针消失、`git diff` 为空、镜像尺寸逐项不变。

### 6.5 并发构建

`App` / `AppB` 两次 `build.bat` 同时跑时：

- **生成串行化**：`.genlock`（`O_CREAT|O_EXCL`，600 s 视为残留自动清）。
  拿到锁后**再判一次**指纹 —— 等锁期间另一个进程可能已经生成完了，
  不加这一判会白跑两遍 7 s 并互相覆盖产物。
- **`.gendb.pkl` 原子落盘**：写进程私有 tmp（带 pid）再 `os.replace`。
  旧实现直接 `pickle.dump` 到目标文件，并发时后写的那次可能只写一半，
  下次读直接抛异常。现在读到损坏文件会当空缓存处理（最坏多生成一次）。
- **`.sconsign.dblite` 仍是全仓库共享**，两次 scons 并发写同一棵树本来就
  不安全。这一层没解决，记为**已知边界**：不要在同一工作区并发跑两个构建。

## 7 复现步骤（换一台机器）

```sh
# 1. 确认依赖
python -c "import ply, pandas, openpyxl; print('ok')"

# 2. 直接构建：门禁会判断要不要生成
cmd //c "build.bat --app=App"

# 想只跑生成链、不编译：
cmd //c "build.bat --generate"

# 想跑完整断言（生成两遍 + 幂等 + 副本一致 + 注入区块）
python tools/a4_gen_check.py
```

**没有客户 DBC 的机器**（新克隆的默认状态）：第一步会打印

```
[DEGRADED] 缺客户 DBC 且无生成记录：用已入库产物构建
           缺：dbc/can0.dbc、dbc/can1.dbc
```

然后正常编译 —— 用的是仓库里已入库的 `config/*_Cfg.c`。这是**正常路径**，
不是降级凑合：那 7 个文件本来就是"上一次用 DBC 生成的快照"。

但**改了 JSON 却没有 DBC** 会被拦住（rc=2），因为那种情况下无法重新生成，
继续构建就等于拿旧配置冒充新配置。

### 7.1 三条硬规矩（A4 落地后不再靠自觉）

1. **不许在生成物里写时间戳**（`GenHeader` 已去掉）。带时间戳的产物
   第二遍生成就和第一遍不同，"重新生成无 diff"这个判据永远不成立。
2. **不许手改 `@generated` 区块内的内容**。`CanIf_Cfg.c` / `PduR_Cfg.c` 里
   `@generated BEGIN … END` 之外随便改，之内一定被脚本覆盖。
   门禁的产物漂移检测会看到手改（区块外也算），并在下一次构建时重新生成 ——
   区块外的改动会被保留（那些是人工内容），区块内的会被覆盖。
3. **`config/Com_Cfg.c|h` 是生成物入库**。改信号要改 `Com/Com.json` 或
   `dbc/can1.dbc`，让门禁自己去重生成；直接改 `.c` 会在下一次生成时消失。
